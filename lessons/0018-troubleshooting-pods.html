2. 實作 A：五粒壞 Pod 診斷賽

逐份 YAML 存檔、套用、診斷、修復。修 Pod 口訣：搵到根因 → 改 YAML → 刪咗重套（Pod 開咗之後大部份 spec 改唔到，唔好嘥時間）。第一粒：個 image tag 根本唔存在。

pod1-bad-image.yaml — 映像 tag 唔存在
apiVersion: v1
kind: Pod
metadata:
  name: bad-image
spec:
  containers:
  - name: app
    image: nginx:9.99
診斷 1：映像拉唔到
# 1. 套用後睇 STATUS——先係 ErrImagePull，重試幾次變 ImagePullBackOff
nano pod1-bad-image.yaml
kubectl apply -f pod1-bad-image.yaml
kubectl get pod bad-image

# 2. describe 搵根因：Events 嘅 Failed to pull image 會寫出真相
kubectl describe pod bad-image

# 3. 修復：tag 改返存在嘅版本，刪咗重套
nano pod1-bad-image.yaml
kubectl delete pod bad-image --wait=false
kubectl apply -f pod1-bad-image.yaml
kubectl get pod bad-image
你應該觀察到咩

ImagePullBackOff 嘅根因幾乎全部寫喺 describe 嘅 Events 最尾嗰筆（例如 manifest unknown／not found）。佢會指數退避自動重試，所以「搞掂就刪咗重套」可以即刻觸發新一輪拉取。

pod2-missing-cm.yaml — env 引用唔存在嘅 ConfigMap
apiVersion: v1
kind: Pod
metadata:
  name: missing-cm
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: APP_ENV
      valueFrom:
        configMapKeyRef:
          name: app-env
          key: APP_ENV
診斷 2：容器開都開唔到
# 4. 套用：STATUS 出 CreateContainerConfigError——容器連建立都失敗
nano pod2-missing-cm.yaml
kubectl apply -f pod2-missing-cm.yaml
kubectl get pod missing-cm

# 5. describe 嘅 Events 直接點名：configmap "app-env" not found
kubectl describe pod missing-cm

# 6. 修復：補返唔見咗嘅 ConfigMap（0006 嘅老朋友）
kubectl create configmap app-env --from-literal=APP_ENV=prod
kubectl delete pod missing-cm --wait=false
kubectl apply -f pod2-missing-cm.yaml
kubectl get pod missing-cm
kubectl exec missing-cm -- sh -c 'echo $APP_ENV'
pod3-crash.yaml — 程式一起身就 exit 1
apiVersion: v1
kind: Pod
metadata:
  name: crash-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo starting; exit 1"]
診斷 3：CrashLoopBackOff
# 7. 套用：CrashLoopBackOff——容器不斷「起身即死」
nano pod3-crash.yaml
kubectl apply -f pod3-crash.yaml
kubectl get pod crash-demo

# 8. 睇日誌：程式自己印咗 starting 之後 exit——死因寫晒喺度
kubectl logs crash-demo

# 9. --previous：上一輪容器（死咗嗰個）嘅日誌——CrashLoop 救星
kubectl logs crash-demo --previous

# 10. 修復：拎走 exit 1，轉返做瞓覺指令
nano pod3-crash.yaml
kubectl delete pod crash-demo --wait=false
kubectl apply -f pod3-crash.yaml
kubectl get pod crash-demo
pod4-oom.yaml — 食爆記憶體上限
apiVersion: v1
kind: Pod
metadata:
  name: oom-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "i=$(dd if=/dev/zero bs=1M count=4 2>/dev/null | tr '\\0' a); while :; do i=$i$i; done"]
    resources:
      limits:
        memory: 64Mi
診斷 4：OOMKilled（唔係程式自己 crash）
# 11. 套用：字串每圈加倍，幾秒內就撞埋 64Mi 嗰埲牆
#     （若果你個 busybox 冇將 \0 換成 a、字串係空所以唔爆，
#       就將 dd 嘅 count=4 改成 count=64 加大起點再試）
nano pod4-oom.yaml
kubectl apply -f pod4-oom.yaml
kubectl get pod oom-demo
#    會見到 CrashLoopBackOff 或者不斷重啟

# 12. describe：Last State 嘅 Reason 係 OOMKilled、Exit Code 137——呢個係「畀人殺」唔係「自爆」
kubectl describe pod oom-demo
#    Exit Code 137 = 128 + 9（SIGKILL）＝畀 OOM killer 斬咗

# 13. 修復：改個應用（將無限膨脹嘅迴圈換返做正常指令）
nano pod4-oom.yaml
kubectl delete pod oom-demo --wait=false
kubectl apply -f pod4-oom.yaml
kubectl get pod oom-demo
OOMKilled 同 CrashLoopBackOff 點分？

Exit Code 係關鍵線索：137＝畀 OOM 殺、非零但唔係 137＝程式自己瓜。記憶體相關仲有個前兆：describe 嘅容器 State 會寫 Reason: OOMKilled，而 logs 成日空空如也（佢嚟唔切印嘢就畀人斬）。見到 137 先check limits，唔好走去追程式邏輯，貼地啲！

🐳 Docker 老朋友帶路：K8s 除錯 = Docker 除錯放大版

玩過 Docker 嘅話，呢三招你一早識——K8s 只係換個名：

Docker 嗰陣K8s 呢度記法
docker ps 睇 STATUSkubectl get pod 睇 STATUS都係先睇「死成點」
docker logs 容器kubectl logs pod（-c 名 / --previous）聽佢自己講遺言
docker exec -it 容器 shkubectl exec -it pod -- sh入去眼見為實
docker inspect 睇死因kubectl describe pod 睇 Events＋ReasonK8s 獨有：連排程原因都寫埋

一句記晒：describe = inspect＋事件簿，logs --previous = 攞死者遺書，exec = 入屋搜證。

🔪 兇案現場：137（畀人殺）vs 非 137（自爆）

兩個死者都係 CrashLoop，但兇手完全唔同——並排睇 describe 嘅驗屍報告：

🔪 畀 OOM 斬（Exit 137）💥 自己瓜（Exit 1）
Reason: OOMKilled
Exit Code: 137
Last State: Terminated
logs 多數空白（嚟唔切講嘢）
→ 唔好追 code，去加 limits／修條無限膨脹迴圈		 Reason: Error
Exit Code: 1
Last State: Terminated
logs --previous 有遺言（starting…）
→ 追程式邏輯，改 command／entrypoint

查案口訣：先睇 Exit Code，再睇 Reason，最後先睇 logs 有冇遺言。137 一定係 128＋9（SIGKILL）——即係系統出手，唔係佢自己想死。

pod5-readiness.yaml — 探針打錯 port（溫習 0007）
apiVersion: v1
kind: Pod
metadata:
  name: not-ready
spec:
  containers:
  - name: app
    image: nginx:1.25
    readinessProbe:
      httpGet:
        path: /
        port: 8080
      periodSeconds: 3
診斷 5：Running 但唔 Ready
# 14. 套用：STATUS Running 但 READY 0/1——服務明明生勾勾，只係過唔到探針
nano pod5-readiness.yaml
kubectl apply -f pod5-readiness.yaml
kubectl get pod not-ready

# 15. describe：Events 寫 Readiness probe failed（GET 8080 失敗）
kubectl describe pod not-ready

# 16. 修復：port 改返 80
nano pod5-readiness.yaml
kubectl delete pod not-ready --wait=false
kubectl apply -f pod5-readiness.yaml
kubectl get pod not-ready

3. 實作 B：logs 技巧同多容器

考場成日瀨嘢位：粒 Pod 有兩隻容器，你唔指名睇邊隻，kubectl 即刻彈你轉頭。

pod-logs.yaml — 一粒 Pod 兩隻容器
apiVersion: v1
kind: Pod
metadata:
  name: logs-demo
spec:
  containers:
  - name: web
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo web-ok; sleep 2; done"]
  - name: debug
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo debug-line; sleep 3; done"]
多容器嘅 logs 旗標
# 17. 多容器 Pod 一定要 -c 指名睇邊隻（唔畀會報錯叫你指定）
nano pod-logs.yaml
kubectl apply -f pod-logs.yaml
kubectl logs logs-demo -c web --tail=3
kubectl logs logs-demo -c debug --tail=3

# 18. 其他常用旗標：--tail=N 只睇最尾 N 行；-f 一路跟住睇
kubectl logs -f logs-demo -c web
#    Ctrl+C 離開 -f

# 19. Events 都係破案證據：sort-by 將最新事件排到最底睇
kubectl get events --sort-by=.lastTimestamp | tail -n 10
收尾：清乾淨，個叢集返返去「乾淨」狀態
# 20. 刪走今課全部練習物件
kubectl delete pod bad-image missing-cm crash-demo oom-demo not-ready logs-demo
kubectl delete configmap app-env
rm -f pod1-bad-image.yaml pod2-missing-cm.yaml pod3-crash.yaml pod4-oom.yaml pod5-readiness.yaml pod-logs.yaml
kubectl get pods -A
考場小抄

① 症狀→第一指令對照表（上面嗰張）背到識背。② CrashLoop 三連：get pods → describe 睇 Events → logs；上次死咗嘅日誌用 --previous（必背）。③ Exit Code：137＝OOM、其他非零＝程式自爆。④ 多容器：logs -c 名、exec -c 名。⑤ 修 Pod 一律「刪咗重套」，唔好諗住熱修 spec。⑥ Pending 先睇 Events：Insufficient memory／cpu、nodeSelector 冇 Node、taint 冇 toleration——全部寫晒喺 Events。

本課戰果

  • 你建立咗「get → describe → logs → exec」嘅系統化除錯流程。
  • 你修好五粒經典壞 Pod：ImagePullBackOff、CreateContainerConfigError、CrashLoopBackOff、OOMKilled、READY 0/1。
  • 你學識 logs 嘅 --previous／--tail／-f／-c 技巧，仲識用 Events 排序輔助判讀。
