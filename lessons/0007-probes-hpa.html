Lesson 0007：Probes 同 HPA

目標：搞掂三種 Probe（liveness／readiness／startup）同 HPA 自動加減副本，親手睇下重啟、READY 0/1 同 CPU 爆煲點樣長胖，排錯唔再企喺度！

💡 點解呢課咁重要？
上一課啲 Pod 攞啱設定，而家要佢哋識得「自己照顧自己」。貼地講：隻 app 卡死咗邊個殺佢重嚟？未 warm up 好點樣唔好派客畀佢？流量爆煲點自動加機？呢啲正正係 Troubleshooting（30%）最鍾意考嘅症狀！

上堂將設定交咗畀 Pod；今課等 Pod「識得照顧自己」：① Probe（探針）等 kubelet 睇得出隻容器係「生勾勾但病咗」定係「搞掂可以接客」；② HPA（HorizontalPodAutoscaler）等 Deployment 嘅副本數跟住 CPU 用量自動加減。兩個都係 CKA Workloads 領域嘅常客，而且探針寫錯搞出嚟嘅「READY 0/1」「CrashLoopBackOff」正正係 Troubleshooting 最愛出嘅題。本課個 cluster 沿用之前雙節點，開場乾淨晒。

1. 三種探針：生勾勾、接唔接得、等大個

Pod 嘅 spec.containers[]. 下面可以掛三種探針，kubelet 照 periodSeconds 週期性去探、失敗超過 failureThreshold 次就出手：

探針問緊咩失敗咩後果典型用途
livenessProbe
（生勾勾咩）		 隻容器仲生勾勾、冇卡死？ 殺咗隻容器再重啟 捉死結、記憶體漏水後冇反應
readinessProbe
（接得客咩）		 隻容器接唔接得流量？ 喺 Service 嘅 Endpoints 摘走（唔重啟） 起動慢、要 warm up 或者載大 model 嘅 service
startupProbe
（等大個咩）		 隻容器起好未？ 失敗照 restartPolicy 處理；成功之前唔跑另外兩種探針 要起好耐嘅容器（唔好畀 liveness 誤殺）

三種探針都有三種寫法：exec（走條 command 睇 exit code）、httpGet（HTTP GET 睇 2xx/3xx）、tcpSocket（TCP 駁唔駁到）。記住口訣：liveness 失敗＝重啟；readiness 失敗＝暫時唔好派客嚟；startup 等佢大個先。

🩺 三探針分工圖：kubelet 醫生巡房

記住方向：永遠係 kubelet 左邊出發，探右邊嘅 Pod。後果兩條路完全唔同。

2. HPA：CPU 一高就加副本

HPA 係一個控制器，週期性問 metrics API「呢班 Pod 平均 CPU 用咗幾多」，除以「每粒 Pod 申報嘅 requests.cpu」得出利用率百分比，超過 targetCPUUtilizationPercentage（例如 50%）就調高 Deployment 副本數。前提有二：

  • 個 cluster 裝咗 metrics-server（收齊節點同 Pod 用量，餵畀 metrics API）——本課實作 C 會裝。
  • Pod 有寫 resources.requests.cpu——冇寫就冇分母，HPA 計唔到百分比（TARGETS 顯示 <unknown>）。

縮返落嚟另有冷卻邏輯：連續幾輪都低過目標先縮，唔好彈上彈落（flapping）。HPA 只搞「副本數」；Pod 本身食幾多資源唔關佢事。

🥤 HPA 計數杯：80m ÷ 100m = 80% > 50% 即加機

HPA 條數好簡單：實際用量 ÷ 你申報嘅 requests。有分母先計到數。

3. 實作 A：liveness 故意失敗 → 睇住佢重啟

liveness-demo.yaml — 30 秒後自己「裝死」
# liveness-demo.yaml — 容器先摸出 /tmp/healthy，30 秒後把它刪掉
apiVersion: v1
kind: Pod
metadata:
  name: liveness-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600"]
    livenessProbe:
      exec:
        command: ["cat", "/tmp/healthy"]
      initialDelaySeconds: 5
      periodSeconds: 5
套用、觀察、看事件
# 1. 套用後先看它 Running（前 30 秒檔案還在，探針成功）
nano liveness-demo.yaml
kubectl apply -f liveness-demo.yaml
kubectl get pod liveness-demo

# 2. -w 持續看：約 30 秒後 RESTARTS 開始往上加
kubectl get pod liveness-demo -w
#    每失敗一次就重啟一次，重啟太密集會看到 CrashLoopBackOff

# 3. describe 看事件鏈：Liveness probe failed → Killing → 重新 Created
kubectl describe pod liveness-demo
#    Events 會出現 "Liveness probe failed" 與 "Container liveness-demo died"
修復：把裝死的那行刪掉
# 4. nano 編輯：command 改回只做 sleep（拿掉 rm -f /tmp/healthy）
#    注意：Pod 的 command／探針欄位一旦建立就「不可改」——直接刪掉重套最快
nano liveness-demo.yaml
kubectl delete pod liveness-demo
kubectl apply -f liveness-demo.yaml

# 5. 重新建立後 RESTARTS 停在 0，不再重啟
kubectl get pod liveness-demo

# 6. 觀察夠了，收掉
kubectl delete pod liveness-demo
你應該觀察到咩

第 2–3 步就係「liveness 失敗＝重啟」嘅現場：隻容器明明仲跑緊（process 未退出），但 kubelet 判佢「唔健康」就成粒砍咗重嚟。呢個就係 CrashLoopBackOff 嘅成因之一——唔係隻程式炒，係探針判佢死。第 4 步「Pod 起咗之後探針欄位改唔到」都係考點嚟。

4. 實作 B：readiness 打錯 port → READY 0/1

readiness-demo.yaml — 探測一個沒有服務的 port
# readiness-demo.yaml — nginx 只聽 80，readiness 卻去戳 8080
apiVersion: v1
kind: Pod
metadata:
  name: readiness-demo
spec:
  containers:
  - name: app
    image: nginx:1.25
    readinessProbe:
      httpGet:
        path: /
        port: 8080
      initialDelaySeconds: 3
      periodSeconds: 3
套用：容器活著，但 READY 0/1
# 7. 套用後看：STATUS = Running，但 READY = 0/1
nano readiness-demo.yaml
kubectl apply -f readiness-demo.yaml
kubectl get pod readiness-demo

# 8. describe 看 Events：readiness 探測 8080 失敗
kubectl describe pod readiness-demo
#    "Readiness probe failed"——容器沒被殺掉，只是被標成不 Ready
修復：port 改回 80
# 9. nano 把 8080 改成 80
nano readiness-demo.yaml
kubectl delete pod readiness-demo
kubectl apply -f readiness-demo.yaml

# 10. READY 1/1——修好了
kubectl get pod readiness-demo

# 11. 收掉
kubectl delete pod readiness-demo
你應該觀察到咩

第 7 步個 READY 0/1 就係「liveness 同 readiness 分家」嘅最佳教材：隻容器冇畀人重啟（liveness 冇寫就當過），但 Service 唔會派流量畀佢。下一課學 Service 嗰陣，呢粒 READY 0/1 嘅 Pod 就會直接喺 Endpoints 消失——而家記住「READY 分母唔滿＝有探針瀨嘢」就得。整返好 READY 即刻彈返 1/1。

startup-demo.yaml — 慢啟動容器 + startupProbe 護航
# startup-demo.yaml — 容器要 45 秒才「啟動完成」，startupProbe 先擋著、liveness 暫不開跑（參考寫法，不動本課步驟）
apiVersion: v1
kind: Pod
metadata:
  name: startup-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 45; touch /tmp/started; sleep 600"]
    startupProbe:
      exec:
        command: ["cat", "/tmp/started"]
      periodSeconds: 5
      failureThreshold: 12      # 啟動預算 = 12 × 5 秒 = 60 秒，遠大於 45 秒的啟動時間
    livenessProbe:
      exec:
        command: ["cat", "/tmp/started"]
      periodSeconds: 5
#    關鍵：liveness 沒寫 initialDelaySeconds。startup 成功前 liveness／readiness 都不跑，
#    所以慢啟動不會被誤殺；startup 一成功，liveness 立刻接手。沒有 startupProbe 的年代，
#    只能用 initialDelaySeconds 猜啟動時間——猜太短＝啟動到一半被殺（小抄 ② 的症狀）。

# 想親眼看（約 2 分鐘，非本課編號步驟）：
nano startup-demo.yaml
kubectl apply -f startup-demo.yaml
kubectl get pod startup-demo -w
#    前 45 秒：READY 0/1、RESTARTS 0——startup 還在等，沒有人被殺
kubectl describe pod startup-demo
#    Events 連續幾次 "Startup probe failed"，45 秒後歸於安靜；READY 轉 1/1
kubectl delete pod startup-demo
rm -f startup-demo.yaml

5. 實作 C：裝 metrics-server + HPA 現場擴縮

metrics-server 係成個 cluster 嘅「用量收數佬」，HPA 同 kubectl top 都靠佢。裝咗先（今課裝完留返，之後啲課要用 top）：

安裝 metrics-server（kind 需加一個參數）
# 12. 官方 manifest（latest release 的 components.yaml）
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 13. kind 的 kubelet 沒設 TLS 認證——加 --kubelet-insecure-tls（只有本機測試叢集這樣做）
kubectl -n kube-system patch deployment metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deployment/metrics-server

# 14. 等約 15–30 秒讓它收第一筆資料，驗證 metrics API 有東西
kubectl top nodes
kubectl top pods -A
top 空轉 / HPA 冇反應，第一時間查 metrics-server

如果 kubectl top nodes 彈 error: metrics not available yet：等 30 秒再試；仲係唔得就 kubectl -n kube-system logs deployment/metrics-server --tail=20 睇下有冇 TLS 或者連線問題。HPA「好似冇反應」九成係 metrics-server 冇餵料或者 Pod 冇寫 requests——呢條排錯路考試會考完又考。

準備一個會喘的 Deployment
# 15. 產出帶 requests 的 Deployment（HPA 需要分母）
kubectl create deployment hpa-demo --image=nginx:1.25 --replicas=1 --dry-run=client -o yaml > hpa-demo.yaml
nano hpa-demo.yaml
#    spec.template.spec.containers[0] 加：
#      resources:
#        requests:
#          cpu: 100m
kubectl apply -f hpa-demo.yaml
kubectl rollout status deployment/hpa-demo

# 16. 建 Service（HPA 不需要，但等一下壓力來源要靠它）
kubectl expose deployment hpa-demo --port=80

# 17. 下 autoscale 指令：平均 CPU 超過 50% 就加副本，最多 5 顆
kubectl autoscale deployment hpa-demo --cpu-percent=50 --min=1 --max=5

# 18. 看 HPA：現在沒流量，TARGETS 顯示 <unknown> 或很低的百分比
kubectl get hpa
施加壓力，看它長胖
# 19. 開「第二個」WSL2 終端，跑 2–3 個無限迴圈同時打 hpa-demo 的 Service
#     （單一 load-gen 對靜態 nginx 頁的壓力可能不夠，多開幾個比較保險）
kubectl run load-gen --image=busybox:1.36 --restart=Never -- sh -c 'while true; do wget -q -O- http://hpa-demo > /dev/null; done'
kubectl run load-gen2 --image=busybox:1.36 --restart=Never -- sh -c 'while true; do wget -q -O- http://hpa-demo > /dev/null; done'

# 20. 先確認用量真的有上去（TARGETS 有數字、top 看得到 CPU 在爬）
kubectl top pods -l app=hpa-demo

# 21. 回第一個終端，盯著 HPA 與 Pod——約 1–2 分鐘後 REPLICAS 往上爬
kubectl get hpa -w
kubectl get pods -l app=hpa-demo -w
#    TARGETS 超過 50%，副本數 1 → 2 → 3 …（每次調整間隔約 15–30 秒）

# 22. 觀察夠了，到第二個終端停掉壓力來源
kubectl delete pod load-gen load-gen2
收縮、收尾
# 23. 回第一個終端：壓力停掉後不會立刻縮——HPA 要連續幾輪低於目標才縮
kubectl get hpa -w
kubectl get pods -l app=hpa-demo -w
#    幾分鐘後副本數會慢慢回到 1（冷卻避免抖動）

# 24. 不等它縮完也行，直接收尾
kubectl delete deployment hpa-demo
kubectl delete service hpa-demo
kubectl delete horizontalpodautoscaler hpa-demo
rm hpa-demo.yaml

# 25. 課末確認：叢集乾淨、metrics-server 保留在 kube-system
kubectl get nodes
kubectl get pods -n kube-system
你應該觀察到咩

第 20–22 步就係 HPA 嘅完整一生：先確認 top 有數（壓力真係食到 CPU）→ TARGETS 過咗 50% → Deployment 嘅 replicas 畀人調高 → 新 Pod 陸續 Ready。第 23 步「唔即刻縮」係縮放冷卻（cooldown）：HPA 用最近幾輪平均值做決定，唔想流量一震就狂縮狂放。

🌳 症狀分叉樹：三秒斷症

先睇 kubectl get pod 兩個欄，再對 describe 嘅 event 句式，唔使估。

考場小抄

① 三探針口訣：liveness 失敗＝重啟；readiness 失敗＝摘流量；startup 等大個先。 ② 症狀判斷：READY 0/N → readiness 探針瀨嘢；RESTARTS 升 → liveness 失敗或者隻程式真炒；「起得慢成日畀人殺」→ 加 startupProbe。③ HPA 三前提：metrics-server 有料、Pod 有 requests、target 啱——出事照次序查。④ 指令：kubectl autoscale deployment NAME --cpu-percent=50 --min=1 --max=5、kubectl get hpa。⑤ 整探針：Pod 起咗之後探針欄位改唔到，刪咗重套。

本課戰果

  • 你親眼睇住 liveness 失敗觸發容器重啟（RESTARTS 升），仲整返好佢。
  • 你睇住 readiness 失敗搞到 READY 0/1（容器生勾勾但唔接客），仲整返好佢。
  • 你用 startupProbe 幫慢熱容器護航：起好之前 liveness 唔開跑（READY 0/1、RESTARTS 0），唔使再靠 initialDelaySeconds 估時間。
  • 你喺 kind 裝好 metrics-server，仲用 kubectl top 驗證咗 metrics API。
  • 你用 kubectl autoscale 完成一次真嘅 CPU 驅動擴縮：加壓變大隻、停壓慢慢縮返。
