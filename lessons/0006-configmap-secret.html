Lesson 0006：ConfigMap 同 Secret

目標：唔再將設定寫死喺 image 入面，搞掂 ConfigMap 同 Secret 兩種注入手法（env 同 volume），親手睇下熱更新同 base64 陷阱，考試見到唔會瀨嘢！

💡 點解呢課咁重要？
上一課搞掂 Pod 擺邊，而家要搞掂 Pod 入面食咩設定。貼地講：dev 同 prod 用同一個 image，只係換設定——密碼改咗唔使 rebuild image。考場成日用 base64 係咪加密呢啲位捉你，呢課一次過拆掂佢！

上一課搞掂 Pod「放邊度」；今課搞掂 Pod 嘅「內容物」：設定。將設定寫死喺 Dockerfile（ENV、config 檔）入面，你就要為每個環境各起一個 image——dev 一個、prod 一個，改個密碼又要 rebuild。Kubernetes 嘅答案係將設定抽做獨立物件，等同一個 image 周圍用、設定隨環境換。兩個主角登場：ConfigMap（非機密設定）同 Secret（機密嘢）。兩個都係 namespace 層級、大細上限約 1MiB 嘅細粒鍵值／檔案庫。

1. ConfigMap vs Secret：機密同非機密要分開

ConfigMapSecret
裝咩 非機密設定（環境名、URL、開關） 機密資料（密碼、Token、憑證）
值點擺 明文 base64 編碼（唔係加密！）
點睇 describe 直接睇到內容 describe 只顯示位元組數
預設檔案權限 0644 0644（同 ConfigMap 一樣；想收緊可設 defaultMode: 0400）
必背：base64 ≠ 加密

Secret 嘅 data 用 base64 編碼，純粹係為咗等啲值塞得入 YAML（咩古怪字元都擺到）。只要有人對個 cluster 有讀權，kubectl get secret -o yaml 再 base64 -d 就還原到——Secret 唔係加密機制。考試最鍾意捉呢個：以為 base64 就等於加密。真加密（etcd 加密、外部 KMS）係另一回事，CKA 只考到「識得分辨唔係加密」。

🔓 base64 三步解碼帶：攞 → 天書 → 人話

記住：base64 係摩斯密碼，唔係鎖——人人識篤，一篤就開。

2. 兩條注入路：環境變數 vs 檔案掛載

ConfigMap／Secret 自己唔會做嘢，要注入入 Pod 先有用。兩條路差在「改完設定邊個會變」：

  • env（環境變數）：env.valueFrom.configMapKeyRef／secretKeyRef 攞「單一鍵」，或者 envFrom 一次過灌「成包」。容器一起身就定死——之後改設定，跑緊嗰粒唔會更新。
  • volume（檔案掛載）：將每個鍵變成一個檔名、值變成檔內容。kubelet 週期性 sync，改完設定約 1 分鐘內啲檔會自動更新（唔使重啟 Pod；隻 app 要自己識得偵測檔案變化）。

選擇貼士：要重啟先生效就用 env；想熱更新就用 volume。本課個 cluster 沿用之前雙節點、無殘留嘅乾淨場。

📦 注入路時間線漫畫：env 快照 vs volume 熱更新

睇住同一個改動，兩條路命運完全唔同。T = 改 ConfigMap 前後嘅時間。

3. 實作 A：ConfigMap 兩種注入都試勻

建立 ConfigMap 並檢視
# 1. --from-literal 一次帶多鍵（key=value 一一列出）
kubectl create configmap app-config --from-literal=APP_ENV=prod --from-literal=LOG_LEVEL=info

# 2. DATA 欄顯示有幾個鍵
kubectl get configmaps

# 3. describe 直接讀回明文內容
kubectl describe configmap app-config
pod-env.yaml — envFrom 整包注入
# pod-env.yaml — 用 envFrom 把整包 configmap 灌成環境變數
apiVersion: v1
kind: Pod
metadata:
  name: env-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    envFrom:
    - configMapRef:
        name: app-config
套用並進容器驗證
# 4. 用 nano 寫好上面那份後套用
nano pod-env.yaml
kubectl apply -f pod-env.yaml
kubectl get pod env-demo

# 5. exec 進去看環境變數——每把 key 都是一個環境變數
kubectl exec env-demo -- sh -c 'env | grep -E "APP_ENV|LOG_LEVEL"'
pod-vol.yaml — 同一個 ConfigMap 掛成檔案
# pod-vol.yaml — 把 configmap 掛成 /etc/config 下的檔案
apiVersion: v1
kind: Pod
metadata:
  name: vol-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: cfg
      mountPath: /etc/config
  volumes:
  - name: cfg
    configMap:
      name: app-config
套用、觀察鍵變檔名，再改設定睇傳播延遲
# 6. 套用後等待 Running
nano pod-vol.yaml
kubectl apply -f pod-vol.yaml
kubectl get pod vol-demo

# 7. 掛載的樣貌：每個鍵是一個檔名，內容是它的值
kubectl exec vol-demo -- ls /etc/config
kubectl exec vol-demo -- cat /etc/config/APP_ENV

# 8. 改 ConfigMap：APP_ENV 改成 staging（dry-run 產 YAML 再 apply，之前學過的老朋友）
kubectl create configmap app-config --from-literal=APP_ENV=staging --from-literal=LOG_LEVEL=debug --dry-run=client -o yaml | kubectl apply -f -

# 9. 立刻 cat——還是 prod；kubelet 週期同步不是即時的
kubectl exec vol-demo -- cat /etc/config/APP_ENV

# 10. 等約 1 分鐘再 cat——變 staging 了
kubectl exec vol-demo -- cat /etc/config/APP_ENV
你應該觀察到咩

第 7 步睇下 volume 注入個「樣」：鍵變咗檔名。第 8–10 步係關鍵對比——改 ConfigMap 唔會自動重啟任何 Pod，但掛載住佢嘅 volume 會畀 kubelet 週期性 sync（約 1 分鐘）。對照返：env-demo（env 注入）嘅環境變數永遠停喺起動嗰刻個值，就算 ConfigMap 改咗都唔郁。

4. Secret：玩法一樣，只係多咗 base64

Secret 嘅建立同注入路徑同 ConfigMap 幾乎一樣，差在「值用 base64 擺喺 data」。起 Secret 有兩種寫法：--from-literal（值直接畀明文，kubectl 幫你編碼）同 YAML 嘅 stringData（寫明文字串、儲存嗰陣自動轉做 data）。

建立 Secret、睇 base64、解碼驗證
# 11. 建立 Secret（generic 型別；值用單引號包住防 shell 解讀特殊字元）
kubectl create secret generic db-secret --from-literal=DB_USER=admin --from-literal='DB_PASSWORD=s3cr3t!'

# 12. data 的值是 base64——印出來對照一下
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}'

# 13. 直接解碼驗證還原（管線：jsonpath 輸出 → base64 -d）
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d

# 14. describe：不顯示內容，只顯示幾個位元組——安全設計
kubectl describe secret db-secret
secret.yaml — stringData 寫明文、存檔變 data
# secret-plain.yaml — stringData 裡可以直接寫明文
apiVersion: v1
kind: Secret
metadata:
  name: db-plain
type: Opaque
stringData:
  DB_PASSWORD: hunter2
套用並觀察 stringData → data 的轉換
# 15. 套用後讀回：stringData 已經被轉成 data 的 base64
nano secret-plain.yaml
kubectl apply -f secret-plain.yaml
kubectl get secret db-plain -o yaml

# 16. 用 --from-literal 建的那顆，data 長得一樣（值來源不同，儲存形式相同）
kubectl get secret db-secret -o yaml
pod-secret.yaml — Secret 掛成檔案（預設 0644）
# pod-secret.yaml — 用 valueFrom 取單一鍵當 env，再把整顆 secret 掛成檔案
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: DB_USER
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: DB_USER
    volumeMounts:
    - name: db
      mountPath: /etc/db
  volumes:
  - name: db
    secret:
      secretName: db-secret
套用並驗證：環境變數與唯讀檔案
# 17. 套用後進容器驗證兩種注入
nano pod-secret.yaml
kubectl apply -f pod-secret.yaml
kubectl get pod secret-demo

# 18. env 那路：valueFrom.secretKeyRef 取的單一鍵
kubectl exec secret-demo -- sh -c 'echo $DB_USER'

# 19. volume 那路：檔名 = 鍵名；-l 看權限是 -rw-r--r--（0644，與 ConfigMap 相同）
kubectl exec secret-demo -- ls -l /etc/db
kubectl exec secret-demo -- cat /etc/db/DB_PASSWORD
你應該觀察到咩

第 19 步個 ls -l 會見到 -rw-r--r--：Secret 掛載做檔案嘅預設權限係 0644（同 ConfigMap 一樣，同 namespace 嘅人都睇到）。想收緊到得 root 睇到，就喺 volume 寫 defaultMode: 0400——「Secret 預設 0444」係流傳好廣嘅誤解，考試唔好瀨嘢。掛做檔案真正嘅好處係畀隻程式起動嗰陣先讀密碼。

defaultMode: 0400 的陷阱：隻 app 用咩身份跑？

一句記：Secret 檔主係 root，app 係 user1000，0400 = 得主人開到。kubelet 掛載 Secret 檔案嗰陣，擁有者固定係 root:root。所以 defaultMode: 0400（-r--------）淨係主人開到：

  • 容器用 root 跑（busybox 等多數 image 嘅預設）→ 佢就係主人，冇影響，照讀到。
  • 容器用非 root 跑（securityContext.runAsUser，或者 image 本身 USER 1000，例如 nginx-unprivileged、postgres）→ 企喺門口入唔到（Permission denied），多數一起身就炒。

Unix 檔案權限得三道門——owner／group／others，隻 process 每次只行一道門（r=4、w=2、x=1）。用 0440（r--r-----）做例：

0440 = r-- r-- ---邊個結果
owner（r--）· ①號門uid 0（root，檔案擁有者）讀到*
group（r--）· ②號門uid 1000＋補充群組 2000（fsGroup 派 badge）——你隻 app 行呢道門讀到
others（---）· ③號門uid 3000、唔喺群組 2000Permission denied

非 root 嘅正解＝fsGroup＋群組可讀：fsGroup: 2000 好似公司派員工證 badge——kubelet 做兩樣嘢：將檔案嘅 gid 改做 2000，同時將 2000 呢張 badge 扣喺容器 process 身上。隻 app（uid 1000）唔係主人，但有 badge 就行到 ②號 group 門；冇 badge 嘅人一律跌落 ③號 others 門畀人擋。另兩個小位：① Secret volume 本身就係唯讀（更新靠 kubelet 換檔），攞走 write 位元對隻 app 冇額外影響；② defaultMode 套落成個 volume，想淨係改單一鍵就用 items[].mode。

*註：root 仲有 DAC_OVERRIDE 能力，就算位元全關都照讀到——考試唔使深究，記住「root 永遠入到」就得。

🚪 三道門＋badge 圖：點解要 fsGroup？

pod-secret-hardened.yaml — 非 root 讀 Secret 的正解
# pod-secret-hardened.yaml — 非 root ＋ fsGroup ＋ 0440：app 讀得到、別人讀不到（參考寫法，不動本課步驟）
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo-hardened
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000            # kubelet：檔案 gid 改成 2000 ＋ 2000 加進程序補充群組
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: db
      mountPath: /etc/db
  volumes:
  - name: db
    secret:
      secretName: db-secret
      defaultMode: 0440      # -r--r-----：owner(root) 與群組(2000)可讀，others 不可

5. 實作 C：將指令式起嘅設定轉做宣告式 YAML

課堂到而家都用 kubectl create configmap/secret（指令式）求快。收尾搞掂佢哋「轉正」做可以入版控嘅 YAML——先用 dry-run 印出嚟、kubectl apply 套用，同之前學 Job 嗰套工作法一樣：

dry-run 產 YAML → apply 宣告式套用
# 20. 把 app-config 的「現況」導成 YAML 存檔（-o yaml 可接已存在的物件）
kubectl get configmap app-config -o yaml > app-config.yaml

# 21. 宣告式重建：先刪再 apply（kubectl apply 管的是「檔案」這份宣告）
kubectl delete configmap app-config
kubectl apply -f app-config.yaml

# 22. 驗證檔案內容還是 staging（第 8 步改的版本沒跑掉）
kubectl exec vol-demo -- cat /etc/config/APP_ENV

考場小抄

① 起嘢：kubectl create configmap NAME --from-literal=k=v／--from-file=path；Secret 同理（create secret generic）。② 注入三式：成包 envFrom、單鍵 valueFrom.xxxKeyRef、掛檔 volume——寫法差一個字都要背熟。③ 更新行為：env 唔更新、volume 約 1 分鐘內 sync。④ 必背陷阱：Secret 嘅 base64 唔係加密；describe secret 只睇到大細。⑤ 大細上限約 1MiB、namespace 層級。⑥ 喺現有物件倒出 YAML：kubectl get cm/secret NAME -o yaml。

本課戰果

  • 你識得用 --from-literal 起 ConfigMap 同 Secret，講得出兩者儲存差異（明文 vs base64）。
  • 你識得用 envFrom／valueFrom／volume 三種方式注入設定，明白「env 唔熱更新、volume 約 1 分鐘 sync」。
  • 你親眼睇住 stringData 儲存嗰陣轉做 data 嘅 base64，亦驗證過 Secret 掛載嘅預設權限（0644）同收緊方法（defaultMode）。
  • 你識得用 get -o yaml／dry-run 將設定物件轉做宣告式 YAML 入版控。
