Lesson 0008：儲存三層 PV／PVC／StorageClass

目標：搞掂 PV、PVC 同 StorageClass 三層分工，親手試動態供應同靜態供應，睇下刪 Pod 資料仲喺度、Delete 同 Retain 差幾遠！

💡 點解呢課咁重要？
之前七課啲 Pod 全部「冇記性」——隻容器一重啟，寫入去嘅嘢就冇晒。貼地講：資料庫啲 data 點可以跟住隻 Pod 一齊死？呢課就係 Phase 2 資料面嘅收尾：Storage 佔考綱 10%，仲係 Troubleshooting 成日見到嘅底層元兇！

之前七課，你啲 Pod 全部係「冇狀態」——容器一重啟，寫喺容器檔案系統嘅嘢就冇晒。今課將 Phase 2 收尾喺資料面：Kubernetes 嘅儲存抽象。PV（PersistentVolume，實際隻碟）、PVC（PersistentVolumeClaim，你想要隻碟）、StorageClass（整碟嘅工廠）三層分工，等「容器會死」同「資料要生」可以並存。Storage 佔考綱 10%，而 PV/PVC 係 Troubleshooting 常見場景嘅底層原因。本課個 cluster 沿用之前：雙節點、metrics-server 在位。

1. 三層分工：邊個擁有、邊個用、邊個整

層級係咩比喻
PV
PersistentVolume		 實際嘅儲存空間（NFS、雲碟、hostPath…），cluster 資源、唔屬於任何 namespace 貨倉「已經買好」嘅一格架
PVC
PersistentVolumeClaim		 「我要 1Gi、讀寫一次」嘅申請表；有 namespace。K8s 幫你搵粒啱嘅 PV 綁埋一齊 你填嘅「我要一格」申請表
StorageClass
（儲存類別）		 「動態供應」嘅工廠：PVC 一到，就照參數幫你即刻整粒 PV 照單即整架嘅廠商

Pod 永遠只識 PVC（persistentVolumeClaim.claimName），唔會直接掂 PV——條界好清楚：開發者寫 PVC，管理員管 PV，StorageClass 自動補貨。

💾 兩條供應線：外賣現整 vs 食現貨

分工先記：dev 寫 PVC＋Pod，admin 整 PV＋SC。Pod 永遠只識 PVC。

2. 存取模式同回收策略

存取模式縮寫意思
ReadWriteOnceRWO單一節點讀寫（最常見；同節點多 Pod 可共用）
ReadOnlyManyROX多節點唯讀
ReadWriteManyRWX多節點讀寫（NFS 等共享儲存先支援）

PV 畀人放返出嚟之後點搞，由 persistentVolumeReclaimPolicy 話事：Retain（留返隻碟，PV 變 Released、等人清）同 Delete（連底層儲存一齊刪，雲碟常見設定）。口訣：Delete 係「PVC 一刪，PV 連本帶利還返畀雲」；Retain 係「隻碟留低，管理員自己執手尾」。

🔑 三種借法：鎖匙村、圖書館、白板

accessModes 決定幾多人用得、寫唔寫得。本課 local-path 淨係識 RWO。

把「儲存檔案」的一生畫一遍
PVC（我要 1Gi）───> StorageClass 工廠（dynamic provisioning）
                        │ 現做一個底層磁碟
                        ▼
                   PV 綁給 PVC（Bound）
                        │ Pod 透過 PVC 掛載使用
                        ▼
                PVC 刪除 ──> 依 ReclaimPolicy：
                            Delete → PV 一起消失
                            Retain → PV 變成 Released 等人接手

🎬 一生狀態帶：Pending → Bound → 資料留低 → 分叉結局

跟住 badges 行一次，全課實作就係呢條路。

3. 實作 A：動態供應——PVC 一張單，PV 自動嚟

kind 預設內置一個 StorageClass（local-path provisioner 畀，個名叫 standard），所以「動態供應」一開箱就用得。

看看 kind 的 StorageClass
# 1. 內建 SC：PROVISIONER 是 rancher.io/local-path，RECLAIMPOLICY 是 Delete
kubectl get storageclass
#    standard（default）是 WaitForFirstConsumer——第一次有 Pod 要用才真正綁 PV
pvc.yaml — 一張「我要 1Gi」的申請單
# pvc.yaml — 不指定 storageClassName，就會用 default 的 standard 動態供應
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
套用：PVC 先「掛單」
# 2. 套用申請單
nano pvc.yaml
kubectl apply -f pvc.yaml

# 3. 看 PVC：Pending——standard 是 WaitForFirstConsumer，還沒人用就不供給
kubectl get pvc

# 4. PV 也還沒有——動態供應要等「第一個使用者」出現才開工
kubectl get pv
disk-demo.yaml — Pod 把 PVC 掛進 /data
# disk-demo.yaml — 啟動時寫一筆資料進 PVC，然後睡著
apiVersion: v1
kind: Pod
metadata:
  name: disk-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo hello-from-pvc > /data/message.txt; sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc
布 Pod 觸發供給：PVC 綁定、PV 現身
# 5. 套用 Pod，等它 Running——Pod 被排到節點的那一瞬間，SC 才開始「現做」PV
nano disk-demo.yaml
kubectl apply -f disk-demo.yaml
kubectl get pod disk-demo

# 6. 回頭看：PVC 變 Bound，PV 也自動出現（名字像 pvc-xxxxxxxxxx）
kubectl get pvc
kubectl get pv

# 7. describe PVC 看綁到哪顆 PV；再讀回寫入的檔案
kubectl describe pvc my-pvc
kubectl exec disk-demo -- cat /data/message.txt
你應該觀察到咩

第 3–6 步就係「三層」一齊現身嘅時刻：PVC 先 Pending（WaitForFirstConsumer），直到第一個用家（disk-demo Pod）排上節點，StorageClass 先幫你即整粒 PV、PVC 轉 Bound。第 7 步寫入去個檔已經瞓喺 PV 底層隻碟度——下一節證明「隻容器死咗佢仲生勾勾」。

4. 實作 B：容器會死，資料要生

刪 Pod、重建、資料還在
# 8. 把 Pod 整個刪掉（容器檔案系統跟著消失——但 /data 不在裡面）
kubectl delete pod disk-demo

# 9. 用同一份 YAML 重建一顆全新的 Pod
kubectl apply -f disk-demo.yaml
kubectl get pod disk-demo

# 10. 新容器讀得到舊資料——寫進 PV 的東西跟著 PVC 走，不跟著容器
kubectl exec disk-demo -- cat /data/message.txt

# 11. 到節點上親眼看「檔案實際放在哪」：先讀 local-path 的設定，再對照實際目錄
kubectl -n kube-system get cm local-path-config -o yaml | grep -A4 nodePathMap
docker exec kind-worker ls /var/local-path-provisioner
#     找不到就試 /opt/local-path-provisioner（版本不同路徑不同）；
#     若那顆 PV 是綁在 control-plane 那一端，把 kind-worker 換成 kind-control-plane
#     PV 的實際名稱就是上面 kubectl get pv 看到的 pvc-xxxx
刪 PVC：睇 Delete 回收策略出手
# 12. 先刪 Pod（PVC 還在使用中時不能刪）
kubectl delete pod disk-demo

# 13. 刪 PVC——standard 的回收策略是 Delete
kubectl delete pvc my-pvc

# 14. PV 跟著消失：底層磁碟也被回收（get pv 應該空了）
kubectl get pv
你應該觀察到咩

第 10 步係全課最關鍵嗰幕：Pod 死得，資料唔死——因為啲 data 瞓喺 PV，Pod 只係暫借嚟用。第 13–14 步就係 StorageClass 回收策略嘅現場：Delete 即係「PVC 刪嗰陣，連同自動整出嚟嘅 PV 同底層目錄一齊清走」。

5. 實作 C：靜態供應——管理員預先整好 PV

動態供應係「工廠即整」；靜態供應係「貨倉現貨」——系統管理員先手刻粒 PV（呢粒我哋用 hostPath，直接食節點個目錄，最啱本機學嘢；落場會係 NFS／雲碟）。關鍵：PVC 要寫 storageClassName: ""，閂咗動態供應，佢先會去配「現貨」。

pv-static.yaml — 管理者預先造好的 PV
# pv-static.yaml — hostPath 吃 kind-worker 節點的 /mnt/data；nodeAffinity 釘住節點
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-static
spec:
  capacity:
    storage: 1Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  hostPath:
    path: /mnt/data
    type: DirectoryOrCreate
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: ["kind-worker"]
套用 PV、再用 PVC 認領
# 15. 套用後 PV 停在 Available，等有人來認領
nano pv-static.yaml
kubectl apply -f pv-static.yaml
kubectl get pv

# 16. 一張「只要現貨」的申請單：storageClassName 設空字串、關閉動態供應
kubectl create -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-static
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: ""
  resources:
    requests:
      storage: 1Gi
EOF

# 17. pvc-static 綁上 pv-static（兩邊狀態都變 Bound）
kubectl get pvc
kubectl get pv
用這顆「現貨」PVC 寫資料
# 18. 換個 Pod 掛 pvc-static（claimName 改成 pvc-static），寫一筆再讀回
kubectl delete pod disk-demo 2>/dev/null; true
kubectl run static-demo --image=busybox:1.36 --restart=Never --dry-run=client -o yaml > static-demo.yaml
nano static-demo.yaml
#    把 spec 加上 volumeMounts/volumes，claimName 用 pvc-static（照 disk-demo.yaml 抄）
kubectl apply -f static-demo.yaml
kubectl exec static-demo -- sh -c 'echo static-works > /data/note.txt; cat /data/note.txt'

# 19. 收尾：刪 Pod → 刪 PVC（Retain：PV 不會被刪，只變 Released）
kubectl delete pod static-demo
kubectl delete pvc pvc-static
kubectl get pv
#    pv-static 還在，但 STATUS 變成 Released——等著管理者清理（這個示範直接刪）

# 20. 手動刪掉 Released 的 PV，收乾淨
kubectl delete pv pv-static
rm pvc.yaml disk-demo.yaml pv-static.yaml static-demo.yaml

# 21. 課末確認：雙節點、乾淨、無殘留 PV/PVC
kubectl get nodes
kubectl get pv,pvc
你應該觀察到咩

第 19 步對返第 13 步，回收策略差幾遠一睇就明：Delete 令 PV 自動消失；Retain 令 PV 留喺原地、標做 Released——呢個就係「PVC 刪咗但 PV 仲喺度」嘅標準場景，考場問「點解隻 PV 仲喺度？」答案就係 reclaim policy 係 Retain。

考場小抄

① 三層口訣：PVC 係申請、PV 係現貨、StorageClass 係工廠；Pod 只識 PVC。② 查詢三寶：kubectl get pvc／get pv／get storageclass。③ 存取模式縮寫：RWO（單節點讀寫）、ROX（多節點唯讀）、RWX（多節點讀寫）。④ 回收策略：Delete 連根拔、Retain 留 Released。⑤ 想配靜態 PV：PVC 寫 storageClassName: ""；hostPath PV 一定要用 nodeAffinity 釘實節點。⑥ 動態綁定常見 WaitForFirstConsumer：PVC 先 Pending、有 Pod 用先 Bound——唔係故障嚟。

本課戰果

  • 你見證咗動態供應：淨係寫 PVC，StorageClass 自動即整 PV 兼綁定。
  • 你證明咗「Pod 會死、資料會生」：刪咗 Pod 重建返個檔仲喺度。
  • 你親眼睇住 Delete 回收（PV 同 PVC 一齊消失）同 Retain 回收（PV 變 Released）嘅分別。
  • 你手刻咗粒靜態 hostPath PV，仲用 storageClassName: "" 嘅 PVC 精準認領佢。

Pod 個 volume 來源應該寫咩？
