Lesson 0012：NetworkPolicy 同 CNI：叢集內防火牆

目標：搞掂叢集入面「邊個連到邊個」——親手裝 Calico、由預設全通行到 default deny 再精準放行，仲要踩一次 egress 唔記得 DNS 嘅經典氹。考場見到連線 timeout，一眼知係咪 NetworkPolicy 搞鬼！

💡 點解呢課咁重要？
0011 搞掂「外面點入嚟唔同服務」；今課守住「入面邊個掂到邊個」——NetworkPolicy 就係 K8S 原生防火牆。最伏係：寫咗 policy 但 CNI 唔支援＝寫咗等於冇寫！搞掂「NetworkPolicy 係法例、CNI 係差人」呢條因果鏈，Phase 3 先算真正收工。

1. CNI：派 IP、接網絡嗰個人

0011 搞掂「外面流量點入唔同服務」；今課守「叢集入面邊個連到邊個」——NetworkPolicy。佢係 K8S 原生嘅防火牆 API：宣告「邊啲來源連到邊啲 Pod 嘅邊啲 port」。但 NetworkPolicy 有個關鍵前提：要 CNI 撐先真係識擋（kindnet 唔撐）。所以今課開場會再重建叢集，裝上撐佢嘅 Calico，順手將 CNI 係咩一次講透。呢課之後部機 keep 住「Calico 雙節點」，0013–0014 直接沿用。

每粒 Pod 都要有自己 IP、要駁入叢集網絡。做呢樣嘢嘅係一支每粒節點跑住嘅 CNI plugin：kubelet 起好 Pod 之後，嗌 CNI plugin 將個容器駁上網。CNI（Container Network Interface）就係呢個「嗌人標準」個名；唔同實作有唔同網絡模型：

  • kindnet：kind 內置嘅輕量 CNI（ptp 路由式）——夠簡單，但唔識做 NetworkPolicy。
  • Calico：老牌 CNI，用 BGP 或 VXLAN 起 Pod 網絡，仲用 iptables/eBPF 執行 NetworkPolicy。
  • 其他：Cilium、Flannel（Flannel 都唔識做 NetworkPolicy）…。

記住呢條因果鏈：NetworkPolicy 係法例、CNI 係差人。寫咗 NetworkPolicy 但 CNI 唔撐＝條例瞓喺 etcd 度、冇人執行。

🛡️ NetworkPolicy 拓樸圖：邊個入到 db 房

點讀呢幅圖：左邊兩個客一齊敲右邊道門——frontend 有兩把鎖匙（namespace＋label）所以開到，backend 少一把所以食閉門羹。下面 inset 話你知：出門（egress）嗰陣唔記得帶 DNS 嗰條鎖匙，直連 IP 通、用人名就唔通。

2. NetworkPolicy 語意，唔好諗錯

  • 預設全通：叢集冇 NetworkPolicy 嗰陣，任何 Pod 連到任何 Pod。規則淨會「收緊」，唔會「放寬」。
  • 空規則 ＝ 全選：podSelector: {} 代表嗰個 namespace 嘅所有 Pod（唔係冇規則）。
  • policyTypes：宣告呢份規則管 Ingress（入嚟嘅）定 Egress（出去嘅）。一旦某個方向畀任何一份 policy 揀中，嗰個方向就變預設拒絕——呢個就係「default deny」嘅由來。
  • 揀來源：podSelector（同 namespace 揀 Pod）、namespaceSelector（揀 namespace）、ipBlock（揀 IP 段）；ports 鎖死協議同 port。
default deny 兩條模板（必背）
# 淨擋「入嚟嘅」：namespace 內全部 Pod 都唔收任何入站流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
spec:
  podSelector: {}
  policyTypes: ["Ingress"]

# 淨擋「出去嘅」：namespace 內全部 Pod 都唔畀對外連線
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-egress
spec:
  podSelector: {}
  policyTypes: ["Egress"]

kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'

5. 實作 B：db 嘅 default deny，再放行 frontend

np-deny-db.yaml — db namespace 全部唔收站流量
# np-deny-db.yaml — podSelector 空物件 = 揀中 db namespace 內所有 Pod
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: db
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
套用之後：兩邊都入唔到去
# 13. 套用 default deny
nano np-deny-db.yaml
kubectl apply -f np-deny-db.yaml

# 14. frontend 同 backend 都連唔到 db（畀人擋 = timeout）
kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
kubectl exec backend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
np-allow-frontend.yaml — 放行「default namespace 掛 app=frontend 嘅 Pod」
# np-allow-frontend.yaml — 重點：podSelector 淨係揀到「同 namespace」嘅來源，
# frontend 住喺 default，所以一定要 namespaceSelector（揀 namespace）＋ podSelector（揀 Pod）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
  namespace: db
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: default
      podSelector:
        matchLabels:
          app: frontend
套用之後：frontend 返嚟，backend 繼續畀人擋
# 15. 套用放行規則
nano np-allow-frontend.yaml
kubectl apply -f np-allow-frontend.yaml

# 16. frontend 通返（佢喺 default namespace 又掛 app=frontend——兩個條件都中）
kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local | head -n 1

# 17. backend 仲係畀人擋（佢冇 app=frontend）
kubectl exec backend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
你應該觀察到咩

第 13–17 步就係「default deny ＋ 精準放行」嘅完整節奏：先落 podSelector: {} 嘅 deny 將所有門閂晒，再用「更準嘅 allow」開門——NetworkPolicy 係白名單思維：預設全通 → 一出現 policy 就反做預設拒絕 → 每條 allow 都係一道開好嘅門。backend 畀人擋但 frontend 通，證明條規則認嘅係 namespace＋label，唔係 Pod 個名——跨 namespace 放行嗰陣 namespaceSelector 嗰半最易漏。

🥁 白名單節奏三步曲（背到識背）：
步驟落咗咩 policyfrontend → dbbackend → db
Step 0：冇 policy
（第 12 步）		零——預設全通✅ 200 通✅ 200 通
Step 1：deny-all
（第 13–14 步）		deny-all（podSelector: {}）❌ BLOCKED（timeout）❌ BLOCKED（timeout）
Step 2：allow-frontend
（第 15–17 步）		deny-all ＋ allow-frontend✅ 200 返嚟❌ BLOCKED 照擋

🧩 YAML 邏輯 callout（考場必用）：同一個 from 入面 namespaceSelector＋podSelector 黐埋一齊＝AND（兩把鎖匙要齊：係 default namespace 而且係 app=frontend）。唔同 - 項目分開寫＝OR（任何一條中就開門）。所以 backend 住啱 default 但 label 唔啱＝AND 失敗＝照擋！記：同一格 AND、唔同格 OR。

6. 實作 C：Egress 唔好唔記得 DNS（經典氹）

Ingress 管「邊個入到 db」，Egress 管「db／某粒 Pod 去到邊」。經典陷阱：你幫 Pod 設咗 egress 白名單，但唔記得放行 DNS（53/UDP 畀 kube-dns）——粒 Pod 連「解服務個名」都做唔到。實作：閂死 frontend 淨係「打到 db 嘅 80」，特登漏咗 DNS，睇佢點死，再加返。

frontend-egress.yaml — 淨准對外打 db:80（唔記得 DNS）
# frontend-egress.yaml — 淨係准 egress 去「db namespace 入面 app=db 嘅 Pod:80」
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-egress
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes: ["Egress"]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: db
      podSelector:
        matchLabels:
          app: db
    ports:
    - protocol: TCP
      port: 80
套用：frontend 連 DNS 都出唔到去
# 18. 套用之後，frontend 連 db 個「名」都解唔到（DNS 封包畀 egress 規則掉咗）
nano frontend-egress.yaml
kubectl apply -f frontend-egress.yaml
kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- DNS BLOCKED --'

# 19. 對照組：轉用 db Pod 嘅 IP 直連（唔經 DNS）——條規則有放行 db:80，呢條應該通

echo $DBIP

考場小抄

① NetworkPolicy 唔擋就放行；一出現 policy「畀人揀中嗰個方向」就預設拒絕。② podSelector: {}＝嗰個 namespace 全部 Pod；policy 有 namespace 欄，跨 namespace 用 namespaceSelector。③ 畀人擋嘅症狀係timeout（唔係 connection refused）——除非個 CNI 係 iptables REJECT。④ egress 唔記得 DNS 係經典考點：白名單要留 kube-dns 嘅 53/UDP（加埋 53/TCP 保險）。⑤ 規則冇生效先查三樣：CNI 撐唔撐（kindnet 唔撐）、label 打啱未、policy 嘅 namespace 啱唔啱。⑥ default deny 兩條模板（上面個框）背熟佢，考場直接改。

本課戰果

  • 你重建咗 disableDefaultCNI 嘅叢集，親眼見「冇 CNI 節點唔 Ready」，仲用官方 manifest 裝好 Calico（v3.32.2）。
  • 你起咗 frontend／backend／db 三層拓樸，見證「預設全通」同「一有規則即收緊」。
  • 你用 default deny ＋ allow-frontend 做到「淨係放行特定來源」嘅 NetworkPolicy。
  • 你踩過兼整返 egress 唔記得 DNS 嘅經典氹（kube-dns 53/UDP）。
