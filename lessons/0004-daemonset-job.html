CKA 第四課 · 特殊控制器

Lesson 0004：DaemonSet 與 Job（Deployment 搞唔掂嘅場景）

目標：Deployment 只識「 keep 住 N 粒、永遠唔收工」。今課搞掂佢做唔到嘅兩種嘢：每台 Node 都要一粒（DaemonSet：log 收集、monitoring agent、CNI）同跑完就收工（Job / CronJob：batch 任務），最後仲會起返個雙節點叢集留返下堂用。

💡 點解 Deployment 唔夠用？
諗下貼地例子：log agent 邊台 Node 冇佢就等於盲咗，Deployment 點知有新 Node 加入要補返粒？Batch 任務跑完仲 keep 住唔熄，唔係嘥錢咩？CKA 就係要你識揀：補數量、補節點、補失敗、補時間，揀啱控制器先唔會瀨嘢！

🗺️ 四大控制器：幾時補 Pod？

記住呢句口訣，考試一見題目問「每台都要」定「跑完收工」，即刻知揀邊個。

1. 四控制器：邊個喺咩時候補 Pod？

將 0001–0003 學過嘅 Deployment 放返入大地圖：控制器之間最大分別，就係「咩情況會觸發佢補 Pod」。想查術語可睇 詞彙表，考綱對照睇 考綱地圖。

控制器何時補 Pod典型場景
Deployment副本數不足時（補數量）Web／API 等長期服務
DaemonSet有節點需要時（每節點一顆）日誌收集、監控 agent、CNI
Job任務失敗時（補失敗、不補成功）批次任務、一次性初始化
CronJob時間到時（定時生一個 Job）定時備份、定期清理

一句記晒，之後直接背：Deployment 補數量、DaemonSet 補節點、Job 補失敗、CronJob 補時間。

🔍 DaemonSet vs Deployment：邊個決定 Pod 落邊台？＋ CronJob 三層鏈

對比記：DaemonSet 係「邊台新嚟就去邊台報到」；Deployment 係「邊台有位就去邊台」；CronJob 係三級外判：鬧鐘叫任務單，任務單叫工人，工人做完企喺度等收工車。

2. DaemonSet：每台 Node 一粒

DaemonSet（簡寫 ds）嘅期望狀態唔係「N 粒」，而係「每台 Node 啱啱好一粒」：叢集加 Node，佢自動喺嗰台生返粒；Node 走，嗰粒跟住收皮。你早就用緊佢都唔知——kube-system 入面嘅 kindnet（CNI）同 kube-proxy 都係 DaemonSet，因為「網路服務」每台 Node 都一定要有。控制器鏈係 DaemonSet → Pod，冇中間嘅 ReplicaSet。原理同 0003 同一條路：DaemonSet controller watch 住 apiserver 嘅 Node 事件，有 Node 加入或者離開就重新 reconcile。

CKA 重點：DaemonSet 沒有 create 指令

kubectl create daemonset 唔存在——kubectl 只幫少數物件整 create 指令（deployment、job、namespace…）。想起 DaemonSet 唯有寫 YAML，呢啲就係 CKA 最鍾意考嘅位。記返 0003 規則：selector.matchLabels 一定要同 template 嘅 labels 一樣，唔係 apiserver 即刻彈你（selector does not match template labels）。

# ds.yaml — 每台節點都跑一個監控 agent
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-monitor
spec:
  selector:
    matchLabels:
      app: node-monitor
  template:
    metadata:
      labels:
        app: node-monitor
    spec:
      containers:
      - name: agent
        image: busybox:1.36
        command: ["sh", "-c", "echo agent on $(hostname); sleep 3600"]

4. Job：跑完就收工嘅控制器

Deployment 嘅 Pod「永遠唔應該完」；Job 嘅 Pod 則出世就係為咗完。Job 嘅期望狀態係「成功跑完 completions 次」，唔係「keep 住 N 粒」：

  • completions：總共要成功幾次（預設 1）。
  • parallelism：同時最多跑幾粒（預設 1）。
  • backoffLimit：失敗重試上限（預設 6）。
  • restartPolicy：只可以係 Never 或者 OnFailure——唔可以係 Always（同 Deployment 最大嘅語法分別，因為「跑完仲重開」對 Job 嚟講冇意義）。

Job 自癒口訣係「補失敗、唔補成功」：Pod 炒咗就換粒新嘅 retry；任務一成功，嗰粒 Pod keep 住 Completed、唔再重啟——呢個就係同 Deployment 最大分別。用 kubectl create job 就起到最簡單嘅 Job——但佢得 --image 同 --from 兩個專屬旗標；completions／parallelism 係 spec 欄位、冇對應旗標，一定要寫 YAML set（實作 B 會練呢套，亦係 CKA 陷阱）。

Deployment（replicas）Job（completions / parallelism）DaemonSet（DESIRED）
數字係咩意思replicas: 3＝永遠 keep 住 3 粒 Runningcompletions: 3, parallelism: 2＝總共成功 3 次、最多同時 2 粒（分兩浪跑）DESIRED＝Node 數目（2 台 Node 就 2 粒，唔係你 set）
做完／死咗點死一粒補一粒，永遠 Running成功唔補、失敗先補；做完留 Completed斬走嗰台嘅 Pod 即喺返嗰台補返粒
restartPolicy只可以用 Always（長期服務唔收工）只可以用 Never／OnFailure（做完唔重開，唔可以用 Always）只可以用 Always（每台長期駐守）

一句記：Deployment 數字係「人頭數」、Job 數字係「要交幾多單＋一次做幾多單」、DS 數字係「有幾多台機」；Job 專用 Never／OnFailure，一見 Always 即錯。

PowerShell 陷阱：`>` 存成 UTF-16

喺 Windows PowerShell 用 kubectl ... > job.yaml save 檔，會寫成 UTF-16，kubectl 睇唔明（會彈 error converting YAML to JSON）。所以上面第 21 步轉用 | Out-File job.yaml -Encoding utf8。考場係 Linux/WSL2，直接用 kubectl ... > job.yaml 就得——養成習慣：喺 PowerShell 一律用 Out-File。

多粒 Pod 嘅 Job 點睇晒所有 log？

第 29 步嘅 multi 有三粒 Pod。想撈成個 Job 嘅 log，kubectl logs job/multi 預設只揀一粒，仲會提示 Found 3 pods, using pod/multi-...。想睇晒所有 Pod 輸出、仲要每行標明邊粒嚟，加 --all-pods=true：kubectl logs job/multi --all-pods=true。

失敗重試：Job 補失敗、不補成功
# 30. 一支注定失敗的任務（exit 1）
kubectl create job fail --image=busybox:1.36 -- sh -c 'exit 1'

# 31. 列 Pod：Job 一直換新 Pod 重試，每顆都以失敗收場
kubectl get pods

# 32. 看重試紀錄（Events 有 Backoff）；看到換了 2–3 顆就夠了
kubectl describe job fail

# 33. 不繼續等了——backoffLimit 預設 6 會重試很久。直接刪掉

點解步驟 33 唔等佢自然完？

Job 嘅 retry 間隔係指數退避：10s → 20s → 40s → 80s → 160s → 320s（單次上限 6 分鐘）。backoffLimit 預設 6——要等齊 6 次失敗先會標 Failed，成餐要 10 分鐘以上。所以步驟 33 直接鏟走，唔陪佢等。考場想快啲見到 Job 自然炒：喺 YAML 嘅 spec: 加 backoffLimit: 0，第一粒炒即結案。

執行緊嘅 Job Pod 畀人斬走會點？

上面見到「做完嘅 Pod 斬咗唔補」。調轉，如果斬嘅係仲跑緊嘅 Job Pod，Job 會補返粒繼續跑（任務未完成）。想親眼驗證：先 kubectl delete job multi，將 multi.yaml 嘅 sleep 5 改成 sleep 60，再 kubectl apply -f multi.yaml——趁佢跑緊開多個 terminal 斬一粒，再睇 kubectl get pods -w，新 Pod 會接手。睇完記得 kubectl delete job multi。

6. CronJob：時間到就生粒 Job

Job 嘅定時版就係 CronJob（cronjob/cj）：佢唔直接生 Pod，而係照 cron 五欄排程（分 時 日 月 週）定時起粒 Job——所以係更長嘅控制器鏈：CronJob → Job → Pod。啱晒定時備份、定期清理呢啲工夫。

實作 C：每分鐘跑一次的 CronJob（迷你版）
# 35. 建立每分鐘執行一次的 CronJob（schedule 用雙引號包住）
kubectl create cronjob minute --image=busybox:1.36 --schedule="*/1 * * * *" -- date

# 36. 看 SCHEDULE（LAST SCHEDULE 還是 <none>）
kubectl get cronjob

# 37. 等 1–2 分鐘到整分，會出現 minute-xxxxx 的 Job——時間到，CronJob 生了一個 Job
kubectl get jobs

# 38. 收尾：刪 CronJob（已產生的 Job/Pod 不會自動消失，一起清掉）
kubectl delete cronjob minute
kubectl delete jobs --all
你應該觀察到咩

第 37 步嘅 minute-xxxxx 就係「時間到，CronJob 幫你 create 嗰粒 Job」——佢又行一次 Job 流程：生 Pod、跑 date、完成後 keep 住 Completed。三層各有各做：CronJob 管時間、Job 管完成、Pod 管執行。

每分鐘一粒，Completed 嘅 Job 唔會愈堆愈多咩？

唔會。CronJob 會自動回收超額嘅已完成 Job：successfulJobsHistoryLimit 留返最近幾粒成功嘅（預設 3）、failedJobsHistoryLimit 留返最近幾粒失敗嘅（預設 1）——一生新嘅，最舊嗰粒連 Pod 一齊畀控制器鏟走，所以 kubectl get jobs 唔會愈 list 愈長。

想自訂要放啱層：呢兩個歷史欄位寫喺 CronJob 嘅 spec:（jobTemplate 出面）；想 Job 跑完自動倒數刪除，用 ttlSecondsAfterFinished，寫喺 jobTemplate.spec:（同 backoffLimit 同層）。兩個都唔係 pod template 嘅欄位——口訣：邊個嘅欄位就放邊個嘅 spec。想完全唔留歷史，兩個 historyLimit set 做 0。

YAML 巢狀地圖：邊個欄位住邊層（縮排即層級）
# CronJob 專屬層：spec（CronJob 自己）
apiVersion: batch/v1
kind: CronJob
spec:                              # ← 第 1 層：CronJob.spec
  schedule: "*/1 * * * *"
  successfulJobsHistoryLimit: 3    # ← 住呢層！管留幾多粒成功 Job
  failedJobsHistoryLimit: 1        # ← 住呢層！管留幾多粒失敗 Job
  jobTemplate:                     # ← 第 2 層：入面先係粒 Job
    spec:                          # ← Job.spec
      completions: 1               # ← 住呢層！總共成功幾次
      parallelism: 1               # ← 住呢層！同時跑幾粒
      backoffLimit: 6              # ← 住呢層！失敗重試幾多次
      ttlSecondsAfterFinished: 100 # ← 住呢層！做完幾秒後自動刪除
      template:                    # ← 第 3 層：先係 Pod template
        spec:                      # ← Pod.spec（restartPolicy 住呢層）
          restartPolicy: OnFailure
          containers: [...]
CronJob 跑完啲 log 會留低咩？

Log 跟住 Pod，唔跟 CronJob/Job 物件——kubectl logs 讀嘅係 Node 上 container runtime 嘅檔案。所以 log 壽命 = Job/Pod 壽命：喺 historyLimit 個窗口入面（成功 3、失敗 1），kubectl logs job/minute-xxxxx 仲查到；Job 一畀回收，Pod 連 log 一齊冇晒。

想留耐啲：① 治標——調大 historyLimit 或者 ttlSecondsAfterFinished 延長物件壽命；② 正路——外部集中 log（Loki、EFK、雲方案），k8s 本身唔 save 舊 log。考場觀念：鏟 Job = 連 Pod 一齊鏟 = log 冇埋，要撈趁物件仲喺度快手。

考場小抄

五個必背反射動作：① DaemonSet 冇 create daemonset，唯有寫 YAML——趕時間可先 kubectl create deployment 用 --dry-run=client -o yaml 吐底稿，再將 kind 改成 DaemonSet、拎走 replicas。② create job 得 --image／--from——冇 --completions／--parallelism；batch 欄位用 --dry-run=client -o yaml 吐 YAML 加返入去再 apply。③ Job log：kubectl logs job/NAME——多粒 Pod 加 --all-pods=true 一次睇晒。④ Job 卡住點查：kubectl describe job NAME 配 kubectl get pods -l job-name=NAME；想必炒嘅 Job 快啲結案，YAML set backoffLimit: 0。⑤ 四控制器口訣：Deployment 補數量、DaemonSet 補節點、Job 補失敗、CronJob 補時間。

本課戰果

  • 你用 YAML 起到 DaemonSet，親眼見到「每節點一粒」同「斬走補返同 Node」嘅自癒。
  • 你用 kubectl create job 起一次性任務，識用 dry-run 吐 YAML 再 set completions／parallelism 控制 batch，仲識 kubectl logs job/NAME 直攞 log。
  • 你見到 Job「補失敗、唔補成功」，仲有失敗 retry（backoffLimit）係點行。
  • 你識咗 dry-run 吐 YAML 工作法，仲知 PowerShell > 嘅 UTF-16 陷阱（轉用 Out-File）。
  • 你簡單識咗 CronJob（時間到就生 Job），仲將叢集升咗做雙節點留返後面用。
