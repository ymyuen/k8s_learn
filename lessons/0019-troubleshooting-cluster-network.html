CKA 第十九課 · 由粒 Pod 睇到成個場

Lesson 0019：故障排除 II — 節點、控制平面同網路服務

目標：0018 識修「單粒 Pod」；今課將視野推高兩層：① 節點（NotReady、Conditions 判讀）同 控制平面（static pod 巡檢），② 將 0010 嘅分層除錯擴大成端到端故障鏈——由 curl 唔通一路查到 NetworkPolicy。

💡 點解呢課咁重要？
Pod 本身冇事，但成個 Service 照樣瀨嘢——呢啲先係 CKA 最鍾意考嘅大佬級題目！識得分層查 Node → 控制平面 → DNS → NetworkPolicy，先至叫真正搞掂 Troubleshooting 嗰 30%，貼地出師！
開場先裝返 metrics-server

0007 裝嗰個 metrics-server 喺 0011／0012 兩次重建叢集嗰陣畀人洗走咗。呢課開場裝返佢（呢課同 0020 嘅 kubectl top 都靠佢），指令同 0007 一模一樣。

1. 節點層：describe node 嘅 Conditions

Node 健唔健康，寫晒喺 describe node 嘅 Conditions 嗰版，逐條睇下：

  • Ready＝kubelet 正常回報。False 或者 Unknown 即係「粒 Node 瓜咗／斷咗線」。
  • MemoryPressure／DiskPressure／PIDPressure＝粒 Node 資源告急（多數跟住 evict Pod）。

判讀口訣：Ready 睇 kubelet；Pressure 睇資源。

2. 控制平面：static pod

kubelet 會自動起返 /etc/kubernetes/manifests/ 下面嘅 manifest——控制平面四件頭（apiserver、controller-manager、scheduler、etcd）就係咁樣生存（0014／0015 都見過）。所以「控制器唔郁」可以咁樣模擬：將 controller-manager 嘅 manifest 搬走，kubelet 就會收走佢粒 pod——Deployment 從此冇人理。

🏢 大廈比喻：兩條唔同嘅「起樓」迴圈

成棟大廈（叢集）有兩種起樓法，唔好撈亂：左邊係「管理員自己起保安亭」（static pod，唔經 API），右邊係「住客申請、管業處批」（正常 Deployment，經 API＋foreman 蓋印）。

一句記：static pod 係「地盤佬自己起嘢」——kubelet 睇住個 folder 起，API 死咗都起倒；Deployment 係「要 foreman 蓋印」——controller-manager 唔喺度，張申請表就永遠瞓喺度冇人批。

🌐 端到端故障鏈：Station 0 出事，五站檢查法

成日都係由呢句開始：「curl 唔通！」——唔好慌，由 Station 0 逐站排：

記住：「curl 唔通」唔係一個問題，係一串問題，由 Station 0 逐站排就搞掂。timeout 同 refused 係兩種唔同死法——前者多數畀 NP 擋，後者多數無後端。

🎯 podSelector: {} 係咩？一個圈笪晒所有 Pod

podSelector: {} 唔係「冇揀嘢」，係「成個 namespace 笪晒」——好似魚網大到成個魚塘都罩住。

情況有冇 NetworkPolicy效果（HK 話）
冇任何 Policy零張全開——所有 Pod 任連，好似大廈大門長期開住
一張 Policy 出現（就算只寫一條 allow）≥1 張揀中咗粒 Pod預設拒絕——中咗嗰粒即刻變「除咗寫明准許，其餘全擋」，好似一裝閘機，無卡一律唔入得

所以今課 deny-all 用 podSelector: {} 加 policyTypes: ["Ingress"]，就係「成個 default namespace 落閘」——一張就夠閂晒，唔使逐粒 Pod 寫。

3. 實作 A：裝返 metrics-server 兼睇 Node 健康

補裝 metrics-server（0007 重播）
# 1. 先確認佢真係唔見咗（0012 重建之後 kube-system 冇 metrics-server）
kubectl get pods -n kube-system | grep metrics-server
#    冇輸出 = 冇裝

# 2. 裝官方 components.yaml
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 3. kind 嘅 kubelet 冇設 TLS 認證——補參數（淨係本地測試叢集先咁做）
kubectl -n kube-system patch deployment metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deployment/metrics-server

# 4. 等約 30 秒收數據，驗證
kubectl top nodes
kubectl top pods -A
節點條件判讀
# 5. Conditions 嗰版：Ready=True；三種 Pressure 都 False 先叫健康
kubectl describe node kind-worker

# 6. -o wide 睇 Node 狀態同版本
kubectl get nodes -o wide
static pod 巡檢
# 7. kube-system 入面「冇 -replicaset 尾碼」嘅 Pod 就係 static pod：
#    etcd-kind-control-plane / kube-apiserver / kube-controller-manager / kube-scheduler
kubectl get pods -n kube-system -o wide

# 8. 佢哋嘅 manifest 全部瞓喺 control-plane 粒 Node 嘅呢個目錄
docker exec kind-control-plane ls /etc/kubernetes/manifests

4. 實作 B：模擬「控制器瓜咗」——Deployment 生唔到 Pod

進階實驗，郁手前睇定

將 controller-manager 嘅 manifest 搬走會令佢停擺約 1–2 分鐘，期間 Deployment 唔會有任何郁動——呢個正係「控制平面某件頭瓜咗」嘅經典症狀。做完即刻擺返，個叢集會自己復原。如果你唔想郁個正式叢集，可以跳過呢節（概念照讀）。

整故障：controller-manager 消失
# 9. 先將 controller-manager 嘅 manifest 搬出 manifests 目錄
docker exec kind-control-plane mv /etc/kubernetes/manifests/kube-controller-manager.yaml /tmp/

# 10. 確認佢粒 static pod 畀 kubelet 收走（等一陣再 get）
kubectl get pods -n kube-system | grep controller-manager
#    會發現嗰粒 pod 唔見咗
睇症狀：Deployment 冇 ReplicaSet、冇 Pod
# 11. 開一支 Deployment——佢「應該」要畀 controller-manager 處理
kubectl create deployment ghost-cm --image=nginx:1.25 --replicas=2
kubectl get deployment ghost-cm
kubectl get rs,pods
#    Deployment 存在，但 ReplicaSet 建唔到、Pod 出唔到世——
#    因為「負責生 RS 嘅控制器」唔喺度。

# 12. 診斷結論：唔係 YAML 錯、唔係 Pod 壞，係控制器層冇人做嘢
kubectl describe deployment ghost-cm
#    冇 ReplicaSet 相關事件——同平時「即刻生 RS」嘅表現對照就好有感
復原：將 manifest 擺返去
# 13. 擺返 manifest，kubelet 幾秒內重新起返 controller-manager
docker exec kind-control-plane mv /tmp/kube-controller-manager.yaml /etc/kubernetes/manifests/
kubectl get pods -n kube-system | grep controller-manager
kubectl get pods -l app=ghost-cm
#    ReplicaSet 出現、Pod 出世——控制器復原後自動補做（reconcile）
kubectl delete deployment ghost-cm
你應該觀察到咩

第 11–12 步係「控制平面元件故障」嘅指紋：Deployment 存在但冇對應 ReplicaSet，describe 睇唔到任何新事件。現實世界撞到呢種「控制器冇做嘢」嘅症狀，方向係查 kube-controller-manager（logs、static pod 仲喺唔喺度），唔係走去反 Deployment 份 YAML。

5. 實作 C：端到端故障鏈——curl 唔通，由頭查到尾

將 0010（DNS 層）＋0009（endpoints 層）＋0012（NetworkPolicy）串成一次完整除錯：個服務突然連唔到，點樣一步步定位？

準備：一支服務＋一支客戶端＋先確認通
# 14. 開服務同客戶端（同 0010 同一招）
kubectl create deployment web --image=nginx:1.25 --replicas=2
kubectl expose deployment web --port=80
kubectl run client --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/client --timeout=60s

# 15. 基準線：而家係通嘅
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local | head -n 1
落故障：default namespace 全面 deny ingress
# 16. 0012 嘅 default deny 出場——特登將 default 嘅所有入站流量閂咗佢
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
EOF
kubectl get networkpolicy
故障鏈第一站：curl 唔通
# 17. 症狀出現：wget 逾時
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local || echo '-- BLOCKED --'
第二站：DNS 層正唔正常？（0010 嗰招）
# 18. nslookup 解到 VIP——DNS 層冇事，唔係名錯
kubectl exec client -- nslookup web.default.svc.cluster.local
第三站：endpoints 有冇後端？（0009 嗰招）
# 19. endpoints 有 2 個 IP——selector 有打中、Pod 都 Ready（0007 嘅 READY 都 check 下）
kubectl get endpoints web
kubectl get pods -l app=web
第四站：係咪 NetworkPolicy 擋住？（0012 嗰招）
# 20. 頭三站都正常，剩返嘅疑犯：NetworkPolicy
kubectl get networkpolicy
kubectl describe networkpolicy deny-all
#    podSelector {} + Ingress = 將 default 全擋——搵到兇手喇

# 21. 拎走故障源，服務復活
kubectl delete networkpolicy deny-all
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local | head -n 1
收尾
# 22. 清走練習物件（metrics-server 留返畀 0020）
kubectl delete deployment web
kubectl delete svc web
kubectl delete pod client
kubectl get pods -A
kubectl get nodes
你應該觀察到咩

第 17–21 步係 Troubleshooting 30% 嘅濃縮：「curl 唔通」唔係一個問題，係一串問題。照「DNS → endpoints → Pod READY → NetworkPolicy」逐層排，每層都有對應嘅 kubectl 指令——呢個就叫系統化除錯。Service 連唔到三大原因：selector 唔啱、Pod 唔 Ready、NetworkPolicy 擋（呢課一次過收齊）。想溫返字眼可睇 詞彙表。

考場小抄

① Node：describe node 嘅 Conditions——Ready 查 kubelet、MemoryPressure 等查資源；NotReady 先查 kubelet 同 CNI。② 控制平面係 static pod：manifest 喺 /etc/kubernetes/manifests；「Deployment 存在但冇 RS」＝控制器冇做嘢。③ kubectl top 嘅前提係 metrics-server。④ 端到端除錯鏈：curl 唔通 → nslookup（DNS 層）→ get endpoints（後端層）→ get pods READY（0007）→ get networkpolicy（0012）。⑤ 畀 NP 擋＝逾時；冇後端＝connection refused。⑥ Service 冇 endpoints 三原因：selector 唔啱、Pod 唔 Ready、畀 NP 擋。

本課戰果

  • 你將 metrics-server 裝返個叢集，仲用 kubectl top 驗證咗。
  • 你識得判讀 Node Conditions，仲搵到控制平面嘅 static pod 同佢哋嘅 manifest。
  • 你模擬兼復原咗「controller-manager 瓜咗」嘅故障，睇得明 Deployment 生唔到 Pod 嘅指紋。
  • 你沿住 DNS → endpoints → NetworkPolicy 完成一次端到端網路除錯。
