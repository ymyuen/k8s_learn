Lesson 0010：CoreDNS 同服務發現：靠名搵人

目標：搞掂叢集內置 DNS——CoreDNS：背熟 Service 個 FQDN 點寫、短名點解同 namespace 先通，再練熟「DNS 層 vs Endpoints 層」兩層排錯，考場分分鐘救你一命！

💡 點解呢課咁重要？
0009 畀咗每班 Pod 一個 VIP，但你總唔可以叫工程師個個背 VIP 嘛。今課將「搵到對方」變成靠名嘅事：識咗短名、全名、跨 namespace 三招，排錯嗰陣先分到係「個名錯咗」定「後面冇人接」——呢個分層係 CKA Troubleshooting 必考位！

1. Service 嘅 FQDN 樣板，背熟佢

每個 Service 都會畀 CoreDNS 登記一個 A record，個樣板係咁：

FQDN 樣板（背熟佢）
<service>.<namespace>.svc.<cluster-domain>
     │        │        │        └─ 預設 svc.cluster.local
     │        │        └─ 固定係 svc（代表 Service）
     │        └─ Service 身處嘅 namespace
     └─ Service 個名

hello.default.svc.cluster.local   ← 全名（FQDN）
hello                              ← 短名：靠 resolv.conf 嘅 search 補尾

🔍 CoreDNS 查名流程圖：Pod 內放大鏡 + Normal vs Headless 對照

點讀呢幅圖：由上而下跟住粒封包行：Pod 內砌名 → UDP 問總機 → 總機報號；再睇下面對照——同一個 nslookup，Normal 回 1 個 VIP，Headless 回成堆 Pod IP。

Pod 入面嘅 /etc/resolv.conf 係 kubelet 自動整嘅：nameserver 指住 kube-system 嘅 kube-dns Service（CoreDNS 嘅門面），search 就列住一堆自動補尾嘅後綴（多數有 <pod 嘅 namespace>.svc.cluster.local 等）——呢個就係「同 namespace 打短名就通」嘅原因。另外一個細節：ndots:5 代表個名有 5 個點（含）以上先當 FQDN 查，否則先套 search 後綴試下。

cat /etc/resolv.conf 逐行解（Pod 內真 output，加註）
kubectl exec client -- cat /etc/resolv.conf
# nameserver 10.96.0.10   ← 公司總機號碼：kube-dns Service 嘅 VIP，唔係某粒 CoreDNS Pod 嘅 IP
# search default.svc.cluster.local svc.cluster.local cluster.local  ← 分機速撥表：短名 hello 會逐個補尾試
# options ndots:5         ← 夠 5 點先當全號（FQDN）直查；唔夠點＝先當分機撳速撥

2. A record 同 SRV record

  • A record：Service 名 → VIP。Headless Service（0009 嗰個 clusterIP: None）就回佢身後每粒 Pod 嘅 IP——呢個係數據庫類 workload「直連每粒 Pod」嘅機制。
  • SRV record：Service 有「具名 port」嗰陣，_<port-name>._<protocol>.<svc>... 會回「邊個 port 有服務」。

CoreDNS 係一堆跑喺 kube-system 嘅 Deployment，佢 watch 住 Service／Pod 變化嚟更新紀錄；設定收喺 ConfigMap/coredns 嘅 Corefile 入面。今課部機沿用 0009 嗰個雙節點叢集。

3. 實作 A：短名、全名、跨 namespace

準備解到名嘅服務同客
# 1. 確認 0009 嗰粒 client pod 仲喺度兼 Running（NotFound 或 Completed 都重建）
kubectl get pod client
#    如果唔係 Running：kubectl delete pod client --ignore-not-found
#    kubectl run client --image=busybox:1.36 --restart=Never -- sleep 3600
#    kubectl wait --for=condition=Ready pod/client

# 2. 佈粒要畀人解名嘅 nginx 服務
kubectl create deployment hello --image=nginx:1.25 --replicas=1
kubectl expose deployment hello --port=80
kubectl rollout status deployment/hello
解名：全名、短名、resolv.conf
# 3. 睇 Pod 內嘅 DNS 設定：nameserver = kube-dns、search 幫你補尾
kubectl exec client -- cat /etc/resolv.conf

# 4. 全名解名（busybox 嘅 nslookup 唔食 search 自動補，畀全名最穩陣）
kubectl exec client -- nslookup hello.default.svc.cluster.local

# 5. 短名「hello」會通，係因為 search 欄自動補上 default.svc.cluster.local
kubectl exec client -- wget -qO- http://hello | head -n 3
跨 namespace：淨係可以用全名
# 6. 開個 team-a namespace，放支 api 服務
kubectl create ns team-a
kubectl -n team-a create deployment api --image=nginx:1.25 --replicas=1
kubectl -n team-a expose deployment api --port=80

# 7. 由 default namespace 用全名打過去
kubectl exec client -- nslookup api.team-a.svc.cluster.local
kubectl exec client -- wget -qO- http://api.team-a.svc.cluster.local | head -n 3
#    短名 http://api 喺呢度唔通——client 嘅 search 只會補 default 嘅尾
你應該觀察到咩

第 4–5 步嘅對照就係 DNS 縮寫機制嘅全部：全名一定通；短名通唔通睇 search 欄。第 7 步係跨 namespace 嘅唯一寫法：服務名.namespace.svc.cluster.local。想喺第二個 namespace 用短名？將 Pod 起去同一個 namespace，或者自己改 dnsConfig——考試知「預設短名淨係喺本 namespace 有效」就夠。

4. 實作 B：故障分層——名錯 vs 後端吉

跟住嚟演 CKA 最鍾意考嘅「分層判斷」：同樣係「連唔到」，係 DNS 搵唔到個名，定係 DNS 搵到但冇後端接得？兩層症狀完全唔同，唔好撈亂。

第一層：名打錯（NXDOMAIN）
# 8. 個名唔存在：CoreDNS 回 NXDOMAIN——呢個係「DNS 層」嘅問題
kubectl exec client -- nslookup hello.wrong.svc.cluster.local
#    output 會有 "can't find" / NXDOMAIN
第二層：Service 存在但 selector 射唔中任何 Pod
# 9. 整粒 selector 對唔中任何 Pod 嘅 Service（個名叫 ghost）
kubectl create -f - <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: ghost
spec:
  selector:
    app: no-such-app
  ports:
  - port: 80
EOF

# 10. DNS 解到 ghost（Service 存在就有 A record）——DNS 層正常
kubectl exec client -- nslookup ghost.default.svc.cluster.local

# 11. 但 Endpoints 吉嘅——冇後端，連線被拒
kubectl get endpoints ghost
kubectl exec client -- wget -qO- -T 3 http://ghost || echo '-- connection refused --'
你應該觀察到咩

對返第 8 同 10–11 步：名打錯 ＝ DNS 直接話查無此人（NXDOMAIN）；selector 冇射中 ＝ DNS 話有呢個 Service，但 Endpoints 空空如也、TCP 連唔上。除錯次序從此定死：先 nslookup 確認 DNS 層，再 get endpoints 確認後端層——兩層都通先輪到睇 Pod 本身。0019 會將呢條鏈駁上 NetworkPolicy。

4a. 故障對照表：死喺邊層，一眼分

症狀（terminal 真 output）死喺邊層解讀＋下一手
nslookup hello.wrong.svc.cluster.local
** server can't find hello.wrong…: NXDOMAIN		 DNS 層死 ☠️
總機話冇呢個分機		 個名根本唔存在（打錯字／Service 未起／namespace 錯）。下一手：get svc 對名＋namespace，唔使睇 endpoints 住。
nslookup ghost.default.svc.cluster.local
Address: 10.96.77.88（有回音）
wget http://ghost → connection refused／卡住
get endpoints ghost → <none>		 DNS 生、後端死 🔇
總機報咗號，但分機冇人聽		 Service 存在所以有 A record，但 selector 冇射中任何 Ready Pod。下一手：get endpoints＋查 selector／readiness（0007 回帶）。

一句分生死：冇 Address＝總機都唔識你（DNS 層）；有 Address 但連唔上＝總機識你但後面冇人（後端層）。考場見到 NXDOMAIN 三個字，即刻答「名錯／Service 唔存在」，唔好走去 restart Pod！

5. 實作 C：睇下 CoreDNS 本尊

CoreDNS 嘅 Pod 同服務
# 12. CoreDNS 以 Deployment 跑喺 kube-system，label 係 k8s-app=kube-dns
kubectl get pods -n kube-system -l k8s-app=kube-dns

# 13. Pod 嘅 resolv.conf 指住嘅 kube-dns Service（ClusterIP）
kubectl get svc -n kube-system kube-dns

# 14. Corefile：CoreDNS 嘅設定檔（kubernetes 嗰段負責 cluster.local 嘅紀錄）
kubectl get configmap -n kube-system coredns -o yaml
#    睇到 kubernetes cluster.local in-addr.arpa ip6.arpa 嗰幾行，就係佢
收尾
# 15. 刪走今課練習資源（client pod 都一齊收工）
kubectl delete deployment hello
kubectl delete svc hello ghost
kubectl delete ns team-a
kubectl delete pod client

# 16. 課尾確認：叢集乾淨、雙節點
kubectl get pods,svc
kubectl get nodes
考場小抄

① FQDN 樣板：<svc>.<ns>.svc.cluster.local；同 namespace 可以用短名（search 幫你補）。② 除錯兩層：nslookup 個名（DNS 層）→ get endpoints（後端層）→ 再睇 Pod。③ DNS 有回應唔代表用得：NXDOMAIN＝名錯；解到但連唔上＝後端吉或 NetworkPolicy。④ 入 pod 睇設定：cat /etc/resolv.conf（nameserver 應該係 kube-dns）。⑤ headless 嘅 A record 直接回 Pod IP 群。⑥ CoreDNS 設定檔喺 ConfigMap/coredns（Corefile）。

本課戰果

  • 你背熟 Service FQDN 樣板，仲用短名／全名／跨 namespace 三種方法解名成功。
  • 你親手整出「NXDOMAIN」同「Endpoints 吉」兩種故障，建立 DNS 層同後端層嘅分層除錯。
  • 你搵到 CoreDNS 嘅 Pod、kube-dns Service 同 Corefile ConfigMap。
