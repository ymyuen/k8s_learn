Lesson 0011：Ingress 同 Gateway API：L7 路由

目標：將個入口升呢做第七層（HTTP）——用「網址 ＋ 路徑」將外面流量分流去唔同 Service，親手裝好 ingress-nginx、行通 /foo、/bar 同 HTTPS，再認住 Gateway API 企喺邊。考場見到 Ingress 唔通，識分層追！

💡 點解呢課咁重要？
0009 個 NodePort 已經帶到流量入嚟，但佢係「IP:Port」級數——每支服務記一個 port，又唔係人睇嘅網址，好唔貼地。真實世界同 CKA 都要你識 L7：同一個 port，靠條 path 分流。搞掂 Ingress 三件套，呢個係 Services & Networking 最重磅嘅實戰位！
今課先重建叢集（一次性）

Ingress Controller 要接「由 host 入嚟嘅 80/443」，起 kind 嗰陣就要將節點嘅 80/443 mapping 去 host——舊叢集（0005–0010）冇呢個設定，所以要重建。重建會洗走晒所有練習物件，連 0007 裝嘅 metrics-server 都洗埋（唔使驚，0019 開場會補裝）。課尾唔好刪呢個叢集——下堂會成座刪走重建、轉裝 Calico（換 CNI），到時再見。

1. L7 vs L4：一個認網址、一個認 port

0009 嘅 NodePort 已經帶到流量入嚟，但佢係「IP:Port」級數——每支服務記一個 port，亦唔係一般人識睇嘅網址。今課將個入口升上第七層（HTTP）：Ingress 畀你用「網址（host）＋ 路徑（path）」將外面流量帶去唔同 Service，例如 example.com/foo → 服務 A、example.com/bar → 服務 B。同場加映概念級認識 Gateway API（考綱點名、但 CKA 淨係考到概念）。

Service（L4，0009）Ingress（L7，今課）
睇咩 IP ＋ port（TCP/UDP） HTTP host、path、headers
邊個路由 kube-proxy 嘅規則 Ingress Controller（一支真係跑 HTTP server 嘅 Pod）
典型用法 叢集內互嗌、TCP/UDP 服務 對外 HTTP/HTTPS 服務、網址路由

2. Ingress 三件套：資源、類別、控制器

Ingress 機制由三個角色組成，爭一個都唔得：

  • Ingress（資源）：你宣告「邊個 host＋path 轉去邊個 Service」嘅規則——佢淨係一份資料。
  • Ingress Controller（控制器）：真係跑喺叢集入面嘅程式（我哋用 ingress-nginx，一隻 nginx）。佢 watch 住 Ingress 資源，將規則譯做自己嘅設定再真係收流量。
  • IngressClass（類別）：將「Ingress 資源」駁去「Controller」嘅插頭——一個叢集可以同時有幾間 Controller（nginx、traefik…），Ingress 用 ingressClassName 指名要用邊間。

🌐 Ingress 雙層圖：控制面（虛線）vs 數據面（粗線）

點讀呢幅圖：上面虛線係「換腦」：改 Ingress → Controller 重載 nginx.conf；下面粗線係「行腳」：同一個 80 入嚟，靠條 path 派去唔同 Service。TLS 把鎖只鎖大門（Controller），入面行 http 好正常。

三者關係一句話
Ingress（規則：/foo → foo-svc）───ingressClassName───> IngressClass（nginx）
                                                        │ 指向
                                                        ▼
                              Ingress Controller（實際收流量嘅 nginx Pod）

3. 實作：重建帶 host port 嘅叢集

重建 ingress-ready 叢集
# 1. 先睇舊叢集（0005–0010 用落嚟嘅雙節點）
kubectl get nodes
kind delete cluster

# 2. 起個新設定檔 kind-ingress.yaml（control-plane 標上 ingress-ready，
#     並將節點 80/443 mapping 去 host 嘅 80/443）
nano kind-ingress.yaml
kind-ingress.yaml 全文
# kind-ingress.yaml — 0001 嘅雙節點設定 + ingress-ready 三行
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  kubeadmConfigPatches:
  - |
    kind: InitConfiguration
    nodeRegistration:
      kubeletExtraArgs:
        node-labels: "ingress-ready=true"
  extraPortMappings:
  - containerPort: 80
    hostPort: 80
    protocol: TCP
  - containerPort: 443
    hostPort: 443
    protocol: TCP
- role: worker
起叢集並驗證 label
# 3. 起（約 2 分鐘）
kind create cluster --config kind-ingress.yaml
kubectl get nodes

# 4. 確認 control-plane 掛住 ingress-ready=true（kubelet 註冊嗰陣打嘅 label）
kubectl get nodes --show-labels

4. 實作 A：裝 Ingress Controller

裝 ingress-nginx（kind 專用 manifest，v1.15.1 釘版）
# 5. 官方 kind provider manifest（一次起好 Namespace/RBAC/Deployment/IngressClass…）
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller

# 6. 控制器 Pod 一定要喺 kind-control-plane 上——host 嘅 80/443 淨係 mapping 畀佢
kubectl -n ingress-nginx get pods -o wide

# 7. 呢份 manifest 冇釘節點，控制器成日跌咗去 kind-worker——如果係咁，
#    用 0005 嘅 nodeSelector 將佢釘返去 control-plane（ingress-ready label 得佢有）
kubectl -n ingress-nginx patch deployment ingress-nginx-controller --type=json -p '[{"op":"replace","path":"/spec/template/spec/nodeSelector","value":{"ingress-ready":"true","kubernetes.io/os":"linux"}}]'
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller
kubectl -n ingress-nginx get pods -o wide

# 8. 睇呢份 manifest 幫你起好嘅 IngressClass（個名叫 nginx）
kubectl get ingressclass
你應該觀察到咩

第 5 步個 manifest 一次搞掂「控制器 ＋ IngressClass」：之後寫 Ingress 淨係要 ingressClassName: nginx 就自動駁到佢。第 7 步將 0005 嘅 nodeSelector 派上用場——呢份 manifest 冇釘節點，控制器成日跌去 worker，但 host port 淨係 mapping 喺 control-plane，所以多數要自己補第 7 步將控制器釘返去（真實世界叫「將 workload 釘去特定節點」）。

第 11 步就係「L7 路由」嘅全部意義：同一個 localhost:80，靠「條路徑」分別送去兩支唔同 Service。返去 0009 你會發現呢件事 NodePort 做唔到——NodePort 一個 port 淨係對到一支服務。第 12 步個 404 嚟自控制器自己，代表流量有到控制器、淨係冇規則啱用。

喺 Mac 上 curl localhost 唔通？睇下 Docker Desktop 有冇將 port 80 綁定成功，或者轉用 curl http://localhost/foo，再唔得就檢查 kind 嘅 extraPortMappings 係咪真係寫咗入去。

🪜 Ingress 疑難排解天梯（由大門行入房）

點行呢條梯：永遠由大門（host port）行入去，唔好一嚟就拆房（restart Pod）。Timeout＝門／路問題；ADDRESS 吉＝人未返；404＝指示牌問題；502＝後端問題——四個數字，四個唔同部門。

🔍 拆解 curl -k --resolve（三粒掣做咩）：
  • --resolve demo.local:443:127.0.0.1＝自己扮 DNS：我哋冇真 DNS 將 demo.local 指去部機，所以手動話畀 curl 知「呢個名就係 127.0.0.1」。真世界有 DNS 嗰陣唔使加。
  • -k＝唔驗證自簽證：張 cert 係自己用 openssl 簽嘅，唔係公認 CA——-k 即係「我信呢張自簽證，照連」。生產環境有真 cert 就唔使 -k。
  • https://demo.local/foo＝SNI＋path 雙料：個 host 名（demo.local）決定 Controller 揀邊張 cert＋邊條 rule，條 path（/foo）決定去邊支 Service——L7 路由就係靠呢兩個字。

6. 實作 C：Ingress 加 TLS（https）

Ingress 嘅 TLS 好簡單：TLS 憑證係「Secret」，Ingress 引用 Secret 就自動做 TLS 終止（pod 入面仲係行 http）。

自簽憑證 → Secret
# 13. openssl 整自簽憑證（demo.local 做測試網域；-nodes 指唔加密私鑰）
openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout tls.key -out tls.crt -subj "/CN=demo.local"

# 14. 包做 type=kubernetes.io/tls 嘅 Secret（cert/key 兩條鎖匙畀齊）
kubectl create secret tls demo-tls --cert=tls.crt --key=tls.key
kubectl get secret demo-tls
ingress-tls.yaml — host + tls 兩段加落去
# ingress-tls.yaml — tls 段：憑證畀 demo-tls，淨係對 demo.local 呢個 host 生效
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tls-ingress
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - demo.local
    secretName: demo-tls
  rules:
  - host: demo.local
    http:
      paths:
      - path: /foo
        pathType: Prefix
        backend:
          service:
            name: foo-svc
            port:
              number: 8080
套用並用 https 打
# 15. 套用之後，--resolve 將 demo.local 指去 127.0.0.1（我哋冇真 DNS）；-k 跳過自簽警告
nano ingress-tls.yaml
kubectl apply -f ingress-tls.yaml
curl -k --resolve demo.local:443:127.0.0.1 https://demo.local/foo
#    回 foo-app——今次係行 HTTPS 入嚟
收尾同課尾狀態
# 16. 洗走示範應用（叢集本身留返畀 0012 換 CNI）
kubectl delete -f ingress.yaml -f ingress-tls.yaml
kubectl delete -f app.yaml
kubectl delete secret demo-tls
rm -f tls.key tls.crt app.yaml ingress.yaml ingress-tls.yaml

7. Gateway API：Ingress 嘅下一代（概念）

Gateway API 係官方一路推緊嘅下一代流量 API（ingress 嘅進化版）。佢將「入口」拆得更細，用幾隻 CRD 分工：GatewayClass（似 IngressClass）、Gateway（真實入口位，好似 LB）、HTTPRoute（路由規則，可以跨 namespace 引用後端）。好處：表達力勁好多（headers 路由、權重分流、跨 namespace）、又啱幾個 team 共用一個入口。CKA 考綱點咗佢名，但概念識就夠，唔使背 YAML。

考場小抄

① 三件套：Ingress＝規則紙、IngressClass＝指名邊間控制器、Ingress Controller＝真係收流量嗰隻 Pod——ADDRESS 吉通常代表 Controller 未起好。② kubectl get ingress 睇 ADDRESS（kind 會係 localhost）同 describe ingress 睇規則。③ TLS：憑證存做 kubernetes.io/tls Secret（key：tls.crt/tls.key），Ingress 嘅 tls.secretName 引用就得。④ pathType 用 Prefix 就夠應付九成考題；host 同 path 都可以唔寫（唔寫＝全部流量）。⑤ Ingress 規則同後端 Service 要喺同 namespace，除非用 Gateway API。⑥ 出事分層嚟：host 通唔通 → controller pod 喺唔喺 → ingress 規則 → endpoints（0009–0010 舊招）。

本課戰果

  • 你重建咗個 ingress-ready 叢集（host 80/443 → 節點），仲裝好 ingress-nginx（v1.15.1）。
  • 你見證咗 L7 路由：同一個 port，靠 /foo 同 /bar 分流去兩支唔同 Service。
  • 你用自簽憑證 ＋ TLS Secret，令 Ingress 識得終止 HTTPS。
  • 你建立咗 Ingress／IngressClass／Ingress Controller 三件套心智模型，認住 Gateway API 企喺邊。
