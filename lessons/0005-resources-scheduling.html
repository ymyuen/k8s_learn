1. requests 同 limits：Pod 嘅「底價」同「上限」

Pod 可以宣告兩種資源（CPU、memory）嘅兩組數。呢四個欄位就係排程同運行嘅關鍵，睇下呢張表就搞掂：

requests（請求）limits（上限）
作用時機排程時（scheduler 找節點）運行時（kubelet 強制執行）
意義「我至少要這麼多」——保證額度「我最多用這麼多」——使用天花板
CPU 超過會怎樣—被節流（throttle），變慢但不會死
Memory 超過會怎樣—OOMKilled，容器被殺掉重啟

CPU 單位：1＝一粒完整核心，細數或者毫核 100m＝0.1 核。Memory 單位：128Mi（mebibytes，2 嘅次方）或者 1Gi；考場最常見 Mi/Gi。Scheduler 揀 Node 嗰陣淨係計 requests：佢將每台 Node 上面所有 Pod 嘅 requests 加總，describe node 嘅「Allocated resources」就係呢本數簿。想查術語可睇 詞彙表 QoS。

2. QoS：冇寫 requests 嘅 Pod 排最尾

三個欄位冇寫齊，Pod 會畀人分入三種 QoS（服務品質）等級之一，OOM 要殺人嗰陣就按等級嚟：

  • Guaranteed：每粒 container 都寫咗 requests，而且 requests ＝ limits（CPU 同 memory 都係）。優先級最高，最難畀 OOM 斬。
  • Burstable：至少一粒 container 有 requests，但唔等於 limits（最常見）。
  • BestEffort：任何 container 都冇寫 requests／limits。唔夠資源嗰陣第一個畀人斬。

秒判法：「有冇寫」→「等唔相等」。全部冇寫＝BestEffort；有寫兼全等＝Guaranteed；其他＝Burstable。

requests（訂位）limits（食量上限）真實用量（實際食幾多）
邊個話事你寫喺 YAML，scheduler 用嚟揀位你寫喺 YAML，kubelet 用嚟執法container 實際用幾多，metrics-server 先知
CPU 爆咗唔夠位就 Pending，排唔到被 throttle（限速變慢，唔會死）用多過 limit 就畀人限速，似水喉收細
Memory 爆咗唔夠位就 Pending，排唔到OOMKilled（直接斬咗個 container 再重啟）用多過 limit 即畀 kubelet 斬，似食自助餐食爆要離場

🪜 QoS 天梯：邊個先畀 OOM 斬？

記法：訂位都冇嗰個（BestEffort）OOM 一嚟第一個畀人斬；訂咗位又唔食過龍嗰個（Guaranteed）留到最後。CPU 爆只係慢（throttle），Memory 爆先會死（OOMKilled）——呢句係選擇題熱門。

4. Taints 同 Tolerations：邊個唔畀嚟、邊個忍到

0001 預告過：正式叢集嘅 control-plane 帶 node-role.kubernetes.io/control-plane:NoSchedule 污點，普通 Pod 上唔到去；kind 起單節點嗰陣幫你拔走咗，所以你先喺 kind-control-plane 跑到 Pod。成個機制拆開兩半睇：

  • Taint 打喺Node 上面，好似貼「本店唔招待」：效果有 NoSchedule（唔排新嘅）、PreferNoSchedule（盡量唔排）、NoExecute（唔排新嘅，仲將上面啲 Pod 趕走）。
  • Toleration 寫喺Pod 上面，好似「我有 VIP 卡」：對得上污點嘅 Pod 先畀排上去。口訣：容忍只係「畀你入」，唔係「 prefer 你入」——加咗 toleration 唔代表一定會排過去。

Taint 語法：kubectl taint node <節點名> <key>=<value>:<Effect>；拎走嗰陣尾加 -。Toleration 喺 Pod 嘅 spec.tolerations：

toleration 的標準 YAML 寫法（對照關係用顏色記）
# taint（節點上）：disk=slow:NoSchedule
tolerations:
- key: disk
  operator: Equal
  value: slow
  effect: NoSchedule
# 一一對應：key 相同、operator=Equal + value 相同、effect 相同，
# 這顆 Pod 才「忍得住」那顆節點上的污點。

5. 實作 B：親眼見 control-plane 污點，再將 Node「閂／開」

今課開場起嘅雙節點 kind 叢集，control-plane 留返正式叢集個污點（kind 得單節點嗰陣先自動幫你拎走，0001 講嘅就係單節點 case）。呢個就係今課最好嘅教材：先睇污點點樣令 Pod「全逼去 worker」，再貼多個污點睇 Pod 卡 Pending，最後用 toleration 放行。

想將 Pod 都放上 control-plane？（實驗用）

兩個方法二揀一：① 拎走 control-plane 個污點 kubectl taint node kind-control-plane node-role.kubernetes.io/control-plane:NoSchedule-；② 喺 Pod 加返條對應嘅 toleration（key node-role.kubernetes.io/control-plane、effect NoSchedule）。正式叢集唔建議將普通 workload 放上 control-plane，但考試可能叫你將某粒 Pod 排上去——識呢條指令就夠。

NoExecute 的差別（考試愛考一句話）

將效果換成 NoExecute，唔止「唔排新嘅」——kubelet 會將已經喺嗰台 Node 上面、又冇對應 toleration 嘅 Pod 直接趕走（terminate）。Pod 可以加 tolerationSeconds 話「寬限 N 秒先趕」。NoExecute 成日用嚟做「要落線維修嘅 Node 先將 Pod 趕走」。

6. nodeSelector 同 Node Affinity：Pod 指定要去邊台

Taint/Toleration 係「Node 拒絕你」；調轉，Pod 都可以「指明想去邊」：

  • nodeSelector：最簡單——將 Pod 釘死喺「帶某 label」嘅 Node 上面。語法淨係識比「等於」，而且 nodeSelector 指明嗰個鍵嘅 label 要喺 Node 度存在先排得上。
  • Node Affinity（節點親和性）：更強表達力——requiredDuringSchedulingIgnoredDuringExecution（硬性，等於 nodeSelector 但支援 In/NotIn 等 operator）同 preferredDuringSchedulingIgnoredDuringExecution（軟性，「盡量」但唔包）。

一句對比：nodeSelector 係「淨識等於嘅 affinity」；affinity 係「識揀 label 嘅 nodeSelector」。

🍸 酒吧版一次記晒：保安、訂位、同「盡量坐窗口」

諗返 0001 門口保安：taint 係門口阿哥話「呢層 VIP 先入得」（Node 拒絕你），toleration 係你袋住張 VIP 卡（有卡先畀入，無卡企門口＝Pending）。而 nodeSelector 係你自己話「我要坐有 disk=fast 牌嗰張枱」（Pod 指明要去邊，冇嗰張枱就企喺度等）。affinity required 係同一句說話講得精啲（識講 In/NotIn），preferred 係「最好有窗口位啦，無都坐低先」（軟性，盡量但唔包）。保安唔畀入同你揀錯位，結果都係 Pending——分別只在於怪保安定怪自己。

並排對照：nodeSelector vs required（硬）vs preferred（軟）——留意縮排層級
# A. nodeSelector：最短，淨識「等於」（縮排 2 層：spec.template.spec → nodeSelector）
spec:
  template:
    spec:                    # ← Pod.spec（第 1 層）
      nodeSelector:          # ← 第 2 層：同 containers 平級
        disk: fast           # ← 第 3 層：key: value，淨識等於

# B. nodeAffinity required：硬性，等於 nodeSelector 但識 In/NotIn（縮排 5 層先到 key）
spec:
  template:
    spec:                    # ← 第 1 層
      affinity:              # ← 第 2 層
        nodeAffinity:        # ← 第 3 層
          requiredDuringSchedulingIgnoredDuringExecution:  # ← 第 4 層：硬性
            nodeSelectorTerms:                             # ← 第 5 層
            - matchExpressions:                            # ← 第 6 層（list 加 -）
              - key: disk            # ← 第 7 層：先見到條件
                operator: In         # ← In / NotIn / Exists 任揀
                values: [fast]       # ← 想要嘅值

# C. nodeAffinity preferred：軟性，「盡量」唔包（多 weight＋preference 包住）
spec:
  template:
    spec:                    # ← 第 1 層
      affinity:              # ← 第 2 層
        nodeAffinity:        # ← 第 3 層
          preferredDuringSchedulingIgnoredDuringExecution: # ← 第 4 層：軟性
          - weight: 10                         # ← 第 5 層：分數，愈大愈想去
            preference:                        # ← 第 5 層：想要咩
              matchExpressions:                # ← 第 6 層
              - key: disk                      # ← 第 7 層
                operator: In
                values: [fast]
# 考場背法：見 required＝唔啱就 Pending；見 preferred＋weight＝唔啱都照排，只係少分

7. 實作 C：nodeSelector 釘死 worker，再改寫做 affinity

nodeSelector 把 Pod 釘在 worker
# 25. 先幫 kind-worker 貼一個 label（用 0003 的 kubectl label）
kubectl label node kind-worker disk=fast

# 26. 產出 YAML 並加 nodeSelector（在 template.spec 下、containers 外）
kubectl create deployment pinned --image=nginx:1.25 --replicas=2 --dry-run=client -o yaml > pinned.yaml
nano pinned.yaml
#      spec.template.spec:
#        nodeSelector:
#          disk: fast
kubectl apply -f pinned.yaml

# 27. 兩顆都該在 kind-worker 上——這就是「釘選」
kubectl get pods -o wide -l app=pinned
把 nodeSelector 改寫成等價的 nodeAffinity
# 28. 用 nano 把 nodeSelector 段換成 nodeAffinity（硬性 required）
nano pinned.yaml
#      spec.template.spec:
#        affinity:
#          nodeAffinity:
#            requiredDuringSchedulingIgnoredDuringExecution:
#              nodeSelectorTerms:
#              - matchExpressions:
#                - key: disk
#                  operator: In
#                  values: [fast]
kubectl apply -f pinned.yaml
kubectl get pods -o wide -l app=pinned
#    效果與 nodeSelector 相同，但 operator 可以換成 NotIn 等條件

# 29. 收尾：刪 Deployment、移除節點 label
kubectl delete deployment pinned
kubectl label node kind-worker disk-
rm pinned.yaml

# 30. 課末確認叢集狀態：乾淨的雙節點，留給下一課
kubectl get nodes
kubectl get pods -A | head
你應該觀察到咩

第 26 步兩粒 Pod 全部喺 kind-worker，因為 nodeSelector 係硬條件：Node 上面冇 disk=fast 呢個 label，Pod 就會卡喺 Pending（試下拎走個 label 再起就見到）。第 28 步將同一個條件翻譯做 nodeAffinity，行為一樣、表達力升級——考試兩樣都要識寫。

考場小抄

① taint 語法：kubectl taint node <node> key=value:Effect，拎走加 -；三種效果 NoSchedule／PreferNoSchedule／NoExecute，最後嗰個會趕走舊 Pod。② toleration 同 taint 要「一對一」：key、operator/value、effect 三樣啱晒先有效；容忍 ≠ 偏好。③ 資源數簿：kubectl describe node 睇 Allocated resources；Pod 排唔上先查 Node 嘅 Events 同污點。④ QoS 秒判：全冇寫＝BestEffort；有寫兼全等＝Guaranteed；其他＝Burstable。⑤ 想排指定 Node：先確認 label（kubectl get nodes --show-labels），nodeSelector 淨識等於、affinity 先支援 In/NotIn。

本課戰果

  • 你將練習環境正式切咗去 WSL2 bash，仲喺 WSL2 起返雙節點 kind 叢集。
  • 你識寫 requests／limits，識睇 Node 嘅 Allocated resources，仲識分三種 QoS 等級。
  • 你親手貼過又拎走 Node 污點，見證 NoSchedule「淨擋新 Pod」，仲識用 toleration 攞返排程資格。
  • 你識用 nodeSelector 將 Pod 釘去指定 Node，仲識將同一個條件改寫做 nodeAffinity。
