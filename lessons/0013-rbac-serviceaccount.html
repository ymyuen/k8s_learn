Lesson 0013：RBAC 與 ServiceAccount：邊個做得咩

目標：搞掂「你係邊個」（ServiceAccount）同「你做得咩」（RBAC）兩件事，親手玩齊 Role、ClusterRole、Binding 四件套，再用 auth can-i 秒驗權限。考場見到 403 即刻知邊度瀨嘢！

💡 點解呢課咁重要？
之前你一路都係用管理員權限，橫行直撞冇人阻你。真實世界同考場一樣，每個人、每支程式都只應該有「啱啱好」嘅權限。RBAC 係 CKA 必考實作題，唔識四格表就等如送分畀人！

1. 睇下先：Authentication 同 Authorization

  • 人用 kubeconfig 憑證登入；Pod 唔係人——佢用 ServiceAccount 做身份證。每個 namespace 都有個自動起好嘅 default ServiceAccount，Pod 冇指明就用佢。
  • Pod 一指明 SA，kubelet 就會將 SA 嘅 token 掛入 /var/run/secrets/kubernetes.io/serviceaccount——Pod 入面啲程式就靠佢去搵 apiserver 傾偈。
  • RBAC 授權模型好貼地：將權限（Role）「綁」畀身份（User／Group／ServiceAccount）。Role 寫明「對咩資源做得咩動作」；Binding 決定「邊個拎到呢份權限」。

詳細定義睇 詞彙表 ServiceAccount 同 詞彙表 RBAC。

RBAC 最細詞彙
Role（角色）            ：對「某些資源」嘅「某些動作」白名單
                           例：對 pods 可以 get、list
  │ 被 binding 綁畀
  ▼
ServiceAccount（身份）  ：example：demo namespace 嘅 app-sa

2. 兩種 Role × 兩種 Binding：四格表

權限可以「只管一個 namespace」（Role）或者「管成個叢集」（ClusterRole）；綁定可以「只綁一個 namespace」（RoleBinding）或者「綁成個叢集」（ClusterRoleBinding）。合法組合得三種：

RoleBinding（綁 namespace 範圍）ClusterRoleBinding（綁叢集範圍）
Role
（單 namespace 權限）		 權限只喺嗰個 namespace 生效
例：Role「睇 pod」+ RoleBinding in demo → 只睇到 demo 嘅 pod		 （唔合法嘅組合——唔可以將單 namespace 嘅 Role 綁成全叢集）
ClusterRole
（叢集權限）		 考點：權限被「縮返」入 binding 嘅 namespace
例：ClusterRole「view」+ RoleBinding in demo → 喺 demo 睇 deployments 得，別嘅 namespace 唔得		 權限全叢集生效
例：ClusterRole「node-reader」+ ClusterRoleBinding → 去邊都睇到 node

一句記住：ClusterRoleBinding 將 ClusterRole 放到全叢集；RoleBinding 將「namespaced 資源」嘅權限放行喺「嗰個 namespace」。（注意：RoleBinding 對 node 呢類叢集資源本身無效——nodes 唔屬於任何 namespace。Kubernetes 有內建 ClusterRole 如 view／edit／cluster-admin，考場直接重用好方便。）

🍜 港式比喻：員工證＋門禁白名單＋大堂保安
ServiceAccount 就係張員工證（app-sa 寫住你係邊個）；Role 就係張門禁白名單（寫明邊道門開得：pods 准 get／list）；Binding 就係人事部話「呢張證配呢張白名單」；apiserver 就係大堂保安，每次拍卡都要查表，唔啱即刻彈 403。

🔐 RBAC 授權流向圖：四格過關鏈＋閘口

成個 RBAC 就係一條鏈：身份（Pod＋SA）→ 保安（apiserver）→ 綁定＋權限 → 資源。斷咗任何一環都係 403，排錯就係逐環睇。

--as= 拆骨：四節就係門牌＋人名
system : serviceaccount : demo : app-sa
￣￣￣￣   ￣￣￣￣￣￣￣￣￣   ￣￣￣   ￣￣￣￣
固定前綴   帳號種類         房號     個人名
（系統帳號）（SA 身份證）   （ns）   （SA 名）
例：kubectl auth can-i get pods -n demo --as=system:serviceaccount:demo:app-sa
Role 段寫咩白話
rulesapiGroups／resources／verbs白名單：邊啲門用得、開門動作有咩
subjectskind: ServiceAccount＋name＋namespace邊張員工證拎到（本課：demo/app-sa）
roleRefkind＋name（改唔到，一綁定終身）指去邊張白名單（本課：Role/pod-reader）

📌 新手注意：apiGroups: [""] 嘅空字串唔係打漏嘢——pods、nodes 呢啲住喺「核心群組」，佢哋係無姓家族，個姓就係空字串。deployments 先姓 apps，jobs 姓 batch。

3. 實作 A：ServiceAccount 同「用佢嘅 Pod」

建 namespace 與 ServiceAccount
# 1. 開個練習 namespace（之後嘅 Role/RoleBinding 都要指名佢）
kubectl create ns demo

# 2. 建立 ServiceAccount app-sa
kubectl -n demo create serviceaccount app-sa
kubectl -n demo get sa
pod-sa.yaml — Pod 指名用 app-sa
# pod-sa.yaml — serviceAccountName 一指定，token 就自動掛入 Pod
apiVersion: v1
kind: Pod
metadata:
  name: sa-demo
  namespace: demo
spec:
  serviceAccountName: app-sa
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
套用並睇自動掛載嘅憑證
# 3. 套用後入容器睇 SA 嘅 token 同 CA
nano pod-sa.yaml
kubectl apply -f pod-sa.yaml
kubectl exec -n demo sa-demo -- ls /var/run/secrets/kubernetes.io/serviceaccount
#    token / ca.crt / namespace 三件套——Pod 內程式用佢哋呼叫 apiserver
你應該觀察到咩

ServiceAccount 係「畀 Pod 用嘅身份證」：佢本身唔畀任何權限（權限靠 RBAC 另行派），只係等 apiserver 認得「呢支程式係 app-sa」。預設嘅 default SA 通常冇綁任何權限，所以「Pod 內程式直接呼叫 apiserver」成日撞 403——呢個好正常，唔使驚。

4. 實作 B：Role + RoleBinding，逐步驗證

role.yaml — 只准喺 demo 睇 Pod
# role.yaml — apiGroups "" 係核心群組（pods 住喺呢度）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
rolebinding.yaml — 將 pod-reader 綁畀 app-sa
# rolebinding.yaml — subjects 指名 ServiceAccount 身份
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: demo
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: demo
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
套用，用 auth can-i 逐項驗證
# 4. 套用 Role 同 RoleBinding
nano role.yaml
nano rolebinding.yaml
kubectl apply -f role.yaml -f rolebinding.yaml

# 5. 以 app-sa 嘅身份「試問」權限——CKA 必備驗證工具
kubectl auth can-i get pods -n demo --as=system:serviceaccount:demo:app-sa
#    yes（Role 准 get）
kubectl auth can-i list pods -n demo --as=system:serviceaccount:demo:app-sa
#    yes（Role 准 list）
kubectl auth can-i delete pods -n demo --as=system:serviceaccount:demo:app-sa
#    no（Role 冇畀 delete）
kubectl auth can-i get pods -n kube-system --as=system:serviceaccount:demo:app-sa
#    no——Role 只活喺 demo namespace
加權限：edit Role 再驗證一次
# 6. nano 將 verbs 加上 delete，重新 apply
nano role.yaml
kubectl apply -f role.yaml
kubectl auth can-i delete pods -n demo --as=system:serviceaccount:demo:app-sa
#    變成 yes——Role 一改，綁定即刻跟住生效
你應該觀察到咩

第 5 步嘅 --as= 係「扮成邊個」：唔使真係換憑證，就可以問 apiserver「如果我係 app-sa，我 delete pods 得唔得？」。auth can-i 係 CKA 除錯 RBAC 嘅萬用起手式——見到 403 先問佢，答案九成都係「唔記得綁權限」或者「綁咗去隔籬 namespace」。

5. 實作 C：ClusterRole × 兩種 Binding 嘅差別

clusterrole.yaml — 叢集級嘅「睇 node」權限
# clusterrole.yaml — ClusterRole 冇 namespace（全叢集得一份）
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list"]
實驗一：ClusterRoleBinding → 全叢集都睇到 node
# 7. 用 kubectl 一鍵綁（clusterrolebinding 冇 namespace）
kubectl create clusterrolebinding sa-see-nodes --clusterrole=node-reader --serviceaccount=demo:app-sa

# 8. 驗證：nodes 係叢集資源，去邊都睇到
kubectl auth can-i get nodes --as=system:serviceaccount:demo:app-sa
#    yes（ClusterRoleBinding = 叢集級生效）
kubectl auth can-i list nodes --as=system:serviceaccount:demo:app-sa
#    yes
實驗二：RoleBinding 綁 ClusterRole → 被困返入 namespace
# 9. 換種綁法：改用內建 ClusterRole「view」＋ RoleBinding 綁喺 demo
#    （先刪走頭先嘅 ClusterRoleBinding，費事干擾判讀）
kubectl delete clusterrolebinding sa-see-nodes
kubectl create rolebinding demo-view --clusterrole=view --serviceaccount=demo:app-sa -n demo

# 10. 驗證：喺 demo 睇 deployment 得……
kubectl auth can-i list deployments -n demo --as=system:serviceaccount:demo:app-sa
#    yes（view 含 deployments 嘅 get/list，經 RoleBinding 落喺 demo）
kubectl auth can-i list deployments -n kube-system --as=system:serviceaccount:demo:app-sa
#    no——同一份 ClusterRole，RoleBinding 將佢困返喺 demo
你應該觀察到咩

第 8 步同第 10 步係四格表嘅核心對照：同一份 ClusterRole（甚至內建嘅 view），用 ClusterRoleBinding 綁＝全叢集，用 RoleBinding 綁＝得返嗰個 namespace。「將 ClusterRole 用 RoleBinding 綁喺某個 namespace，畀嗰度啲人一套標準權限」係實務上最常見嘅設計。

收尾
# 11. 收尾：刪走練習物件（ns demo 會連埋刪入面嘅 SA/Pod/Role/Binding）
kubectl delete ns demo
kubectl delete clusterrole node-reader
rm -f pod-sa.yaml role.yaml rolebinding.yaml clusterrole.yaml
kubectl get nodes
考場小抄

① kubectl auth can-i VERB RESOURCE [--as=...] [-n NS]——RBAC 除錯第一招；加 --list 一次列出全部權限。② 四物件組合背到爛：Role×RoleBinding＝嗰個 namespace；ClusterRole×RoleBinding＝被縮返入 binding 嘅 namespace；ClusterRole×ClusterRoleBinding＝全叢集；Role×ClusterRoleBinding＝唔存在。③ 身份字串格式：system:serviceaccount:<ns>:<name>。④ 常用 apiGroups：""（pods/nodes/…）、apps（deployments）、batch（jobs）、networking.k8s.io（ingresses/networkpolicies）、rbac.authorization.k8s.io。⑤ 內建 ClusterRole 可重用：view／edit／cluster-admin。⑥ 見到 403：先確認「Role 有 verbs？」→「Binding 嘅 namespace 啱唔啱？」→「subject 個名啱唔啱？」

本課戰果

  • 你起咗 ServiceAccount，仲令 Pod 指名用佢（token 自動掛載）。
  • 你用 Role + RoleBinding 派咗「demo 睇 Pod」權限，仲用 auth can-i 逐項驗過同加權。
  • 你對照實驗咗 ClusterRole × ClusterRoleBinding 同 × RoleBinding 嘅範圍差別。

小測驗

ClusterRole 經 RoleBinding 綁喺某 namespace，權限範圍係？

Pod 想用指定身份呼叫 apiserver，要 set 邊個欄位？

「對 pods 可以 get、list」喺 RBAC 入面係邊一段？
