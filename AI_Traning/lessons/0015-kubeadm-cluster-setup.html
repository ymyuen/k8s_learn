kubeadm 叢集建置（Killercoda）

到 0014 為止，叢集都是 kind「生」出來的；本課把控制平面親手建一次——用 kubeadm（Kubernetes 官方叢集建置工具）在兩台 VM 上從零 init／join。0001 那張「控制平面元件圖」從此變成你親手裝出來的東西：preflight、憑證、static pod、CNI，每一步都看得到。因為本課要動「整台乾淨的作業系統」，練習環境改用 Killercoda 的拋棄式 VM（瀏覽器內、壞了重建即可）——本機的 Calico 叢集完全不受影響，0017 還會回來用它。

本課與 0016 都在 Killercoda 進行

開啟 killercoda.com（RESOURCES 裡列的免費瀏覽器練習場），挑一個「kubeadm／Kubernetes cluster setup、含 control-plane＋worker 兩台 VM、Ubuntu 且已裝好 kubeadm/kubelet/kubectl」的場景。若該場景沒預裝 kubeadm，先照官方 Install kubeadm 頁面裝：安裝 containerd／kubeadm／kubelet／kubectl 三步驟。練習完直接關掉重建，本機叢集不動。

kubeadm init 在背後做了什麼

記住這條流程，考場填空都用得到：

  • preflight：檢查 root、CPU/記憶體、hostname、port 沒被佔用。
  • 產生憑證與 kubeconfig：CA 與各元件憑證（apiserver/controller-manager/scheduler/etcd/admin…）放 /etc/kubernetes/pki；kubeconfig 放 /etc/kubernetes。
  • 寫下控制平面 static pod manifest：/etc/kubernetes/manifests/ 底下出現 kube-apiserver.yaml、kube-controller-manager.yaml、kube-scheduler.yaml、etcd.yaml——kubelet 一看到就把它們拉起來（0014 的 etcd 就是這樣活的）。
  • 發 bootstrap token：印出 join 指令，讓 worker 可以帶著 token 加入。
  • 等 CNI：網路沒裝前節點是 NotReady、coredns 卡 Pending（0012 看過一模一樣的症狀）。

kubeadm join 則是 worker 端的鏡像流程：拿 token 跟 apiserver 握手、要一張自己的憑證、kubelet 註冊上叢集。

HA 拓撲：兩種 etcd 放法

Stacked etcd（疊放）External etcd（外置）
etcd 放哪 與 control plane 同台（每台 cp 各一份） 獨立的 etcd 主機群
機器需求 少（cp 幾台就幾份 etcd） 多（cp + 獨立 etcd 群）
適合 考試、中小叢集、實驗 生產、etcd 與 cp 要分開維護

實作 A：kubeadm init + CNI

在 control-plane VM 上 init
# 1. 先確認三件套已就位（Killercoda 場景通常已裝好）
kubeadm version
kubelet --version
kubectl version --client

# 2. init：--pod-network-cidr 給 Calico 用的網段（跟 0012 對齊 192.168.0.0/16）
sudo kubeadm init --pod-network-cidr=192.168.0.0/16
#    成功後會印出一大段：kubeconfig 設定步驟、join 指令、token
設定 kubectl（root 的 admin.conf 拷給目前使用者）
# 3. kubeadm 把「管理員 kubeconfig」放在 /etc/kubernetes/admin.conf
#    拷到 $HOME/.kube/config 之後 kubectl 才認得叢集
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 4. 看成果：control-plane 已 Ready，但 worker 還沒 join、網路還沒裝
kubectl get nodes
kubectl get pods -n kube-system
#    coredns 卡 Pending、節點可能 NotReady——都是「還沒裝 CNI」的症狀
裝 CNI（Calico，v3.32.2，0012 同一套）
# 5. Calico operator 與 CRD、安裝設定——三支指令照抄
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.2/manifests/v1_crd_projectcalico_org.yaml
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.2/manifests/tigera-operator.yaml
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.2/manifests/custom-resources.yaml

# 6. 等 calico-system 就緒，節點轉 Ready
kubectl get pods -n calico-system -w
kubectl get nodes
你該觀察到什麼

第 4 步到第 6 步是 0001 理論的完整重現：init 只裝控制平面，不裝網路；節點 NotReady、coredns Pending，直到 CNI 上線才全部轉好。親手建過一次，Troubleshooting 時看到「NotReady + Pending」就會直覺想到「先查 CNI」。

實作 B：worker join + 驗收

在 control-plane 上拿 join 指令
# 7. token 有時效（預設 24h）；過期就重新產生並直接印出完整 join 指令
#    （這支指令要讀 root 的 admin.conf，非 root 記得加 sudo）
sudo kubeadm token create --print-join-command
#    輸出長得像：
#    kubeadm join 192.168.x.x:6443 --token xxxxxx.xxxxxxxxxxxxxxxx \
#        --discovery-token-ca-cert-hash sha256:xxxxxxxxxxxxxxxx
在 worker VM 上執行 join
# 8. 把上一支指令的輸出（整段 kubeadm join ...）貼到 worker VM 執行
sudo kubeadm join 192.168.x.x:6443 --token xxxxxx.xxxxxxxxxxxxxxxx --discovery-token-ca-cert-hash sha256:xxxxxxxxxxxxxxxx
#    成功會印 "This node has joined the cluster"
回 control-plane 驗收
# 9. worker 出現在節點清單、狀態 Ready
kubectl get nodes
kubectl get pods -A -o wide
#    calico-node 在每台節點各一顆（0004 的 DaemonSet 現場）

# 10. 驗收：佈一支 Deployment 跨節點跑，再刪掉
kubectl create deployment demo --image=nginx:1.25 --replicas=3
kubectl get pods -o wide
kubectl delete deployment demo

實作 C：加第二個 control plane（走查）

HA 控制平面需要至少兩台 control-plane 與一個負載平衡器（把 apiserver 流量分給兩台 cp）。本課 Killercoda 場景通常只有 2 台 VM，所以這一段是「走查」——看懂流程即可，不必實跑：

多 cp 的 join 流程（概念走查）
# 在第一台 cp init 時加 --control-plane-endpoint 指向 LB，並 --upload-certs
# 讓憑證可以被第二台 cp 下載：
sudo kubeadm init --pod-network-cidr=192.168.0.0/16 --control-plane-endpoint=lb.example.com:6443 --upload-certs

# 第一台 cp 印出的輸出裡，除了 worker 的 join 指令，還有一段「control-plane 專用」：
sudo kubeadm join lb.example.com:6443 --token xxxxxx --discovery-token-ca-cert-hash sha256:xxx --control-plane --certificate-key yyyyy

# --control-plane 告訴 kubeadm：「我是新的 control plane，不是 worker」；
# --certificate-key 讓它解密第一台 cp 上傳的憑證
考場小抄

① init 後三件事：設 kubeconfig（admin.conf → ~/.kube/config）、裝 CNI、join worker——口訣「config、CNI、join」。② token 過期：kubeadm token create --print-join-command 一行搞定。③ 憑證在 /etc/kubernetes/pki，各 kubeconfig 在 /etc/kubernetes；admin.conf 是管理員權限那把。④ 控制平面元件 = /etc/kubernetes/manifests/ 下的 static pod。⑤ 多 cp：init 加 --control-plane-endpoint（LB）與 --upload-certs，join 加 --control-plane --certificate-key。⑥ 節點 NotReady：九成是 CNI 沒裝或 CNI pod 沒起來。

本課戰果

  • 你在 Killercoda 的乾淨 VM 上用 kubeadm init 建出控制平面，並說出 init 的背後步驟。
  • 你設定 admin kubeconfig、裝上 Calico CNI，看到節點從 NotReady 轉 Ready。
  • 你用 kubeadm token create --print-join-command 讓 worker join 並驗收。
  • 你走查了第二個 control plane 的 join 流程，並認識 stacked 與 external etcd 兩種 HA 拓撲。
