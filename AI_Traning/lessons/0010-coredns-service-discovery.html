CoreDNS 與服務發現

0009 的 Service 給了每群 Pod 一個 VIP，但你總不能叫工程師都背 VIP。本課把「找到對方」變成一件靠名字的事：叢集內建的 DNS——CoreDNS。學會兩件事：① Service 的完整網域名稱（FQDN）長什麼樣、怎麼縮寫；② 出問題時，DNS 層與 Endpoints 層怎麼分（這是 CKA Troubleshooting 的經典分層）。本課沿用 0009 的雙節點叢集。

Service 的 FQDN 樣板

每個 Service 都會被 CoreDNS 登記一個 A record，樣板長這樣：

FQDN 樣板（背起來）
<service>.<namespace>.svc.<cluster-domain>
     │        │        │        └─ 預設 svc.cluster.local
     │        │        └─ 固定是 svc（表示 Service）
     │        └─ Service 所在的 namespace
     └─ Service 名稱

hello.default.svc.cluster.local   ← 全名（FQDN）
hello                              ← 短名：靠 resolv.conf 的 search 補後綴

Pod 內的 /etc/resolv.conf 由 kubelet 自動生成：nameserver 指向 kube-system 的 kube-dns Service（CoreDNS 的前端），search 則列了一串要自動補的後綴（通常含 <pod 的 namespace>.svc.cluster.local 等）——這就是「同 namespace 裡打短名就通」的原因。另外一個細節：ndots:5 代表名稱裡有 5 個點（含）以上才先當 FQDN 查，否則先套 search 後綴試試看。

A record 與 SRV record

  • A record：Service 名稱 → VIP。Headless Service（0009 的 clusterIP: None）則回傳它身後每顆 Pod 的 IP——這是資料庫類工作負載「直接連各顆 Pod」的機制。
  • SRV record：Service 有「具名 port」時，_<port-name>._<protocol>.<svc>... 會回傳「哪個 port 在服務」。

CoreDNS 是一顆跑在 kube-system 的 Deployment，它 watch Service／Pod 的變化來更新紀錄；設定存在 ConfigMap/coredns 的 Corefile 裡。

實作 A：短名、全名、跨 namespace

準備可解析的服務與客戶端
# 1. 確認 0009 的 client pod 還在且 Running（NotFound 或已 Completed 都重建）
kubectl get pod client
#    若非 Running：kubectl delete pod client --ignore-not-found
#    kubectl run client --image=busybox:1.36 --restart=Never -- sleep 3600
#    kubectl wait --for=condition=Ready pod/client

# 2. 佈一顆要被解析的 nginx 服務
kubectl create deployment hello --image=nginx:1.25 --replicas=1
kubectl expose deployment hello --port=80
kubectl rollout status deployment/hello
解析：全名、短名、resolv.conf
# 3. 看 Pod 內的 DNS 設定：nameserver = kube-dns、search 幫你補後綴
kubectl exec client -- cat /etc/resolv.conf

# 4. 全名解析（busybox 的 nslookup 不吃 search 自動補，給全名最保險）
kubectl exec client -- nslookup hello.default.svc.cluster.local

# 5. 短名「hello」會通，是因為 search 欄自動補上 default.svc.cluster.local
kubectl exec client -- wget -qO- http://hello | head -n 3
跨 namespace：只能用全名
# 6. 開一個 team-a namespace，放一支 api 服務
kubectl create ns team-a
kubectl -n team-a create deployment api --image=nginx:1.25 --replicas=1
kubectl -n team-a expose deployment api --port=80

# 7. 從 default namespace 用全名打過去
kubectl exec client -- nslookup api.team-a.svc.cluster.local
kubectl exec client -- wget -qO- http://api.team-a.svc.cluster.local | head -n 3
#    短名 http://api 在這裡不通——client 的 search 只會補 default 的後綴
你該觀察到什麼

第 4–5 步的對照是 DNS 縮寫機制的全部：全名一定通；短名通不通看 search 欄。第 7 步是跨 namespace 的唯一寫法：服務名.namespace.svc.cluster.local。想在別的 namespace 用短名？把 Pod 建到同一個 namespace，或自己改 dnsConfig——考試知道「預設短名只在本 namespace 有效」即可。

實作 B：故障分層——名字錯 vs 後端空

接下來演練 CKA 最愛考的「分層判斷」：同樣是「連不到」，是 DNS 找不到名字，還是 DNS 找得到但沒後端可連？兩層的症狀完全不同。

第一層：名字打錯（NXDOMAIN）
# 8. 名稱不存在：CoreDNS 回 NXDOMAIN——這是「DNS 層」的問題
kubectl exec client -- nslookup hello.wrong.svc.cluster.local
#    輸出會有 "can't find" / NXDOMAIN
第二層：Service 存在但 selector 沒打到任何 Pod
# 9. 造一顆 selector 對不到任何 Pod 的 Service（名字 ghost）
kubectl create -f - <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: ghost
spec:
  selector:
    app: no-such-app
  ports:
  - port: 80
EOF

# 10. DNS 解析得到 ghost（Service 存在就有 A record）——DNS 層正常
kubectl exec client -- nslookup ghost.default.svc.cluster.local

# 11. 但 Endpoints 是空的——後端空，連線被拒
kubectl get endpoints ghost
kubectl exec client -- wget -qO- -T 3 http://ghost || echo '-- connection refused --'
你該觀察到什麼

對照第 8 與 10–11 步：名字打錯 = DNS 直接說查無此人（NXDOMAIN）；selector 沒打到 = DNS 說有這個 Service，但 Endpoints 空空如也、TCP 連不上。除錯順序從此建立：先 nslookup 確認 DNS 層，再 get endpoints 確認後端層——兩層都通才輪到看 Pod 本身。0019 會把這條鏈接上 NetworkPolicy。

實作 C：看看 CoreDNS 本尊

CoreDNS 的 Pod 與服務
# 12. CoreDNS 以 Deployment 跑在 kube-system，label 是 k8s-app=kube-dns
kubectl get pods -n kube-system -l k8s-app=kube-dns

# 13. Pod 的 resolv.conf 指到的 kube-dns Service（ClusterIP）
kubectl get svc -n kube-system kube-dns

# 14. Corefile：CoreDNS 的設定檔（kubernetes 區塊負責 cluster.local 的紀錄）
kubectl get configmap -n kube-system coredns -o yaml
#    看到 kubernetes cluster.local in-addr.arpa ip6.arpa 那幾行，就是它
收尾
# 15. 刪掉本課練習資源（client pod 也一起結束）
kubectl delete deployment hello
kubectl delete svc hello ghost
kubectl delete ns team-a
kubectl delete pod client

# 16. 課末確認：叢集乾淨、雙節點
kubectl get pods,svc
kubectl get nodes
考場小抄

① FQDN 樣板：<svc>.<ns>.svc.cluster.local；同 namespace 可用短名（search 幫你補）。② 除錯兩層：nslookup 名字（DNS 層）→ get endpoints（後端層）→ 再看 Pod。③ DNS 有回應不代表服務能用：NXDOMAIN＝名字錯；解析成功但連不上＝後端空或 NetworkPolicy。④ 進 pod 看設定：cat /etc/resolv.conf（nameserver 應是 kube-dns）。⑤ headless 的 A record 直接回 Pod IP 群。⑥ CoreDNS 設定檔在 ConfigMap/coredns（Corefile）。

本課戰果

  • 你背下 Service FQDN 樣板，並用短名／全名／跨 namespace 三種方式解析成功。
  • 你親手製造「NXDOMAIN」與「Endpoints 空」兩種故障，建立 DNS 層與後端層的分層除錯。
  • 你找到 CoreDNS 的 Pod、kube-dns Service 與 Corefile ConfigMap。
