Ingress 與 Gateway API：L7 路由

0009 的 NodePort 已經能把流量從外部帶進來，但它是「IP:Port」等級——每支服務都要記一個 port，也不是一般人能懂的網址。本課把入口升級到第七層（HTTP）：Ingress 讓你用「網址（host）+ 路徑（path）」把外部流量路由到不同的 Service，例如 example.com/foo → 服務 A、example.com/bar → 服務 B。同場加映概念級認識 Gateway API（考綱點名、但 CKA 只考到概念）。

本課先重建叢集（一次性）

Ingress Controller 要接收「從 host 進來的 80/443」，必須在 kind 建叢集時把節點的 80/443 mapping 到 host——舊叢集（0005–0010）沒有這個設定，所以重建。重建會清掉所有練習物件，也洗掉 0007 裝的 metrics-server（沒關係，0019 開場會補裝）。課末別刪這個叢集——下一課會把整座叢集刪掉重建、改裝 Calico（換 CNI），屆時再見。

L7 vs L4：一個認網址、一個認 port

Service（L4，0009）Ingress（L7，本課）
看什麼 IP + port（TCP/UDP） HTTP host、path、headers
誰來路由 kube-proxy 的規則 Ingress Controller（一支真正跑 HTTP server 的 Pod）
典型用法 叢集內呼叫、TCP/UDP 服務 對外 HTTP/HTTPS 服務、網址路由

Ingress 三件套：資源、類別、控制器

Ingress 機制由三個角色組成，缺一不可：

  • Ingress（資源）：你宣告「哪個 host＋path 轉到哪個 Service」的規則——它只是一份資料。
  • Ingress Controller（控制器）：真正跑在叢集裡的程式（我們用 ingress-nginx，一隻 nginx）。它 watch Ingress 資源，把規則翻譯成自己的設定並實際收流量。
  • IngressClass（類別）：把「Ingress 資源」連結到「Controller」的接頭——一個叢集可以同時有多家 Controller（nginx、traefik…），Ingress 用 ingressClassName 指名要用哪一家。
三者關係一句話
Ingress（規則：/foo → foo-svc）───ingressClassName───> IngressClass（nginx）
                                                        │ 指向
                                                        ▼
                              Ingress Controller（實際收流量的 nginx Pod）

實作：重建帶 host port 的叢集

重建 ingress-ready 叢集
# 1. 先看舊叢集（0005–0010 用下來的雙節點）
kubectl get nodes
kind delete cluster

# 2. 建立新設定檔 kind-ingress.yaml（control-plane 標上 ingress-ready，
#     並把節點 80/443 mapping 到 host 的 80/443）
nano kind-ingress.yaml
kind-ingress.yaml 全文
# kind-ingress.yaml — 0001 的雙節點設定 + ingress-ready 三行
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  kubeadmConfigPatches:
  - |
    kind: InitConfiguration
    nodeRegistration:
      kubeletExtraArgs:
        node-labels: "ingress-ready=true"
  extraPortMappings:
  - containerPort: 80
    hostPort: 80
    protocol: TCP
  - containerPort: 443
    hostPort: 443
    protocol: TCP
- role: worker
建叢集並驗證 label
# 3. 建立（約 2 分鐘）
kind create cluster --config kind-ingress.yaml
kubectl get nodes

# 4. 確認 control-plane 掛著 ingress-ready=true（kubelet 註冊時打的 label）
kubectl get nodes --show-labels

實作 A：安裝 Ingress Controller

安裝 ingress-nginx（kind 專用 manifest，v1.15.1 釘版）
# 5. 官方 kind provider manifest（一次建好 Namespace/RBAC/Deployment/IngressClass…）
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller

# 6. 控制器 Pod 一定要在 kind-control-plane 上——host 的 80/443 只 mapping 給它
kubectl -n ingress-nginx get pods -o wide

# 7. 這份 manifest 沒有釘節點，控制器常會落在 kind-worker——若如此，
#    用 0005 的 nodeSelector 把它釘回 control-plane（ingress-ready label 只有它）
kubectl -n ingress-nginx patch deployment ingress-nginx-controller --type=json -p '[{"op":"replace","path":"/spec/template/spec/nodeSelector","value":{"ingress-ready":"true","kubernetes.io/os":"linux"}}]'
kubectl -n ingress-nginx rollout status deployment/ingress-nginx-controller
kubectl -n ingress-nginx get pods -o wide

# 8. 看這個 manifest 幫你建好的 IngressClass（名字叫 nginx）
kubectl get ingressclass
你該觀察到什麼

第 5 步的 manifest 一次建好了「控制器 + IngressClass」：以後寫 Ingress 只要 ingressClassName: nginx 就自動接到它。第 7 步把 0005 的 nodeSelector 派上用場——這份 manifest 沒釘節點，控制器常落在 worker，而 host port 只 mapping 在 control-plane，所以多半要自己補第 7 步把控制器釘回去（真實世界叫「把工作負載釘到特定節點」）。

# 11. 從 WSL2 host 直接 curl localhost——路徑分流生效
curl localhost/foo
#    回應 foo-app（那一支 Pod 的 hostname）
curl localhost/bar
#    回應 bar-app

# 12. 沒被任何 path 接到的地方：404（控制器預設的 not-found）
curl -i localhost/
你該觀察到什麼

第 11 步是「L7 路由」的全部意義：同一台 localhost:80，靠「路徑」分別送到兩支不同的 Service。回到 0009 你會發現這件事 NodePort 做不到——NodePort 一個 port 只能對一支服務。第 12 步的 404 來自控制器自己，代表流量有到控制器、只是沒規則匹配。

在 WSL2 curl localhost 不通？改用 Windows 端（PowerShell）的 curl http://localhost/foo，或檢查 Docker Desktop 是否把 port 80 綁定成功。

實作 C：Ingress 加 TLS（https）

Ingress 的 TLS 很簡單：TLS 憑證是「Secret」，Ingress 引用 Secret 就自動終止 TLS（pod 內部還是 http）。

自簽憑證 → Secret
# 13. openssl 產生自簽憑證（demo.local 當測試網域；-nodes 指不加密私鑰）
openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout tls.key -out tls.crt -subj "/CN=demo.local"

# 14. 包成 type=kubernetes.io/tls 的 Secret（cert/key 兩把鑰匙給齊）
kubectl create secret tls demo-tls --cert=tls.crt --key=tls.key
kubectl get secret demo-tls
ingress-tls.yaml — host + tls 兩段加進去
# ingress-tls.yaml — tls 段：憑證給 demo-tls，只對 demo.local 這個 host 生效
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tls-ingress
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - demo.local
    secretName: demo-tls
  rules:
  - host: demo.local
    http:
      paths:
      - path: /foo
        pathType: Prefix
        backend:
          service:
            name: foo-svc
            port:
              number: 8080
套用並用 https 打
# 15. 套用後，--resolve 把 demo.local 指到 127.0.0.1（我們沒有真的 DNS）；-k 略過自簽警告
nano ingress-tls.yaml
kubectl apply -f ingress-tls.yaml
curl -k --resolve demo.local:443:127.0.0.1 https://demo.local/foo
#    回應 foo-app——這次是走 HTTPS 進來的
收尾與課末狀態
# 16. 清掉示範應用（叢集本身保留給 0012 換 CNI）
kubectl delete -f ingress.yaml -f ingress-tls.yaml
kubectl delete -f app.yaml
kubectl delete secret demo-tls
rm -f tls.key tls.crt app.yaml ingress.yaml ingress-tls.yaml
kubectl get ingress,svc,pods

Gateway API：Ingress 的下一代（概念）

Gateway API 是官方正在推的下一代流量 API（ingress 的演化）。它把「入口」拆成更細的角色與 CRD：GatewayClass（類似 IngressClass）、Gateway（實際的入口點，如 LB）、HTTPRoute（路由規則，可跨 namespace 引用後端）。優點：更具表達力（headers 路由、權重分流、跨 namespace）、也更適合多個團隊共用一個入口。CKA 考綱點名它，但概念理解即可，不需要背 YAML。

考場小抄

① 三件套：Ingress＝規則資料、IngressClass＝指名哪家控制器、Ingress Controller＝真正收流量那隻 Pod——ADDRESS 空著通常代表 Controller 沒起來。② kubectl get ingress 看 ADDRESS（kind 會是 localhost）與 describe ingress 看規則。③ TLS：憑證存成 kubernetes.io/tls Secret（key：tls.crt/tls.key），Ingress 的 tls.secretName 引用即可。④ pathType 用 Prefix 就夠應付九成考題；host 與 path 都可省略（都省略＝全部流量）。⑤ Ingress 規則與後端 Service 要在同 namespace，除非用 Gateway API。⑥ 出問題先分層：host 通不通 → controller pod 在不在 → ingress 規則 → endpoints（0009–0010 的舊招）。

  • 你重建了一個 ingress-ready 叢集（host 80/443 → 節點），並裝好 ingress-nginx（v1.15.1）。

  • 你用自簽憑證 + TLS Secret，讓 Ingress 終止 HTTPS。
  • 你建立 Ingress／IngressClass／Ingress Controller 三件套的心智模型，並認識 Gateway API 的位置。
