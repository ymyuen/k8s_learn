DaemonSet 與 Job（Deployment 做不到的場景）

到目前為止你學的 Deployment，本質是「隨時維持 N 顆、永不結束」的長期服務——它管副本數、換版本、自我修復，Pod 永遠在跑。但有兩種常見場景它做不到：每台節點都要一顆（日誌收集、監控 agent、CNI 網路外掛），以及跑完就結束（批次任務）。本課的主角就是為這兩種場景而生的 DaemonSet 與 Job，最後用幾分鐘認識定時版的 Job——CronJob。它們全部沿用 0003 的「label selector 認人」機制：控制器只認標籤符合條件的 Pod，誰管誰還是靠 selector。

四控制器：誰在什麼時候補 Pod？

把 0001–0003 學過的 Deployment 放進更大的版圖：控制器之間最大的差別，就是「什麼情況會觸發它補 Pod」。

控制器何時補 Pod典型場景
Deployment 副本數不足時（補數量） Web／API 等長期服務
DaemonSet 有節點需要時（每節點一顆） 日誌收集、監控 agent、CNI
Job 任務失敗時（補失敗、不補成功） 批次任務、一次性初始化
CronJob 時間到時（定時生一個 Job） 定時備份、定期清理

一句話記法（之後直接背這個）：Deployment 補數量、DaemonSet 補節點、Job 補失敗、CronJob 補時間。

DaemonSet：每台節點一顆

DaemonSet（簡寫 ds）的期望狀態不是「N 顆」，而是「每台節點剛好一顆」：叢集新增節點，它自動在那台長一顆；節點被移走，那顆就跟著收掉。你可能早就用著它而不自知——kube-system 裡的 kindnet（CNI）與 kube-proxy 都是 DaemonSet，因為「網路服務」每台節點都必須有。控制器鏈是 DaemonSet → Pod，沒有中間的 ReplicaSet。它的運作方式與你在 0003 問過的機制同一條路：DaemonSet 控制器 watch apiserver 的節點事件，收到節點加入或離開就重新 reconcile。

CKA 重點：DaemonSet 沒有 create 指令

kubectl create daemonset 不存在——kubectl 只為少數物件提供 create 指令（deployment、job、namespace…）。想建 DaemonSet 只能寫 YAML，這是 CKA 愛考的情境。記得 0003 的規則：selector.matchLabels 必須與 template 的 labels 一致，否則 apiserver 直接拒絕（錯誤訊息 selector does not match template labels）。

實作 A：重建雙節點叢集 + 自訂 DaemonSet

單節點叢集看不到「每節點一顆」的意義。本課先把叢集重建回 0001「選配」教過的雙節點版（control-plane + worker）。

重建前先知道

kind delete cluster 會把現有叢集整個刪掉——0002/0003 練習的物件會一併消失，沒關係。重建約需 2 分鐘，kind 會自動更新 kubeconfig，重建後 kubectl 直接可用。本課結束後不要刪掉這個雙節點叢集，後續資源與排程課要用。

開一個 PowerShell 新視窗，建個練習資料夾，並用記事本建立設定檔（貼上存檔即可）：

- role: control-plane

重建為雙節點叢集
# 1. 先確認目前只有一台節點（kind 單節點的預設）
kubectl get nodes

# 2. 刪掉舊叢集
kind delete cluster

# 3. 用雙節點設定檔重建（約 2 分鐘）
kind create cluster --config kind-config.yaml

# 4. 這次應該有兩台：kind-control-plane 與 kind-worker
kubectl get nodes

# 5. 看 kube-system 的現成 DaemonSet——DESIRED/CURRENT 從 1 變成 2
kubectl get ds -n kube-system
你該觀察到什麼

第 5 步的 kindnet 與 kube-proxy，DESIRED、CURRENT、READY 都是 2——我們什麼都沒做，DaemonSet 就自動在新增的 worker 節點上各長了一顆。這就是「每節點一顆」：不是設定副本數，是節點數決定了 Pod 數。

現在動手寫自己的 DaemonSet。注意 selector.matchLabels 與 template 的 labels 都是 app: node-monitor——不一致會被 apiserver 拒絕。

ds.yaml（記事本貼上這份內容存檔）
# ds.yaml — 每台節點都跑一個監控 agent
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-monitor
spec:
  selector:
    matchLabels:
      app: node-monitor
  template:
    metadata:
      labels:
        app: node-monitor
    spec:
      containers:
      - name: agent
        image: busybox:1.36
        command: ["sh", "-c", "echo agent on $(hostname); sleep 3600"]
套用並驗證「每節點一顆」
# 6. 用記事本建檔（內容貼上方那份）
notepad ds.yaml

# 7. 套用 DaemonSet
kubectl apply -f ds.yaml

# 8. -o wide 看 NODE 欄：兩顆 Pod 各在一台節點
kubectl get pods -o wide -l app=node-monitor

# 9. 看 DS 狀態：DESIRED/CURRENT/READY 都是 2
kubectl get ds

# 10. 刪掉其中一顆（尾碼隨機）——DS 版的自我修復
kubectl delete pod node-monitor-(隨機尾碼)

# 11. -w 觀察：同台節點立刻補一顆新的（尾碼變了；Ctrl+C 離開）
kubectl get pods -o wide -l app=node-monitor -w

# 12. 確認 READY 回到 2 之後，收尾刪掉 DS
kubectl get ds
kubectl delete ds node-monitor
你該觀察到什麼

第 10–11 步是 DaemonSet 版的自我修復，但方向跟 Deployment 不同：Deployment 補回「少掉的數量」；DaemonSet 補回「少掉的節點」——所以新 Pod 會出現在被你刪掉的那一顆原本所在的節點，維持每節點一顆。第 8 步的 NODE 欄正是這堂課最想讓你看見的東西。

Job：跑完就結束的控制器

Deployment 的 Pod「永遠不該結束」；Job 的 Pod 則生來就是要結束的。Job 的期望狀態是「成功跑完 completions 次」，而不是「一直有 N 顆」：

  • completions：總共要成功幾次（預設 1）。
  • parallelism：同時最多跑幾顆（預設 1）。
  • backoffLimit：失敗重試上限（預設 6）。
  • restartPolicy：只能是 Never 或 OnFailure——不能是 Always（跟 Deployment 最大的語法差別，因為「跑完重開機」對 Job 沒意義）。

Job 的自我修復口訣是「補失敗、不補成功」：Pod 失敗了就換一顆重試；任務一旦成功，那顆 Pod 保持 Completed 狀態、不再重啟——這正是與 Deployment 的最大差異。用 kubectl create job 就能快速建最簡單的 Job——但它只有 --image 與 --from 兩個專屬旗標；completions／parallelism 是 spec 欄位、沒有對應旗標，必須用 YAML 設定（實作 B 會練這套工作法，也是 CKA 陷阱）。

YAML 工作法：dry-run 產出再存檔（CKA 核心）
# 20. --dry-run=client -o yaml：先印出 YAML（不真正建立）
kubectl create job yaml-demo --image=busybox:1.36 --dry-run=client -o yaml -- echo hi

# 21. 輸出改存成 job.yaml（PowerShell 寫法；見下方 warn）
kubectl create job yaml-demo --image=busybox:1.36 --dry-run=client -o yaml -- echo hi | Out-File job.yaml -Encoding utf8

# 22. 用記事本打開檢查（可看到 apiVersion: batch/v1），改好再套用
notepad job.yaml
kubectl apply -f job.yaml

# 23. yaml-demo 也完成了
kubectl get jobs
PowerShell 陷阱：`>` 存成 UTF-16

在 Windows PowerShell 用 kubectl ... > job.yaml 存檔，會寫成 UTF-16，kubectl 讀不到（報錯：error converting YAML to JSON）。所以上面第 21 步改用 | Out-File job.yaml -Encoding utf8。考場是 Linux/WSL2，可直接用 kubectl ... > job.yaml——養成習慣：在 PowerShell 一律用 Out-File。

completions 與 parallelism：用 YAML 設定批次任務
# 24. 先印出 YAML——注意 dry-run 輸出裡沒有 completions／parallelism（它們是 spec 欄位，不是旗標）
kubectl create job multi --image=busybox:1.36 --dry-run=client -o yaml -- sh -c 'echo task; sleep 5'

# 25. 同一支指令改存成 multi.yaml（create job 沒有 --completions／--parallelism 旗標）
kubectl create job multi --image=busybox:1.36 --dry-run=client -o yaml -- sh -c 'echo task; sleep 5' | Out-File multi.yaml -Encoding utf8

# 26. 記事本打開，在 spec: 底下、template: 上面加兩行（縮排與 template: 相同，都是兩格）
#     completions: 3   ← 總共要成功 3 次
#     parallelism: 2   ← 最多同時 2 顆
notepad multi.yaml

# 27. 套用後：Job 先同時跑 2 顆，完成的空位會補新任務
kubectl apply -f multi.yaml

# 28. -w 觀察：先 2 顆並行，完成的空位會補新任務（Ctrl+C 離開）
kubectl get pods -w

# 29. 全部成功：COMPLETIONS 3/3
kubectl get jobs
多顆 Pod 的 Job 要看全部日誌？

第 29 步的 multi 有三顆 Pod。想抓整個 Job 的日誌時，kubectl logs job/multi 預設只挑一顆，並提示 Found 3 pods, using pod/multi-...。想看所有 Pod 的輸出、而且每行標明是哪一顆 Pod 來的，加 --all-pods=true：kubectl logs job/multi --all-pods=true。

失敗重試：Job 補失敗、不補成功
# 30. 一支注定失敗的任務（exit 1）
kubectl create job fail --image=busybox:1.36 -- sh -c 'exit 1'

# 31. 列 Pod：Job 一直換新 Pod 重試，每顆都以失敗收場
kubectl get pods

# 32. 看重試紀錄（Events 有 Backoff）；看到換了 2–3 顆就夠了
kubectl describe job fail

# 33. 不繼續等了——backoffLimit 預設 6 會重試很久。直接刪掉
kubectl delete job fail
為什麼步驟 33 不等它自然結束？

Job 的重試間隔是指數退避：10s → 20s → 40s → 80s → 160s → 320s（單次上限 6 分鐘）。backoffLimit 預設 6——要等這 6 次失敗全部吃完，Job 才標成 Failed，合計約 10 分鐘以上。所以步驟 33 直接刪掉，不陪它等。考場想快速看到 Job 自然失敗結束：在 YAML 的 spec: 加 backoffLimit: 0，第一顆失敗就結案。

執行中的 Job Pod 被刪掉呢？

上面看到「已完成的 Pod 刪了不補」。反過來，如果刪的是還在執行中的 Job Pod，Job 會補一顆新的續跑（任務還沒完成）。想親眼驗證：先 kubectl delete job multi，把 multi.yaml 的 sleep 5 改成 sleep 60，再 kubectl apply -f multi.yaml——趁它跑的時候開第二個終端機刪一顆 Pod，再看 kubectl get pods -w，新 Pod 會接手。看完記得 kubectl delete job multi。

收尾：刪掉本課所有 Job
# 34. 收尾：刪掉本課所有 Job（hello/yaml-demo/multi/fail 與它們的 Pod）
kubectl delete jobs --all

CronJob：時間到就生一個 Job

Job 的定時版就是 CronJob（cronjob/cj）：它不直接生 Pod，而是照 cron 的五欄排程（分 時 日 月 週）定時建立一個 Job——所以是一條更長的控制器鏈：CronJob → Job → Pod。適合定時備份、定期清理這類工作。

實作 C：每分鐘跑一次的 CronJob（迷你版）
# 35. 建立每分鐘執行一次的 CronJob（schedule 用雙引號包住）
kubectl create cronjob minute --image=busybox:1.36 --schedule="*/1 * * * *" -- date

# 36. 看 SCHEDULE（LAST SCHEDULE 還是 <none>）
kubectl get cronjob

# 37. 等 1–2 分鐘到整分，會出現 minute-xxxxx 的 Job——時間到，CronJob 生了一個 Job
kubectl get jobs

# 38. 收尾：刪 CronJob（已產生的 Job/Pod 不會自動消失，一起清掉）
kubectl delete cronjob minute
kubectl delete jobs --all
你該觀察到什麼

第 37 步的 minute-xxxxx 就是「時間到了，CronJob 幫你 create 的那個 Job」——它又走一遍 Job 的流程：生 Pod、跑 date、完成後保持 Completed。三層控制器各管各的：CronJob 管時間、Job 管完成、Pod 管執行。

每分鐘一顆，Completed 的 Job 不會越堆越多嗎？

不會。CronJob 會自動回收超過上限的已完成 Job：successfulJobsHistoryLimit 保留最近幾顆成功的（預設 3）、failedJobsHistoryLimit 保留最近幾顆失敗的（預設 1）——新的一顆生出來，最舊的就連 Pod 一起被控制器刪掉，所以 kubectl get jobs 不會越列越長。

想自訂要放對層：這兩個歷史欄位寫在 CronJob 的 spec:（jobTemplate 外面）；想讓 Job 跑完後自動倒數刪除，用 ttlSecondsAfterFinished，寫在 jobTemplate.spec:（跟 backoffLimit 同層）。兩者都不是 pod template 的欄位——口訣：誰的欄位就放誰的 spec。想完全不保留歷史，把兩個 historyLimit 都設 0。

CronJob 跑完的日誌會保留嗎？

日誌跟著 Pod，不跟著 CronJob/Job 物件——kubectl logs 讀的是節點上 container runtime 的檔案。所以日誌壽命 = Job/Pod 的壽命：在 historyLimit 留住的窗口內（成功 3、失敗 1），kubectl logs job/minute-xxxxx 查得到；Job 一被回收，Pod 連日誌一併消失。

想留更久：① 治標——調大 historyLimit 或 ttlSecondsAfterFinished 延長物件壽命；② 正解——外部集中日誌（Loki、EFK、雲端方案），k8s 本身不保存歷史日誌。考場觀念：刪 Job = 連 Pod 一起刪 = 日誌沒了，要撈趁物件還在。

考場小抄

五個必背反射動作：① DaemonSet 沒有 create daemonset，只能寫 YAML——趕時間時可先 kubectl create deployment 用 --dry-run=client -o yaml 產出，再把 kind 改成 DaemonSet、拿掉 replicas。② create job 只有 --image／--from——沒有 --completions／--parallelism；批次欄位用 --dry-run=client -o yaml 產出 YAML 加上去再 apply。③ Job 日誌：kubectl logs job/NAME——多顆 Pod 時加 --all-pods=true 一次看全部。④ Job 卡住排查：kubectl describe job NAME 配 kubectl get pods -l job-name=NAME；想讓必失敗的 Job 快速結案，YAML 設 backoffLimit: 0。⑤ 四控制器口訣：Deployment 補數量、DaemonSet 補節點、Job 補失敗、CronJob 補時間。
