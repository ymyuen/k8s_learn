ConfigMap 與 Secret：把設定從映像抽出來

0005 學會讓 Pod「放得下、放對地方」；本課處理 Pod 的「內容物」：設定。把設定寫死在 Dockerfile 裡（ENV、config 檔）會逼你為每個環境各做一個映像——dev 一個、prod 一個，改個密碼就要重 build。Kubernetes 的答案是把設定抽成獨立物件，讓同一個映像到處用、設定隨環境換。兩個物件登場：ConfigMap（非機密設定）與 Secret（機密資料）。兩者都是 namespace 層級、上限約 1MiB 的小型鍵值／檔案庫。

ConfigMap vs Secret：機密與非機密

ConfigMapSecret
裝什麼 非機密設定（環境名稱、URL、開關） 機密資料（密碼、Token、憑證）
值的呈現 明文 base64 編碼（不是加密！）
讀取方式 describe 直接看得到內容 describe 只顯示位元組數
預設檔案權限 0644 0644（與 ConfigMap 相同；想收緊可設 defaultMode: 0400）
必背：base64 ≠ 加密

Secret 的 data 用 base64 編碼，只是為了讓值能放進 YAML（可含任意字元）。任何人只要對叢集有讀取權限，kubectl get secret -o yaml 再 base64 -d 就能還原——Secret 不是加密機制。考試常見陷阱題：有人以為 base64 就是加密。真的加密（etcd 加密、外部 KMS）是另一回事，CKA 只考到「知道它不加密」。

兩種注入路徑：環境變數 vs 檔案掛載

ConfigMap／Secret 自己不會做事，要注入到 Pod 才有意義。兩條路差別在於「更新後誰會變」：

  • env（環境變數）：env.valueFrom.configMapKeyRef／secretKeyRef 取「單一鍵」，或 envFrom 一次灌「整包」。容器啟動時就定死——之後改設定，跑中的容器不會更新。
  • volume（檔案掛載）：把每個鍵變成一個檔名、值變成檔內容。kubelet 週期同步，改設定後約 1 分鐘內檔案會自動更新（不用重啟 Pod；應用要自己偵測檔案變化）。

選擇直覺：要重啟才生效的用 env；想熱更新的用 volume。本課叢集沿用 0005 的雙節點、無殘留。

實作 A：ConfigMap 兩種注入

建立 ConfigMap 並檢視
# 1. --from-literal 一次帶多鍵（key=value 一一列出）
kubectl create configmap app-config --from-literal=APP_ENV=prod --from-literal=LOG_LEVEL=info

# 2. DATA 欄顯示有幾個鍵
kubectl get configmaps

# 3. describe 直接讀回明文內容
kubectl describe configmap app-config
pod-env.yaml — envFrom 整包注入
# pod-env.yaml — 用 envFrom 把整包 configmap 灌成環境變數
apiVersion: v1
kind: Pod
metadata:
  name: env-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    envFrom:
    - configMapRef:
        name: app-config
套用並進容器驗證
# 4. 用 nano 寫好上面那份後套用
nano pod-env.yaml
kubectl apply -f pod-env.yaml
kubectl get pod env-demo

# 5. exec 進去看環境變數——每把 key 都是一個環境變數
kubectl exec env-demo -- sh -c 'env | grep -E "APP_ENV|LOG_LEVEL"'
pod-vol.yaml — 同一個 ConfigMap 掛成檔案
# pod-vol.yaml — 把 configmap 掛成 /etc/config 下的檔案
apiVersion: v1
kind: Pod
metadata:
  name: vol-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: cfg
      mountPath: /etc/config
  volumes:
  - name: cfg
    configMap:
      name: app-config
套用、觀察鍵變檔名，再改設定看傳播延遲
# 6. 套用後等待 Running
nano pod-vol.yaml
kubectl apply -f pod-vol.yaml
kubectl get pod vol-demo

# 7. 掛載的樣貌：每個鍵是一個檔名，內容是它的值
kubectl exec vol-demo -- ls /etc/config
kubectl exec vol-demo -- cat /etc/config/APP_ENV

# 8. 改 ConfigMap：APP_ENV 改成 staging（dry-run 產 YAML 再 apply，0004 的老朋友）
kubectl create configmap app-config --from-literal=APP_ENV=staging --from-literal=LOG_LEVEL=debug --dry-run=client -o yaml | kubectl apply -f -

# 9. 立刻 cat——還是 prod；kubelet 週期同步不是即時的
kubectl exec vol-demo -- cat /etc/config/APP_ENV

# 10. 等約 1 分鐘再 cat——變 staging 了
kubectl exec vol-demo -- cat /etc/config/APP_ENV
你該觀察到什麼

第 7 步看到 volume 注入的「樣貌」：鍵變成檔名。第 8–10 步是關鍵對比——改 ConfigMap 不會自動重啟任何 Pod，但掛載它的 volume 會被 kubelet 週期同步（約 1 分鐘）。對照：env-demo（env 注入）的環境變數永遠停在啟動那一刻的值，就算 ConfigMap 改了也不動。

Secret：一模一樣的玩法，多了 base64

Secret 的建立、注入路徑與 ConfigMap 幾乎全同，差別在「值以 base64 存在 data」。建立 Secret 有兩種寫法：--from-literal（值直接給明文，kubectl 幫你編碼）與 YAML 的 stringData（寫明文字串、儲存時自動轉成 data）。

建立 Secret、看 base64、解碼驗證
# 11. 建立 Secret（generic 型別；值用單引號包住防 shell 解讀特殊字元）
kubectl create secret generic db-secret --from-literal=DB_USER=admin --from-literal='DB_PASSWORD=s3cr3t!'

# 12. data 的值是 base64——印出來對照一下
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}'

# 13. 直接解碼驗證還原（管線：jsonpath 輸出 → base64 -d）
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d

# 14. describe：不顯示內容，只顯示幾個位元組——安全設計
kubectl describe secret db-secret
secret.yaml — stringData 寫明文、存檔變 data
# secret-plain.yaml — stringData 裡可以直接寫明文
apiVersion: v1
kind: Secret
metadata:
  name: db-plain
type: Opaque
stringData:
  DB_PASSWORD: hunter2
套用並觀察 stringData → data 的轉換
# 15. 套用後讀回：stringData 已經被轉成 data 的 base64
nano secret-plain.yaml
kubectl apply -f secret-plain.yaml
kubectl get secret db-plain -o yaml

# 16. 用 --from-literal 建的那顆，data 長得一樣（值來源不同，儲存形式相同）
kubectl get secret db-secret -o yaml
pod-secret.yaml — Secret 掛成檔案（預設 0644）
# pod-secret.yaml — 用 valueFrom 取單一鍵當 env，再把整顆 secret 掛成檔案
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: DB_USER
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: DB_USER
    volumeMounts:
    - name: db
      mountPath: /etc/db
  volumes:
  - name: db
    secret:
      secretName: db-secret
套用並驗證：環境變數與唯讀檔案
# 17. 套用後進容器驗證兩種注入
nano pod-secret.yaml
kubectl apply -f pod-secret.yaml
kubectl get pod secret-demo

# 18. env 那路：valueFrom.secretKeyRef 取的單一鍵
kubectl exec secret-demo -- sh -c 'echo $DB_USER'

# 19. volume 那路：檔名 = 鍵名；-l 看權限是 -rw-r--r--（0644，與 ConfigMap 相同）
kubectl exec secret-demo -- ls -l /etc/db
kubectl exec secret-demo -- cat /etc/db/DB_PASSWORD
你該觀察到什麼

第 19 步的 ls -l 會看到 -rw-r--r--：Secret 掛載成檔案的預設權限是 0644（跟 ConfigMap 一樣，同 namespace 內的人都能讀）。想讓只有 root 能讀，就在 volume 寫 defaultMode: 0400——「Secret 預設 0444」是流傳很廣的誤解，考試別踩。掛成檔案真正的價值是讓「程式啟動時才讀密碼」。

defaultMode: 0400 的陷阱：app 用什麼身份跑？

kubelet 掛載 Secret 檔案時，擁有者固定是 root:root。所以 defaultMode: 0400（-r--------）影響的只有「非 root 身份跑的容器」：

  • 容器以 root 跑（busybox 等多數映像的預設）→ 不影響，app 照常讀得到。
  • 容器以非 root 跑（securityContext.runAsUser，或映像本身 USER 1000，如 nginx-unprivileged、postgres）→ 連讀都不能讀（Permission denied），通常啟動就 crash。

背景知識：Unix 檔案權限分三組身份——owner／group／others，核心檢查時只套用命中的那一組（r=4、w=2、x=1）。以 0440（r--r-----）為例：

0440 = r-- r-- ---誰結果
owner（r--）uid 0（root，檔案擁有者）可讀（root 另有 DAC_OVERRIDE，無視所有位元）
group（r--）uid 1000＋補充群組 2000（fsGroup 辦的）——你的 app 走這條可讀
others（---）uid 3000、不在群組 2000Permission denied

非 root 的正解＝fsGroup＋群組可讀：fsGroup: 2000 讓 kubelet 做兩件事——把檔案的 gid 改成 2000，同時把 2000 加進容器程序的補充群組。app（uid 1000）不是 owner，卻透過「群組成員」命中第二組位元拿到讀取權；不相干身份一律落在 others 被擋。另兩個小點：① Secret volume 本來就唯讀（更新由 kubelet 換檔），拿掉 write 位元對 app 沒額外影響；② defaultMode 套用整顆 volume，只想改單一鍵用 items[].mode。

pod-secret-hardened.yaml — 非 root 讀 Secret 的正解
# pod-secret-hardened.yaml — 非 root ＋ fsGroup ＋ 0440：app 讀得到、別人讀不到（參考寫法，不動本課步驟）
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo-hardened
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000            # kubelet：檔案 gid 改成 2000 ＋ 2000 加進程序補充群組
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: db
      mountPath: /etc/db
  volumes:
  - name: db
    secret:
      secretName: db-secret
      defaultMode: 0440      # -r--r-----：owner(root) 與群組(2000)可讀，others 不可

實作 C：把指令式建立的設定，轉成宣告式 YAML

課堂到目前為止都用 kubectl create configmap/secret（指令式）求快。收尾練習把它們「轉正」成可進版控的 YAML——先用 dry-run 產出、kubectl apply 套用，跟 0004 學的 Job 工作法同一套：

dry-run 產 YAML → apply 宣告式套用
# 20. 把 app-config 的「現況」導成 YAML 存檔（-o yaml 可接已存在的物件）
kubectl get configmap app-config -o yaml > app-config.yaml

# 21. 宣告式重建：先刪再 apply（kubectl apply 管的是「檔案」這份宣告）
kubectl delete configmap app-config

考場小抄

① 建立：kubectl create configmap NAME --from-literal=k=v／--from-file=path；Secret 同理（create secret generic）。② 注入三方式：整包 envFrom、單鍵 valueFrom.xxxKeyRef、掛檔 volume——三者的寫法差一個字元都要背熟。③ 更新行為：env 不更新、volume 約 1 分鐘內同步。④ 必背陷阱：Secret 的 base64 不是加密；describe secret 只看得到大小。⑤ 大小上限約 1MiB、namespace 層級。⑥ 從現有物件導 YAML：kubectl get cm/secret NAME -o yaml。

本課戰果

  • 你能用 --from-literal 建立 ConfigMap 與 Secret，並說出兩者的儲存差異（明文 vs base64）。
  • 你能用 envFrom／valueFrom／volume 三種方式注入設定，並理解「env 不熱更新、volume 約 1 分鐘同步」。
  • 你親眼看到 stringData 在儲存時轉成 data 的 base64，也驗證過 Secret 掛載的預設權限（0644）與收緊方法（defaultMode）。
  • 你學會用 get -o yaml／dry-run 把設定物件轉成宣告式 YAML 進版控。
