Phase 2 · 對應考綱：Storage（10%） · 需時約 25 分鐘

儲存三層：PV、PVC 與 StorageClass

前面七課，你的 Pod 都是「無狀態的」——容器一重啟，寫在容器檔案系統裡的東西就沒了。本課把 Phase 2 收尾在資料面：Kubernetes 的儲存抽象。PV（PersistentVolume，實際的磁碟）、PVC（PersistentVolumeClaim，你要的磁碟）、StorageClass（造磁碟的工廠）三層分工，讓「容器會死」與「資料要活」並存。Storage 佔考綱 10%，但 PV/PVC 是 Troubleshooting 常見情境的底層原因。本課叢集沿用 0007：雙節點、metrics-server 在位。

三層分工：誰擁有、誰使用、誰製造

層級是什麼比喻
PV
PersistentVolume		 實際的儲存空間（NFS、雲端磁碟、hostPath…），叢集資源、不屬於任何 namespace 倉庫裡「已經買好」的一格貨架
PVC
PersistentVolumeClaim		 「我要 1Gi、可讀寫一次」的請求單；有 namespace。K8s 幫你找一個符合的 PV 綁起來 你填的「我要一格」申請表
StorageClass
（儲存類別）		 「動態供應」的工廠：PVC 一來，就照參數幫你現做一個 PV 依訂單現產貨架的廠商

Pod 永遠只認識 PVC（persistentVolumeClaim.claimName），不直接碰 PV——分界線很清楚：開發者寫 PVC，管理者管 PV，StorageClass 自動補貨。

存取模式與回收策略

存取模式縮寫意義
ReadWriteOnceRWO單一節點可讀寫（最常見；多 Pod 同節點可共用）
ReadOnlyManyROX多節點唯讀
ReadWriteManyRWX多節點可讀寫（NFS 等共享儲存才支援）

PV 被釋放後怎麼處理，由 persistentVolumeReclaimPolicy 決定：Retain（保留磁碟，PV 變 Released、等人清）與 Delete（連底層儲存一起刪掉，雲端磁碟的常見設定）。口訣：Delete 是「PVC 一刪，PV 連本帶利還給雲」；Retain 是「磁碟留下，系統管理員自己收拾」。

把「儲存檔案」的一生畫一遍
PVC（我要 1Gi）───> StorageClass 工廠（dynamic provisioning）
                        │ 現做一個底層磁碟
                        ▼
                   PV 綁給 PVC（Bound）
                        │ Pod 透過 PVC 掛載使用
                        ▼
                PVC 刪除 ──> 依 ReclaimPolicy：
                            Delete → PV 一起消失
                            Retain → PV 變成 Released 等人接手

實作 A：動態供應——PVC 一張單，PV 自動來

kind 預設內建一個 StorageClass（local-path provisioner 提供，類別名叫 standard），所以「動態供應」開箱即用。

看看 kind 的 StorageClass
# 1. 內建 SC：PROVISIONER 是 rancher.io/local-path，RECLAIMPOLICY 是 Delete
kubectl get storageclass
#    standard（default）是 WaitForFirstConsumer——第一次有 Pod 要用才真正綁 PV
pvc.yaml — 一張「我要 1Gi」的申請單
# pvc.yaml — 不指定 storageClassName，就會用 default 的 standard 動態供應
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
套用：PVC 先「掛單」
# 2. 套用申請單
nano pvc.yaml
kubectl apply -f pvc.yaml

# 3. 看 PVC：Pending——standard 是 WaitForFirstConsumer，還沒人用就不供給
kubectl get pvc

# 4. PV 也還沒有——動態供應要等「第一個使用者」出現才開工
kubectl get pv
disk-demo.yaml — Pod 把 PVC 掛進 /data
# disk-demo.yaml — 啟動時寫一筆資料進 PVC，然後睡著
apiVersion: v1
kind: Pod
metadata:
  name: disk-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo hello-from-pvc > /data/message.txt; sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc
布 Pod 觸發供給：PVC 綁定、PV 現身
# 5. 套用 Pod，等它 Running——Pod 被排到節點的那一瞬間，SC 才開始「現做」PV
nano disk-demo.yaml
kubectl apply -f disk-demo.yaml
kubectl get pod disk-demo

# 6. 回頭看：PVC 變 Bound，PV 也自動出現（名字像 pvc-xxxxxxxxxx）
kubectl get pvc
kubectl get pv

# 7. describe PVC 看綁到哪顆 PV；再讀回寫入的檔案
kubectl describe pvc my-pvc
kubectl exec disk-demo -- cat /data/message.txt
你該觀察到什麼

第 3–6 步是「三層」同時亮相的時刻：PVC 先 Pending（WaitForFirstConsumer），直到第一個使用者（disk-demo Pod）排上節點，StorageClass 才幫你現做一顆 PV、PVC 轉 Bound。第 7 步寫入的檔案已經躺在 PV 的底層磁碟上——下一節證明「容器死了它還活著」。

實作 B：容器會死，資料要活

刪 Pod、重建、資料還在
# 8. 把 Pod 整個刪掉（容器檔案系統跟著消失——但 /data 不在裡面）
kubectl delete pod disk-demo

# 9. 用同一份 YAML 重建一顆全新的 Pod
kubectl apply -f disk-demo.yaml
kubectl get pod disk-demo

# 10. 新容器讀得到舊資料——寫進 PV 的東西跟著 PVC 走，不跟著容器
kubectl exec disk-demo -- cat /data/message.txt

# 11. 到節點上親眼看「檔案實際放在哪」：先讀 local-path 的設定，再對照實際目錄
kubectl -n kube-system get cm local-path-config -o yaml | grep -A4 nodePathMap
docker exec kind-worker ls /var/local-path-provisioner
#     找不到就試 /opt/local-path-provisioner（版本不同路徑不同）；
#     若那顆 PV 是綁在 control-plane 那一端，把 kind-worker 換成 kind-control-plane
#     PV 的實際名稱就是上面 kubectl get pv 看到的 pvc-xxxx
刪 PVC：看 Delete 回收策略動手
# 12. 先刪 Pod（PVC 還在使用中時不能刪）
kubectl delete pod disk-demo

# 13. 刪 PVC——standard 的回收策略是 Delete
kubectl delete pvc my-pvc

# 14. PV 跟著消失：底層磁碟也被回收（get pv 應該空了）
kubectl get pv
你該觀察到什麼

第 10 步是全課最關鍵的一幕：Pod 可以死、資料不會死——因為資料在 PV，Pod 只是暫時借用。第 13–14 步則是 StorageClass 回收策略的現場：Delete 的意思就是「PVC 刪掉時，連同自動產生的 PV 與底層目錄一起清掉」。

實作 C：靜態供應——管理者預先造好 PV

動態供應是「工廠現做」；靜態供應是「倉庫現貨」——系統管理員先手刻一顆 PV（這顆我們用 hostPath，直接吃節點的目錄，最適合本機學習；實務上會是 NFS／雲端磁碟）。關鍵：PVC 要寫 storageClassName: ""，關掉動態供應，它才會去配「現貨」。

pv-static.yaml — 管理者預先造好的 PV
# pv-static.yaml — hostPath 吃 kind-worker 節點的 /mnt/data；nodeAffinity 釘住節點
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-static
spec:
  capacity:
    storage: 1Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  hostPath:
    path: /mnt/data
    type: DirectoryOrCreate
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: ["kind-worker"]
套用 PV、再用 PVC 認領
# 15. 套用後 PV 停在 Available，等有人來認領
nano pv-static.yaml
kubectl apply -f pv-static.yaml
kubectl get pv

# 16. 一張「只要現貨」的申請單：storageClassName 設空字串、關閉動態供應
kubectl create -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-static
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: ""
  resources:
    requests:
      storage: 1Gi
EOF

# 17. pvc-static 綁上 pv-static（兩邊狀態都變 Bound）
kubectl get pvc
kubectl get pv
用這顆「現貨」PVC 寫資料
# 18. 換個 Pod 掛 pvc-static（claimName 改成 pvc-static），寫一筆再讀回
kubectl delete pod disk-demo 2>/dev/null; true
kubectl run static-demo --image=busybox:1.36 --restart=Never --dry-run=client -o yaml > static-demo.yaml
nano static-demo.yaml
#    把 spec 加上 volumeMounts/volumes，claimName 用 pvc-static（照 disk-demo.yaml 抄）
kubectl apply -f static-demo.yaml
kubectl exec static-demo -- sh -c 'echo static-works > /data/note.txt; cat /data/note.txt'

# 19. 收尾：刪 Pod → 刪 PVC（Retain：PV 不會被刪，只變 Released）
kubectl delete pod static-demo
kubectl delete pvc pvc-static
kubectl get pv
#    pv-static 還在，但 STATUS 變成 Released——等著管理者清理（這個示範直接刪）

# 20. 手動刪掉 Released 的 PV，收乾淨
kubectl delete pv pv-static
rm pvc.yaml disk-demo.yaml pv-static.yaml static-demo.yaml

# 21. 課末確認：雙節點、乾淨、無殘留 PV/PVC
kubectl get nodes
kubectl get pv,pvc
你該觀察到什麼

第 19 步對照第 13 步，回收策略的差別一目了然：Delete 讓 PV 自動消失；Retain 讓 PV 留在原地、標成 Released——這是「PVC 刪了但 PV 還在」的標準情境，考場問「為什麼 PV 還在？」答案就是 reclaim policy 是 Retain。

考場小抄

① 三層口訣：PVC 是請求、PV 是現貨、StorageClass 是工廠；Pod 只認 PVC。② 查詢三寶：kubectl get pvc／get pv／get storageclass。③ 存取模式縮寫：RWO（單節點讀寫）、ROX（多節點唯讀）、RWX（多節點讀寫）。④ 回收策略：Delete 連根拔、Retain 留 Released。⑤ 想配靜態 PV：PVC 寫 storageClassName: ""；hostPath PV 一定要 nodeAffinity 釘節點。⑥ 動態綁定常見的 WaitForFirstConsumer：PVC 先 Pending、有 Pod 用才 Bound——不是故障。

本課戰果

  • 你見證了動態供應：只寫 PVC，StorageClass 自動現做 PV 並綁定。
  • 你證明「Pod 會死、資料會活」：刪掉 Pod 重建後檔案還在。
  • 你親眼看 Delete 回收（PV 跟 PVC 一起消失）與 Retain 回收（PV 變 Released）的差別。
  • 你手刻了一顆靜態 hostPath PV，並用 storageClassName: "" 的 PVC 精準認領它。
