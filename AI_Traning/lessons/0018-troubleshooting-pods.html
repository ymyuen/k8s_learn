Phase 5 · 對應考綱：Troubleshooting（30%） · 需時約 30 分鐘

故障排除 I：Pod 與容器層

最後一個 Phase（Troubleshooting，佔考綱 30%，是最大單一領域）。過去十七課的「事件、describe、logs、readiness」都在為這裡鋪路。本課把除錯變成一套系統化流程，並辦一場「五顆壞 Pod」的診斷賽——每一顆的症狀都是 CKA 愛考的經典。叢集沿用 Calico 雙節點（0012–0017 都好好的）。

除錯流程：從症狀到根因

Pod 除錯標準流程（照順序走）
1. kubectl get pods          症狀：STATUS 欄（CrashLoopBackOff? Pending?）
2. kubectl describe pod       看 Events 與容器狀態（最常一步定案）
3. kubectl logs / --previous  看應用程式自己說了什麼
4. kubectl exec               進容器查證（設定、檔案、連線）

把「症狀」對到「第一件事」是搶分關鍵：

症狀（STATUS）最可能原因第一指令
ImagePullBackOff映像名稱／tag 錯、登入問題describe pod 看 Events
CreateContainerConfigErrorenv 或 volume 引用不存在的 ConfigMap/Secretdescribe pod 看 Events
CrashLoopBackOff程式啟動即掛（exit 非 0）logs／logs --previous
OOMKilled超過 memory limitdescribe pod 看 Reason
Running 但 READY 0/1readiness 探針失敗describe pod 看探針事件
Pending資源不足／污點／nodeSelector 無節點可排describe pod 看 Events

實作 A：五顆壞 Pod 診斷賽

把下面五份 YAML 依序存檔、套用、診斷、修復。修 Pod 的口訣：找到根因 → 改 YAML → 刪掉重套（Pod 建立後大部分 spec 不可改）。第一顆：映像版本不存在。

pod1-bad-image.yaml — 映像 tag 不存在
apiVersion: v1
kind: Pod
metadata:
  name: bad-image
spec:
  containers:
  - name: app
    image: nginx:9.99
診斷 1：映像拉不下來
# 1. 套用後看 STATUS——先是 ErrImagePull，重試幾次後變 ImagePullBackOff
nano pod1-bad-image.yaml
kubectl apply -f pod1-bad-image.yaml
kubectl get pod bad-image

# 2. describe 找根因：Events 的 Failed to pull image 會寫出真實錯誤
kubectl describe pod bad-image

# 3. 修復：tag 改回存在的版本，刪掉重套
nano pod1-bad-image.yaml
kubectl delete pod bad-image --wait=false
kubectl apply -f pod1-bad-image.yaml
kubectl get pod bad-image
你該觀察到什麼

ImagePullBackOff 的根因幾乎都寫在 describe 的 Events 最後一筆（例如 manifest unknown／not found）。它會自動指數退避重試（跟 0004 的 Job backoff 同一個家族），所以「修好就刪掉重套」能立刻觸發新的拉取。

pod2-missing-cm.yaml — env 引用不存在的 ConfigMap
apiVersion: v1
kind: Pod
metadata:
  name: missing-cm
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: APP_ENV
      valueFrom:
        configMapKeyRef:
          name: app-env
          key: APP_ENV
診斷 2：容器建不起來
# 4. 套用：STATUS 出現 CreateContainerConfigError——容器連建立都失敗
nano pod2-missing-cm.yaml
kubectl apply -f pod2-missing-cm.yaml
kubectl get pod missing-cm

# 5. describe 的 Events 直接點名：configmap "app-env" not found
kubectl describe pod missing-cm

# 6. 修復：把缺的 ConfigMap 補上（0006 的老朋友）
kubectl create configmap app-env --from-literal=APP_ENV=prod
kubectl delete pod missing-cm --wait=false
kubectl apply -f pod2-missing-cm.yaml
kubectl get pod missing-cm
kubectl exec missing-cm -- sh -c 'echo $APP_ENV'
pod3-crash.yaml — 程式一啟動就 exit 1
apiVersion: v1
kind: Pod
metadata:
  name: crash-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo starting; exit 1"]
診斷 3：CrashLoopBackOff
# 7. 套用：CrashLoopBackOff——容器一直「起來就死」
nano pod3-crash.yaml
kubectl apply -f pod3-crash.yaml
kubectl get pod crash-demo

# 8. 看日誌：程式自己印了 starting 後 exit——日誌會告訴你死因
kubectl logs crash-demo

# 9. --previous：上一輪容器（已死的那個）的日誌——CrashLoop 的救星
kubectl logs crash-demo --previous

# 10. 修復：拿掉 exit 1，改成睡著
nano pod3-crash.yaml
kubectl delete pod crash-demo --wait=false
kubectl apply -f pod3-crash.yaml
kubectl get pod crash-demo
pod4-oom.yaml — 吃爆記憶體上限
apiVersion: v1
kind: Pod
metadata:
  name: oom-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "i=$(dd if=/dev/zero bs=1M count=4 2>/dev/null | tr '\\0' a); while :; do i=$i$i; done"]
    resources:
      limits:
        memory: 64Mi
診斷 4：OOMKilled（不是程式 crash）
# 11. 套用：字串每圈加倍，幾秒內就撞上 64Mi 的牆
#     （若你的 busybox 沒把 \0 換成 a、字串是空的而不爆，
#       就把 dd 的 count=4 改成 count=64 加大起點再試）
nano pod4-oom.yaml
kubectl apply -f pod4-oom.yaml
kubectl get pod oom-demo
#    會看到 CrashLoopBackOff 或反覆重啟

# 12. describe：Last State 的 Reason 是 OOMKilled、Exit Code 137——這是「被殺」不是「自爆」
kubectl describe pod oom-demo
#    Exit Code 137 = 128 + 9（SIGKILL）＝被 OOM killer 砍掉

# 13. 修復：改應用（把無窮成長的迴圈換成正常指令）
nano pod4-oom.yaml
kubectl delete pod oom-demo --wait=false
kubectl apply -f pod4-oom.yaml
kubectl get pod oom-demo
OOMKilled 與 CrashLoopBackOff 的區分

Exit Code 是關鍵線索：137＝OOM 被殺、非零但非 137＝程式自己掛。記憶體相關還有一個前導症狀：describe 的容器 State 會寫 Reason: OOMKilled，而 logs 常常空空如也（它來不及印東西就被砍）。看到 137 先檢查 limits，而不是追程式邏輯。

pod5-readiness.yaml — 探針打錯 port（複習 0007）
apiVersion: v1
kind: Pod
metadata:
  name: not-ready
spec:
  containers:
  - name: app
    image: nginx:1.25
    readinessProbe:
      httpGet:
        path: /
        port: 8080
      periodSeconds: 3
診斷 5：Running 但不 Ready
# 14. 套用：STATUS Running 但 READY 0/1——服務其實活著，只是沒過探針
nano pod5-readiness.yaml
kubectl apply -f pod5-readiness.yaml
kubectl get pod not-ready

# 15. describe：Events 寫 Readiness probe failed（GET 8080 失敗）
kubectl describe pod not-ready

# 16. 修復：port 改回 80
nano pod5-readiness.yaml
kubectl delete pod not-ready --wait=false
kubectl apply -f pod5-readiness.yaml
kubectl get pod not-ready

實作 B：logs 技巧與多容器

pod-logs.yaml — 一顆 Pod 兩隻容器
apiVersion: v1
kind: Pod
metadata:
  name: logs-demo
spec:
  containers:
  - name: web
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo web-ok; sleep 2; done"]
  - name: debug
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo debug-line; sleep 3; done"]
多容器的 logs 旗標
# 17. 多容器 Pod 一定要 -c 指名看誰（沒給會報錯要你指定）
nano pod-logs.yaml
kubectl apply -f pod-logs.yaml
kubectl logs logs-demo -c web --tail=3
kubectl logs logs-demo -c debug --tail=3

# 18. 其他常用旗標：--tail=N 只看最後 N 行；-f 持續跟隨
kubectl logs -f logs-demo -c web
#    Ctrl+C 離開 -f

# 19. Events 也是除錯證據：sort-by 把最近的事件排到最下面看
kubectl get events --sort-by=.lastTimestamp | tail -n 10
收尾：清乾淨，叢集回到「乾淨」狀態
# 20. 刪掉本課全部練習物件
kubectl delete pod bad-image missing-cm crash-demo oom-demo not-ready logs-demo
kubectl delete configmap app-env
rm -f pod1-bad-image.yaml pod2-missing-cm.yaml pod3-crash.yaml pod4-oom.yaml pod5-readiness.yaml pod-logs.yaml
kubectl get pods -A
考場小抄

① 症狀→第一指令對照表（上面那張）背起來。② CrashLoop 三連：get pods → describe 看 Events → logs；上次死掉的日誌用 --previous（必背）。③ Exit Code：137＝OOM、非零其他＝程式自爆。④ 多容器：logs -c 名字、exec -c 名字。⑤ 修 Pod 一律「刪掉重套」，別想熱修 spec。⑥ Pending 先看 Events：Insufficient memory／cpu、nodeSelector 沒節點、taint 沒 toleration——全部寫在 Events。

本課戰果

  • 你建立「get → describe → logs → exec」的系統化除錯流程。
  • 你修好五顆經典壞 Pod：ImagePullBackOff、CreateContainerConfigError、CrashLoopBackOff、OOMKilled、READY 0/1。
  • 你學會 logs 的 --previous／--tail／-f／-c 技巧，並用 Events 排序輔助判讀。
