故障排除 II：節點、控制平面與網路服務

0018 學會修「單顆 Pod」；本課把視野往上推兩層：① 節點（NotReady、條件判讀）與 控制平面（static pod 巡檢），② 把 0010 的「分層除錯」擴大成端到端故障鏈——從 curl 不通一路查到 NetworkPolicy。叢集沿用 Calico 雙節點。

開場先補裝 metrics-server

0007 裝的 metrics-server 在 0011／0012 兩次重建叢集時被洗掉了。本課開場把它補回來（本課與 0020 的 kubectl top 都靠它），指令與 0007 完全相同。

節點層：describe node 的 Conditions

節點的健康狀態寫在 describe node 的 Conditions 區塊，逐條判讀：

  • Ready＝kubelet 正常回報。False 或 Unknown 就是「節點掛了／網路斷了」。
  • MemoryPressure／DiskPressure／PIDPressure＝節點資源告急（通常伴隨 evict Pod）。

判讀口訣：Ready 看 kubelet；Pressure 看資源。

控制平面：static pod

kubelet 會自動拉起 /etc/kubernetes/manifests/ 底下的 manifest——控制平面四元件（apiserver、controller-manager、scheduler、etcd）都是這樣活的（0014／0015 都碰過）。所以「控制器不動了」的模擬方式：把 controller-manager 的 manifest 移走，kubelet 就會把它的 pod 收掉——Deployment 從此沒人管。

實作 A：裝回 metrics-server 並看節點健康

補裝 metrics-server（0007 重播）
# 1. 先確認它真的不見了（0012 重建後 kube-system 沒有 metrics-server）
kubectl get pods -n kube-system | grep metrics-server
#    沒有輸出 = 沒裝

# 2. 裝官方 components.yaml
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 3. kind 的 kubelet 沒設 TLS 認證——補參數（只有本機測試叢集這樣做）
kubectl -n kube-system patch deployment metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deployment/metrics-server

# 4. 等約 30 秒收資料，驗證
kubectl top nodes
kubectl top pods -A
節點條件判讀
# 5. Conditions 區塊：Ready=True；三種 Pressure 都 False 才是健康
kubectl describe node kind-worker

# 6. -o wide 看節點狀態與版本
kubectl get nodes -o wide
static pod 巡檢
# 7. kube-system 裡「沒有 -replicaset 尾碼」的 Pod 就是 static pod：
#    etcd-kind-control-plane / kube-apiserver / kube-controller-manager / kube-scheduler
kubectl get pods -n kube-system -o wide

# 8. 它們的 manifest 都躺在 control-plane 節點的這個目錄
docker exec kind-control-plane ls /etc/kubernetes/manifests

實作 B：模擬「控制器掛了」——Deployment 生不出 Pod

進階實驗，動手前先看

把 controller-manager 的 manifest 移走會讓它停擺約 1–2 分鐘，期間 Deployment 不會有動作——這正是「控制平面某元件掛了」的經典症狀。做完立刻放回，叢集會自行恢復。若你不想動正式叢集，可跳過此節（概念在下方照讀）。

製造故障：controller-manager 消失
# 9. 先把 controller-manager 的 manifest 移出 manifests 目錄
docker exec kind-control-plane mv /etc/kubernetes/manifests/kube-controller-manager.yaml /tmp/

# 10. 確認它的 static pod 被 kubelet 收掉（等一下再 get）
kubectl get pods -n kube-system | grep controller-manager
#    會發現那顆 pod 消失了
觀察症狀：Deployment 沒有 ReplicaSet、沒有 Pod
# 11. 佈一支 Deployment——它「應該」要被 controller-manager 處理
kubectl create deployment ghost-cm --image=nginx:1.25 --replicas=2
kubectl get deployment ghost-cm
kubectl get rs,pods
#    Deployment 存在，但 ReplicaSet 沒被建、Pod 沒出生——
#    因為「負責生 RS 的控制器」不在。

# 12. 診斷結論：不是 YAML 錯、不是 Pod 壞，是控制器層沒人做事
kubectl describe deployment ghost-cm
#    沒有 ReplicaSet 相關事件——跟平常「立即生 RS」的表現對照就有感
復原：把 manifest 放回去
# 13. 放回 manifest，kubelet 幾秒內重新拉起 controller-manager
docker exec kind-control-plane mv /tmp/kube-controller-manager.yaml /etc/kubernetes/manifests/
kubectl get pods -n kube-system | grep controller-manager
kubectl get pods -l app=ghost-cm
#    ReplicaSet 出現、Pod 出生——控制器恢復後自動補做（reconcile）
kubectl delete deployment ghost-cm
你該觀察到什麼

第 11–12 步是「控制平面元件故障」的指紋：Deployment 存在但沒有對應 ReplicaSet，且 describe 看不到任何新事件。真實世界遇到這種「控制器沒做事」的症狀，方向是查 kube-controller-manager（logs、static pod 是否在跑），而不是去翻 Deployment YAML。

實作 C：端到端故障鏈——curl 不通，從頭查到尾

把 0010（DNS 層）＋0009（endpoints 層）＋0012（NetworkPolicy）串成一次完整除錯：服務突然連不上，怎麼一步步定位？

準備：一支服務＋一支客戶端＋先確認通
# 14. 佈服務與客戶端（跟 0010 同一招）
kubectl create deployment web --image=nginx:1.25 --replicas=2
kubectl expose deployment web --port=80
kubectl run client --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/client --timeout=60s

# 15. 基準線：現在是通的
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local | head -n 1
下故障：default namespace 全面 deny ingress
# 16. 0012 的 default deny 上場——故意把 default 的所有進站流量關上
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
EOF
kubectl get networkpolicy
故障鏈第一站：curl 不通
# 17. 症狀出現：wget 逾時
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local || echo '-- BLOCKED --'
第二站：DNS 層正常嗎？（0010 的招）
# 18. nslookup 解析得到 VIP——DNS 層沒問題，不是名字錯
kubectl exec client -- nslookup web.default.svc.cluster.local
第三站：endpoints 有後端嗎？（0009 的招）
# 19. endpoints 有 2 個 IP——selector 有打到、Pod 也 Ready（0007 的 READY 也檢查一下）
kubectl get endpoints web
kubectl get pods -l app=web
第四站：是不是 NetworkPolicy 擋的？（0012 的招）
# 20. 前面三站都正常，剩下嫌疑犯：NetworkPolicy
kubectl get networkpolicy
kubectl describe networkpolicy deny-all
#    podSelector {} + Ingress = 把 default 全擋——找到了

# 21. 移除故障源，服務恢復
kubectl delete networkpolicy deny-all
kubectl exec client -- wget -qO- -T 3 http://web.default.svc.cluster.local | head -n 1
收尾
# 22. 清掉練習物件（metrics-server 留著給 0020）
kubectl delete deployment web
kubectl delete svc web
kubectl delete pod client
kubectl get pods -A
kubectl get nodes
你該觀察到什麼

第 17–21 步是 Troubleshooting 30% 的濃縮：「curl 不通」不是一個問題，是一串問題。照「DNS → endpoints → Pod READY → NetworkPolicy」逐層排除，每層都有對應的 kubectl 指令——這就是系統化除錯。Service 連不上的三大原因：selector 不合、Pod 不 Ready、NetworkPolicy 擋（0019 一課收齊）。

考場小抄

① 節點：describe node 的 Conditions——Ready 查 kubelet、MemoryPressure 等查資源；NotReady 先查 kubelet 與 CNI。② 控制平面是 static pod：manifest 在 /etc/kubernetes/manifests；「Deployment 存在卻沒 RS」＝控制器沒做事。③ kubectl top 的前提是 metrics-server。④ 端到端除錯鏈：curl 不通 → nslookup（DNS 層）→ get endpoints（後端層）→ get pods READY（0007）→ get networkpolicy（0012）。⑤ 被 NP 擋＝逾時；被拒絕＝connection refused（通常只剩沒後端）。⑥ Service 沒 endpoints 的三原因：selector 不合、Pod 不 Ready、被 NP 擋。

本課戰果

  • 你把 metrics-server 補裝回叢集，並用 kubectl top 驗證。
  • 你學會判讀節點 Conditions，並找到控制平面的 static pod 與它們的 manifest。
  • 你模擬並復原「controller-manager 掛掉」的故障，看懂 Deployment 生不出 Pod 的指紋。
  • 你沿著 DNS → endpoints → NetworkPolicy 鏈完成一次端到端網路除錯。
