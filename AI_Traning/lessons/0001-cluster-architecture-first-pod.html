叢集架構與你的第一個 Pod

你已經有容器經驗：docker run 拉一個 image、跑一個 process，搞定。那 Kubernetes 到底多了什麼？答案就一句話——它把「跑容器」這件事從「一台機器上」搬到「一群機器上」，並讓那群機器看起來像一台。

為什麼需要「一群機器」？

單機跑容器有三個天花板，而 Kubernetes 生來就是來拆這三面牆的：

  • 故障：機器掛了，應用就掛了。Kubernetes 在另一台機器重新把 Pod 拉起來。
  • 伸縮：流量爆掉，加幾台機器裝不下。Kubernetes 告訴新 Pod 該放哪。
  • 管理：幾十台機器各自 ssh 進去開容器？Kubernetes 給你單一 API 統一管。

兩個半場：Control Plane 與 Nodes

一個叢集（cluster）分成兩個角色。想理解 Kubernetes，先記住這張分工圖。

角色在哪裡跑元件一句話職責
Control Plane
（控制平面 = 大腦）		 控制平面節點 kube-apiserver 對外唯一 API 入口，所有管理指令都進這裡
etcd 鍵值資料庫，存放叢集所有狀態（CKA 必考備份）
kube-scheduler、kube-controller-manager 排程器決定 Pod 放哪台節點；控制器負責把現況推向期望狀態
Worker Node
（工作節點 = 手腳）		 工作節點 kubelet、kube-proxy、Container Runtime kubelet 確保節點上的容器照著規格跑；kube-proxy 實作 Service 網路規則

關鍵心法：你（透過 kubectl）永遠只跟 kube-apiserver 說話。apiserver 驗證你的身分，把想要的狀態寫進 etcd，其他元件看著 etcd 各自做事。這叫「宣告式」（declarative）：你宣告「我要 3 個 nginx」，剩下的排程、啟動、自癒都不是你管的事。

一筆請求的生命旅程
你打 kubectl run nginx --image=nginx
  → kube-apiserver（驗證、寫入 etcd）
  → kube-scheduler（選一台節點）
  → 那台節點的 kubelet（叫 container runtime 啟動容器）
  → 回報狀態給 apiserver → 存回 etcd

終端機實作：建叢集、跑第一個 Pod

理論到這裡就夠了——現在動手。我們用 kind（Kubernetes in Docker）在 WSL2 + Docker Desktop 上建一個真叢集，不用碰雲端。

環境準備（只做一次）

先確認 WSL2 內有 Docker 與 kind：docker version、kind --version。沒有就先裝 kind（官方文件：curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.27.0/kind-linux-amd64），再裝 kubectl。若安裝遇到問題，直接問講師。

指令清單（照著打）
# 1. 建立叢集（約 2 分鐘）。注意：不帶設定檔時 kind 只建「單節點」，
#    這台節點同時是 control-plane 兼 worker——所以等等只會看到一台。
kind create cluster

# 2. 看叢集裡的節點——只有 kind-control-plane，ROLE 是 control-plane
kubectl get nodes

# 3. 跑出你的第一個 Pod
kubectl run nginx --image=nginx

# 4. 看 Pod 狀態（耐心等它到 Running）
kubectl get pods

# 5. 看細節——事件、IP、容器狀態都在這裡
kubectl describe pod nginx

  # 6. 結束練習後清理
kubectl delete pod nginx
選配：真正的一主一從

想練習「scheduler 在多台節點之間選一台」，就用設定檔建立雙節點叢集：

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker

# 然後重新建立
kind delete cluster
kind create cluster --config kind-config.yaml
kubectl get nodes   # 這次有 kind-control-plane 與 kind-worker 兩台

也可在 nodes 各項加上 image: kindest/node:vX.Y.Z 對齊特定 K8s 版本（例如考試的 v1.35；以 kind release notes 支援的 tag 為準）。

課前預告：為什麼上面沒有 worker 也能跑 Pod？

正式叢集的 control-plane 節點帶有 taint（node-role.kubernetes.io/control-plane:NoSchedule），一般 Pod 若沒有對應的 toleration 就不會被排程上去。kind 為了讓單節點可用，建立時把這個 taint 拿掉了，所以 nginx 能直接跑在 kind-control-plane 上。Taint 與 Toleration 是考綱 Workloads & Scheduling 的內容，後續課程會正式教。

  • 你能說出控制平面與工作節點的分工，以及誰保存叢集狀態。
  • 你用 kind 建了一個真叢集，並用 kubectl 跑出、檢視、刪除了第一個 Pod。
