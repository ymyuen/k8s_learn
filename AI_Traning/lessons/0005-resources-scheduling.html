requests 與 limits：Pod 的資源「底價」與「上限」

Pod 可以宣告兩種資源（CPU、memory）的兩組數字。這四個欄位是排程與運行的關鍵：

requests（請求）limits（上限）
作用時機 排程時（scheduler 找節點） 運行時（kubelet 強制執行）
意義 「我至少要這麼多」——保證額度 「我最多用這麼多」——使用天花板
CPU 超過會怎樣 — 被節流（throttle），變慢但不會死
Memory 超過會怎樣 — OOMKilled，容器被殺掉重啟

CPU 單位：1＝一整顆核心，小數或毫核 100m＝0.1 核心。Memory 單位：128Mi（mebibytes，2 的次方）或 1Gi；考場最常看到 Mi/Gi。Scheduler 決策時只算 requests：它把每台節點上所有 Pod 的 requests 加總，describe node 的「Allocated resources」就是這本帳。

QoS：沒寫 requests 的 Pod 排最後

三個欄位沒寫齊，Pod 會被歸進三種 QoS（服務品質）等級之一，OOM 時殺誰的順序跟著等級走：

  • Guaranteed：每個容器都寫了 requests，且 requests ＝ limits（CPU 與 memory 皆然）。優先級最高，最不容易被 OOM 殺掉。
  • Burstable：至少一個容器有 requests，但不等於 limits（最常見）。
  • BestEffort：任何容器都沒寫 requests／limits。資源不夠時第一個被殺。

秒判法：「有沒有寫」→「相等不相等」。全部沒寫＝BestEffort；有寫且全等＝Guaranteed；其他＝Burstable。

第 13 步的 describe node 是考場必查頁：Allocated resources 區塊是這台節點的「資源帳本」——把所有 Pod 的 requests（與 limits）分開加總，對照上方的 Allocatable，一眼算出「這台還塞得下多大的 Pod」。當所有節點的剩餘額度都容不下一顆新 Pod 時，它會卡在 Pending，而「排不下」的證據 FailedScheduling 事件是記在那顆 Pod 身上（describe pod 的 Events 會寫 Insufficient cpu／Insufficient memory），不是記在節點的 Events——查法見下面方框。第 12 步的 QoS 顯示 Burstable，呼應概念段的口訣：requests ≠ limits。

「排不下」的長相：節點看帳、Pod 看原因

#   Resource   Requests        Limits
#   cpu        850m (42%)      1500m (75%)
#   memory     300Mi (15%)     700Mi (36%)

CKA 陷阱：只寫 requests 不寫 limits ≠ Guaranteed

Taints 與 Tolerations：誰不准來、誰能忍

0001 預告過：正式叢集的 control-plane 節點帶 node-role.kubernetes.io/control-plane:NoSchedule 污點，一般 Pod 排不上去；kind 建單節點叢集時把這污點拔掉了，所以你在 kind-control-plane 上跑過 Pod。機制拆成兩半：

  • Taint 打在節點上，像貼「本店不招待」：效果有 NoSchedule（不排新的）、PreferNoSchedule（盡量不排）、NoExecute（不排新的，還把已在上面的 Pod 逐出）。
  • Toleration 寫在Pod上，像「我有 VIP 卡」：對應污點的 Pod 才允許被排上去。口訣：容忍只是「允許」，不是「偏好」——加了 toleration 不代表一定會被排過去。

Taint 語法：kubectl taint node <節點名> <key>=<value>:<Effect>；移除時在尾巴加 -。Toleration 在 Pod 的 spec.tolerations：

toleration 的標準 YAML 寫法（對照關係用顏色記）
# taint（節點上）：disk=slow:NoSchedule
tolerations:
- key: disk
  operator: Equal
  value: slow
  effect: NoSchedule
# 一一對應：key 相同、operator=Equal + value 相同、effect 相同，
# 這顆 Pod 才「忍得住」那顆節點上的污點。

實作 B：親眼見證 control-plane 污點，再把節點「關上／打開」

本課開場建的雙節點 kind 叢集，control-plane 保留著正式叢集的污點（kind 只在單節點叢集時自動幫你移除，0001 講的正是單節點案例）。這是本課最好的教材：先看污點怎麼讓 Pod「全擠去 worker」，再貼第二個污點看 Pod 卡 Pending，最後用 toleration 放行。

先回收 0001 的伏筆：control-plane 污點
# 18. 看兩台節點的 Taints：control-plane 掛著 NoSchedule 污點、worker 沒有
kubectl get nodes -o 'custom-columns=NAME:.metadata.name,TAINTS:.spec.taints[*].key,EFFECT:.spec.taints[*].effect'
#    kind-control-plane → node-role.kubernetes.io/control-plane / NoSchedule
#    kind-worker        → <none>

# 19. 佈 3 顆副本：沒有 toleration 的 Pod 進不了 control-plane——三顆全擠在 kind-worker
kubectl create deployment taint-demo --image=nginx:1.25 --replicas=3
kubectl get pods -o wide
污點實戰：NoSchedule 只擋「新的」
# 20. 把 worker 也貼上污點——從現在起兩台都不能排新 Pod
kubectl taint node kind-worker disk=slow:NoSchedule

# 21. 刪一顆 Pod：替身兩台都進不去，直接卡 Pending（這正是「排不上」的現場）
kubectl delete pod taint-demo-(隨機尾碼)
kubectl get pods -o wide
kubectl describe pod -l app=taint-demo | tail -n 15
#    Events 會寫：node(s) had untolerated taint {disk=slow:NoSchedule}
#    原本沒被刪的 Pod 還好好在跑——NoSchedule 不逐出既有 Pod
你該觀察到什麼

第 21 步是三件事同時亮相：① NoSchedule 只擋新 Pod（既有的不動）；② 排不上的症狀是 Pending，根因寫在 describe 的 Events（untolerated taint）；③ 一台節點有污點還不夠絕——等兩台都「關上」，Pod 就真的無處可去。CKA 看到 Pending，第一件事就是查節點 Taints。

加上 toleration，把 worker 重新「打開」
# 22. 產出 deployment YAML，在 spec.template.spec 加 tolerations（0004 的 dry-run 工作法）
kubectl create deployment taint-demo --image=nginx:1.25 --replicas=3 --dry-run=client -o yaml > taint-demo.yaml
nano taint-demo.yaml
#      tolerations:
#      - key: disk
#        operator: Equal
#        value: slow
#        effect: NoSchedule

# 23. 套用：有卡的 Pod 能進 worker，Pending 的替身被接手、全部 Running
kubectl apply -f taint-demo.yaml
kubectl get pods -o wide
#    注意：Pod 仍不會去 control-plane——worker 的污點被容忍，control-plane 的沒有

# 24. 收尾：移除 worker 的污點、刪 Deployment
kubectl taint node kind-worker disk=slow:NoSchedule-
kubectl delete deployment taint-demo
rm taint-demo.yaml
想把 Pod 也放到 control-plane？（實驗用）

兩個方法二選一：① 移除 control-plane 的污點 kubectl taint node kind-control-plane node-role.kubernetes.io/control-plane:NoSchedule-；② 在 Pod 加一條對應的 toleration（key node-role.kubernetes.io/control-plane、effect NoSchedule）。正式叢集不建議讓一般工作負載上 control-plane，但考試可能叫你把某顆 Pod 排上去——知道這條指令就夠了。

NoExecute 的差別（考試愛考一句話）

把效果換成 NoExecute，不只是「不排新的」——kubelet 會把已經在該節點上、且沒有對應 toleration 的 Pod 直接逐出（terminate）。Pod 可加 tolerationSeconds 指定「寬限 N 秒再被逐出」。NoExecute 常被用來做「要下線維修的節點先把 Pod 趕走」。

nodeSelector 與 Node Affinity：Pod 指定要去哪台

Taint/Toleration 是「節點拒絕你」；反過來，Pod 也能「指定想去哪」：

  • nodeSelector：最簡單——把 Pod 釘在「帶某 label」的節點上。語法只能比「等於」，而且要 nodeSelector 指定鍵的 label 存在於節點才排得上去。
  • Node Affinity（節點親和性）：更強的表達力——requiredDuringSchedulingIgnoredDuringExecution（硬性，等同 nodeSelector 但支援 In/NotIn 等運算子）與 preferredDuringSchedulingIgnoredDuringExecution（軟性，「盡量」但不保證）。

一句話對比：nodeSelector 是「只能等於的 affinity」；affinity 是「會選 label 的 nodeSelector」。

實作 C：nodeSelector 釘單節點，再改寫成 affinity

nodeSelector 把 Pod 釘在 worker
# 25. 先幫 kind-worker 貼一個 label（用 0003 的 kubectl label）
kubectl label node kind-worker disk=fast

# 26. 產出 YAML 並加 nodeSelector（在 template.spec 下、containers 外）
kubectl create deployment pinned --image=nginx:1.25 --replicas=2 --dry-run=client -o yaml > pinned.yaml
nano pinned.yaml
#      spec.template.spec:
#        nodeSelector:
#          disk: fast
kubectl apply -f pinned.yaml

# 27. 兩顆都該在 kind-worker 上——這就是「釘選」
kubectl get pods -o wide -l app=pinned
把 nodeSelector 改寫成等價的 nodeAffinity
# 28. 用 nano 把 nodeSelector 段換成 nodeAffinity（硬性 required）
nano pinned.yaml
#      spec.template.spec:
#        affinity:
#          nodeAffinity:
#            requiredDuringSchedulingIgnoredDuringExecution:
#              nodeSelectorTerms:
#              - matchExpressions:
#                - key: disk
#                  operator: In
#                  values: [fast]
kubectl apply -f pinned.yaml
kubectl get pods -o wide -l app=pinned
#    效果與 nodeSelector 相同，但 operator 可以換成 NotIn 等條件

# 29. 收尾：刪 Deployment、移除節點 label
kubectl delete deployment pinned
kubectl label node kind-worker disk-
rm pinned.yaml

# 30. 課末確認叢集狀態：乾淨的雙節點，留給下一課
kubectl get nodes
kubectl get pods -A | head
你該觀察到什麼

第 26 步的兩顆 Pod 全部在 kind-worker，因為 nodeSelector 是硬條件：節點上沒有 disk=fast 這個 label，Pod 就會卡在 Pending（試試把 label 移除後重建就能看到）。第 28 步把同一條件翻譯成 nodeAffinity，行為不變、表達力升級——考試兩者都要會寫。

考場小抄

① taint 語法：kubectl taint node <node> key=value:Effect，移除加 -；三種效果 NoSchedule／PreferNoSchedule／NoExecute，後者會逐出既有 Pod。② toleration 與 taint「一一對應」：key、operator/value、effect 三項都對上才有效；容忍 ≠ 偏好。③ 資源帳：kubectl describe node 看 Allocated resources；Pod 排不上先查 node 的 Events 與污點。④ QoS 秒判：全沒寫＝BestEffort；有寫且全等＝Guaranteed；其他＝Burstable。⑤ 想排特定節點：先確認 label（kubectl get nodes --show-labels），nodeSelector 只會等於、affinity 才支援 In/NotIn。

本課戰果

  • 你把練習環境正式切到 WSL2 bash，並在 WSL2 內重建出雙節點 kind 叢集。
  • 你會寫 requests／limits，能判讀節點的 Allocated resources，並能說出三種 QoS 等級的判法。
  • 你親手貼上並移除節點污點，見證 NoSchedule「只擋新 Pod」，也讓 Pod 用 toleration 重新獲得排程資格。
  • 你能用 nodeSelector 把 Pod 釘到指定節點，並把同一條件改寫成 nodeAffinity。
