RBAC 與 ServiceAccount：誰能做什麼

Phase 4（Cluster Architecture，25%）開始。前十二課你一路都用「管理員」權限操作叢集；真實世界每個人、每支程式都該只有「剛剛好」的權限。本課拆開兩件事：ServiceAccount 是「你是誰」（身分），RBAC 是「你能做什麼」（授權）。兩者合起來就是 CKA 必考的四物件組合。叢集沿用 0012 的 Calico 雙節點。

身分（Authentication）與授權（Authorization）

  • 人類管理員用憑證（kubeconfig）登入；Pod 不是人——它用 ServiceAccount 當身分。每個 namespace 都有一個自動建立的 default ServiceAccount，Pod 沒特別指定就用它。
  • Pod 一但指定了 SA，kubelet 會把 SA 的 token 掛進 /var/run/secrets/kubernetes.io/serviceaccount——Pod 內的程式可用它呼叫 apiserver。
  • RBAC 的授權模型：把權限（Role）「綁」給身分（User／Group／ServiceAccount）。Role 描述「對哪些資源能做哪些動作」；Binding 決定「誰拿到這份權限」。
RBAC 的最小詞彙
Role（角色）            ：對「某些資源」的「某些動作」白名單
                           例：對 pods 可以 get、list
  │ 被 binding 綁給
  ▼
ServiceAccount（身分）  ：example：demo namespace 的 app-sa

兩種 Role × 兩種 Binding：四格表

權限可以「只管一個 namespace」（Role）或「管整個叢集」（ClusterRole）；綁定可以「只綁一個 namespace 的範圍」（RoleBinding）或「綁整個叢集」（ClusterRoleBinding）。組合起來只有三種合法結果：

RoleBinding（綁 namespace 範圍）ClusterRoleBinding（綁叢集範圍）
Role
（單 namespace 權限）		 權限只在該 namespace 生效
例：Role「看 pod」+ RoleBinding in demo → 只看得見 demo 的 pod		 （不合法的組合——不能把單 namespace 的 Role 綁成全叢集）
ClusterRole
（叢集權限）		 考點：權限被「限制」回 binding 的 namespace
例：ClusterRole「view」+ RoleBinding in demo → 在 demo 看 deployments 可以、別的 namespace 不行		 權限全叢集生效
例：ClusterRole「node-reader」+ ClusterRoleBinding → 到處都能看 node

一句話：ClusterRoleBinding 把 ClusterRole 放成全叢集；RoleBinding 把「namespaced 資源」的權限放行在「那個 namespace」。（注意：RoleBinding 對 node 這類叢集資源本來就無效——nodes 不是任何 namespace 的東西。Kubernetes 有內建幾個 ClusterRole，如 view／edit／cluster-admin，考場直接重用很方便。）

實作 A：ServiceAccount 與「用它的 Pod」

建 namespace 與 ServiceAccount
# 1. 開一個練習 namespace（等等的 Role/RoleBinding 都要指名它）
kubectl create ns demo

# 2. 建立 ServiceAccount app-sa
kubectl -n demo create serviceaccount app-sa
kubectl -n demo get sa
pod-sa.yaml — Pod 指名用 app-sa
# pod-sa.yaml — serviceAccountName 一指定，token 就自動掛進 Pod
apiVersion: v1
kind: Pod
metadata:
  name: sa-demo
  namespace: demo
spec:
  serviceAccountName: app-sa
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
套用並看自動掛載的憑證
# 3. 套用後進容器看 SA 的 token 與 CA
nano pod-sa.yaml
kubectl apply -f pod-sa.yaml
kubectl exec -n demo sa-demo -- ls /var/run/secrets/kubernetes.io/serviceaccount
#    token / ca.crt / namespace 三件組——Pod 內程式用它們呼叫 apiserver
你該觀察到什麼

ServiceAccount 是「給 Pod 用的身分證」：它本身不給任何權限（權限靠 RBAC 另外給），只是讓 apiserver 認得出「這支程式是 app-sa」。預設的 default SA 通常沒綁任何權限，所以「Pod 內程式直接呼叫 apiserver」常會撞 403——這很正常。

實作 B：Role + RoleBinding，逐步驗證

role.yaml — 只准在 demo 看 Pod
# role.yaml — apiGroups "" 是核心群組（pods 住在這裡）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: demo
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]
rolebinding.yaml — 把 pod-reader 綁給 app-sa
# rolebinding.yaml — subjects 指名 ServiceAccount 身分
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: demo
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: demo
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
套用，用 auth can-i 逐項驗證
# 4. 套用 Role 與 RoleBinding
nano role.yaml
nano rolebinding.yaml
kubectl apply -f role.yaml -f rolebinding.yaml

# 5. 以 app-sa 的身分「試問」權限——CKA 必備的驗證工具
kubectl auth can-i get pods -n demo --as=system:serviceaccount:demo:app-sa
#    yes（Role 准 get）
kubectl auth can-i list pods -n demo --as=system:serviceaccount:demo:app-sa
#    yes（Role 准 list）
kubectl auth can-i delete pods -n demo --as=system:serviceaccount:demo:app-sa
#    no（Role 沒給 delete）
kubectl auth can-i get pods -n kube-system --as=system:serviceaccount:demo:app-sa
#    no——Role 只活在 demo namespace
增權限：edit Role 再驗證一次
# 6. nano 把 verbs 加上 delete，重新 apply
nano role.yaml
kubectl apply -f role.yaml
kubectl auth can-i delete pods -n demo --as=system:serviceaccount:demo:app-sa
#    變成 yes——Role 一改，綁定立刻跟著生效
你該觀察到什麼

第 5 步的 --as= 是「模擬身分」：你不用真的換憑證，就能問 apiserver「如果是 app-sa，我能 delete pods 嗎？」。auth can-i 是 CKA 除錯 RBAC 的萬用起手式——看到 403 先問它，答案幾乎都是「忘了綁權限」或「綁到別人的 namespace」。

實作 C：ClusterRole × 兩種 Binding 的差別

clusterrole.yaml — 叢集級的「看 node」權限
# clusterrole.yaml — ClusterRole 沒有 namespace（全叢集一份）
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list"]
實驗一：ClusterRoleBinding → 全叢集都看得到 node
# 7. 用 kubectl 一鍵綁（clusterrolebinding 沒 namespace）
kubectl create clusterrolebinding sa-see-nodes --clusterrole=node-reader --serviceaccount=demo:app-sa

# 8. 驗證：nodes 是叢集資源，到哪都能看
kubectl auth can-i get nodes --as=system:serviceaccount:demo:app-sa
#    yes（ClusterRoleBinding = 叢集級生效）
kubectl auth can-i list nodes --as=system:serviceaccount:demo:app-sa
#    yes
實驗二：RoleBinding 綁 ClusterRole → 被侷限回 namespace
# 9. 換一種綁法：改用內建 ClusterRole「view」＋ RoleBinding 綁在 demo
#    （先刪掉剛才的 ClusterRoleBinding，避免干擾判讀）
kubectl delete clusterrolebinding sa-see-nodes
kubectl create rolebinding demo-view --clusterrole=view --serviceaccount=demo:app-sa -n demo

# 10. 驗證：在 demo 看 deployment 可以……
kubectl auth can-i list deployments -n demo --as=system:serviceaccount:demo:app-sa
#    yes（view 含 deployments 的 get/list，經 RoleBinding 落在 demo）
kubectl auth can-i list deployments -n kube-system --as=system:serviceaccount:demo:app-sa
#    no——同一個 ClusterRole，RoleBinding 把它限制在 demo
你該觀察到什麼

第 8 步與第 10 步是四格表的核心對照：同一份 ClusterRole（甚至內建的 view），用 ClusterRoleBinding 綁＝全叢集，用 RoleBinding 綁＝只剩那個 namespace。「把 ClusterRole 用 RoleBinding 綁在某個 namespace，給那個 namespace 的成員一套標準權限」是實務上最常見的設計。

收尾
# 11. 收尾：刪掉練習物件（ns demo 會連帶刪裡面的 SA/Pod/Role/Binding）
kubectl delete ns demo
kubectl delete clusterrole node-reader
rm -f pod-sa.yaml role.yaml rolebinding.yaml clusterrole.yaml
kubectl get nodes
考場小抄

① kubectl auth can-i VERB RESOURCE [--as=...] [-n NS]——RBAC 除錯第一招；加 --list 一次列出全部權限。② 四物件組合背誦：Role×RoleBinding＝該 namespace；ClusterRole×RoleBinding＝被限回 binding 的 namespace；ClusterRole×ClusterRoleBinding＝全叢集；Role×ClusterRoleBinding＝不存在。③ 身分字串格式：system:serviceaccount:<ns>:<name>。④ 常用 apiGroups：""（pods/nodes/…）、apps（deployments）、batch（jobs）、networking.k8s.io（ingresses/networkpolicies）、rbac.authorization.k8s.io。⑤ 內建 ClusterRole 可重用：view／edit／cluster-admin。⑥ 看到 403：先確認「Role 有 verbs？」→「Binding 的 namespace 對？」→「subject 名字對？」

本課戰果

  • 你建立 ServiceAccount，並讓 Pod 指名使用它（token 自動掛載）。
  • 你用 Role + RoleBinding 授予「demo 看 Pod」權限，並用 auth can-i 逐項驗證與增權。
  • 你對照實驗了 ClusterRole × ClusterRoleBinding 與 × RoleBinding 的範圍差別。
