Labels & Selectors 深入

上一課的結論是：「Deployment 靠 selector 認領自己的 ReplicaSet，ReplicaSet 靠 selector 認領自己的 Pod」。本課把這套「認人機制」講透——控制器從來不是靠名字認親，而是靠標籤與選擇器。這個機制貫穿 Workloads & Scheduling 與 Troubleshooting（30%），而「selector 不匹配」正是 CKA 最常見的除錯情境之一。（若 0002 的 rollout undo 還沒補做，先花一分鐘回去做完，再回來繼續。）

Label：物件的身份證

Label 是附著在物件上的鍵值對（key=value），用途只有兩個字：組織與選取。鍵名規則：可加 prefix（如 app.kubernetes.io/name，prefix 須是 DNS 子網域名稱）；名稱與值最多 63 字元、只能含字母數字與 - _ .，且開頭結尾必須是字母數字。慣例上最常見的鍵：app（應用）、tier（層級，frontend/backend）、version（版本）。

Label（標籤）Annotation（註解）
用途 組織與選取物件 附加說明資訊（如 change-cause）
可否被 selector 選取 可以 不可以
典型內容 小型鍵值對（app=nginx） 可較長、結構化文字
範例 app=nginx、tier=frontend kubernetes.io/change-cause="更新到 1.26"

記住這個關鍵差別：Label 是給 selector 選的，Annotation 是給人看的。

Selector 兩種類型

Selector 就是「認人條件」。每個控制器都把一條或多條條件寫在 selector 裡，全部符合才算認領（多條件用 , 連接）。Selector 有兩種寫法：

型別運算子範例意義
Equality-based
（等值式）		 =、== app=nginx 該 label 的值等於 nginx
!= tier!=frontend 值不等於 frontend（或沒有該鍵）
Set-based
（集合式）		 in app in (nginx, busybox) 值是集合中的其中一員
notin tier notin (frontend, backend) 值不在集合中
exists tier（有鍵）、!tier（沒鍵） 只看鍵存不存在，不看值
kubectl 帶 selector 的三種寫法（-l）
# equality：等於
kubectl get pods -l app=nginx

# set-based：值在集合內（留意括號是 ( )，不是 { }）
kubectl get pods -l 'app in (nginx, busybox)'

# set-based exists：只要沒有 tier 這個鍵
kubectl get pods -l '!tier'

實作 A：動手玩 Label

在你的 kind 叢集開一個新終端機照著打。如果 0002 結尾忘了清理，先 kubectl delete deployment nginx。

建立 Deployment，然後動手改 label
# 1. 建立 3 顆副本的 Deployment——它就是我們認人實驗的主角
kubectl create deployment nginx --image=nginx:1.25 --replicas=3
kubectl rollout status deployment/nginx   # 等 3 顆都就緒

# 2. 把 label 一起印出來
kubectl get pods --show-labels
#    每顆 Pod 應該有兩個 label：app=nginx（Deployment 加的）與
#    pod-template-hash=...（ReplicaSet 加的，用來區分新舊版本）

# 3. 依 label 過濾：只要 app=nginx 的 Pod
kubectl get pods -l app=nginx

# 4. 挑一顆，幫它加 label tier=frontend（鍵不存在，直接加）
kubectl label pod nginx-(隨機尾碼) tier=frontend

# 5. 用新 label 也找得到它
kubectl get pods -l tier=frontend

# 6. 移除 label：鍵名尾巴加減號 -
kubectl label pod nginx-(隨機尾碼) tier-

# 7. Set-based 示範：值「在集合內」才選中
kubectl get pods -l 'app in (nginx)'
你該觀察到什麼

--show-labels 多印一欄 LABELS；-l 依條件過濾，列出的 Pod 數量與內容會跟著你的條件改變。把 tier=frontend 加在某一顆上，kubectl get pods -l tier=frontend 就只會列出那一顆；刪掉 label 後再用同一條件就查不到了。

實作 B：讓 Pod 變成孤兒（selector 不匹配）

CKA 常見除錯情境：「有一顆 Pod 沒人管」。新手常想直接寫一顆 selector.matchLabels 與 template labels 不匹配的 ReplicaSet YAML 來觀察——不行，apiserver 會直接拒絕（錯誤訊息：selector does not match template labels）。真實世界的「selector 不匹配」多半是動態改 label造成的：Pod 的 label 一變，控制器就不認它了。繼續在實作 A 的叢集上：

改掉一顆 Pod 的 label，製造孤兒
# 8. 先確認現在 3 顆 Pod 都掛著 app=nginx
kubectl get pods --show-labels

# 9. 挑一顆，把它的 app 值改成 scratch。
#    注意：app 鍵已存在，改值要加 --overwrite
kubectl label pod nginx-(隨機尾碼) app=scratch --overwrite

# 10. 再看一次：Pod 變成 4 顆！
#     新尾碼的那顆是 RS 補的（它只認 app=nginx，少了就補）；
#     舊的那顆還 Running，但 label 已不合——它成了孤兒
kubectl get pods --show-labels

# 11. 用 selector 分邊：誰是 RS 管的、誰是孤兒
kubectl get pods -l app=nginx      # 3 顆，RS 管的
kubectl get pods -l app=scratch     # 1 顆，孤兒

# 12. 看 RS 的認人條件（SELECTOR 欄）
kubectl get rs -o wide
kubectl describe rs (RS 名稱)
#    SELECTOR 是 app=nginx,pod-template-hash=... 兩條件都得符合

# 13. 修復：把孤兒的 app 改回 nginx。
#     RS 一看到符合條件的 Pod 變 4 顆，立刻砍掉多出來的一顆
kubectl label pod (孤兒 Pod 名稱) app=nginx --overwrite
kubectl get pods --show-labels   # 回到 3 顆

# 14. 收尾：刪 Deployment（它的 ReplicaSet 一起刪）
#     （不想修復也可直接刪孤兒：kubectl delete pod (孤兒名稱)）
kubectl delete deployment nginx
你該觀察到什麼

第 10 步的關鍵是「4 顆」：RS 不會去刪除那顆被改標籤的 Pod（它只是不再認它），而是補一顆新的維持期望數 3。那顆舊 Pod 既不被 RS 管理、也不會被自我修復——這就是孤兒（orphan）。判讀 selector 不匹配的標準流程：kubectl get rs -o wide 對照 SELECTOR 欄與 kubectl get pods --show-labels，再用 kubectl describe rs (RS 名稱) 確認。

考場小抄

三個必背旗標：--show-labels（列出物件的 label）、-l 'selector'（依條件過濾）、-L key（大寫，直接多印一欄指定 label，例如 kubectl get pods -L app）。改已有 label 的值要加 --overwrite；刪 label 用 key-。看到「Pod 數量對不上」或「有顆 Pod 沒人管」時，第一件事就是比對 selector 與 labels。

本課戰果

  • 你能寫出 equality-based 與 set-based 的 selector，並用 -l 過濾。
  • 你能用 kubectl label 新增、修改（--overwrite）、移除（key-）label。
  • 你能診斷「selector 不匹配 → Pod 孤立」，並把它修復回正常。
