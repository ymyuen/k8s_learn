NetworkPolicy 與 CNI：叢集內防火牆

0011 解決了「外面的流量怎麼進到不同服務」；本課處理「叢集內部誰能連誰」——NetworkPolicy。它是 Kubernetes 原生的防火牆 API：宣告「哪些來源可以連到哪些 Pod 的哪些 port」。但 NetworkPolicy 有個關鍵前提：要 CNI 支援才會真的擋（kindnet 不支援）。所以本課開場會再重建叢集，裝上支援它的 Calico，順便把 CNI 是什麼一次講透。本課之後叢集保持「Calico 雙節點」，0013–0014 直接沿用。

CNI：發 IP、接網路的那個人

每個 Pod 都要有自己的 IP、要被接進叢集網路。做這件事的是一支在每台節點上跑的 CNI plugin：kubelet 建好 Pod 後，呼叫 CNI plugin 把容器接上網路。CNI（Container Network Interface）是這個「呼叫標準」的名字；不同實作有不同的網路模型：

  • kindnet：kind 內建的輕量 CNI（ptp 路由式）——夠簡單，但不實作 NetworkPolicy。
  • Calico：老牌 CNI，用 BGP 或 VXLAN 建立 Pod 網路，並用 iptables/eBPF 實作 NetworkPolicy。
  • 其他：Cilium、Flannel（Flannel 也不實作 NetworkPolicy）…。

記住這條因果鏈：NetworkPolicy 是 API、CNI 是執法人。寫了 NetworkPolicy 但 CNI 不支援＝規則躺在 etcd 裡、沒人執行。

NetworkPolicy 的語意

  • 預設全通：叢集裡沒有 NetworkPolicy 時，任何 Pod 可以連任何 Pod。規則只會「收緊」，不會「放寬」。
  • 空規則 = 全選：podSelector: {} 代表該 namespace 的所有 Pod（不是沒有規則）。
  • policyTypes：宣告這份規則管 Ingress（進來的）還是 Egress（出去的）。一旦某個方向被任何一份 policy 選中，該方向就變成預設拒絕——這就是「default deny」的由來。
  • 選來源：podSelector（同 namespace 挑 Pod）、namespaceSelector（挑 namespace）、ipBlock（挑 IP 段）；ports 限定協議與 port。
default deny 兩條模板（必背）
# 只擋「進來的」：namespace 內全部 Pod 都不收任何進站流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
spec:
  podSelector: {}
  policyTypes: ["Ingress"]

# 只擋「出去的」：namespace 內全部 Pod 都不能對外連線
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-egress
spec:
  podSelector: {}
  policyTypes: ["Egress"]

實作 B：db 的 default deny，再放行 frontend

np-deny-db.yaml — db namespace 全部拒收進站流量
# np-deny-db.yaml — podSelector 空物件 = 選中 db namespace 內所有 Pod
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: db
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
套用後：兩邊都進不去了
# 13. 套用 default deny
nano np-deny-db.yaml
kubectl apply -f np-deny-db.yaml

# 14. frontend 與 backend 都連不到 db（被擋 = 逾時）
kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
kubectl exec backend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
np-allow-frontend.yaml — 放行「default namespace 中掛 app=frontend 的 Pod」
# np-allow-frontend.yaml — 重點：podSelector 只能選「同 namespace」的來源，
# frontend 住在 default，所以一定要 namespaceSelector（挑 namespace）＋ podSelector（挑 Pod）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
  namespace: db
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: default
      podSelector:
        matchLabels:
          app: frontend
套用後：frontend 回來，backend 繼續被擋
# 15. 套用放行規則
nano np-allow-frontend.yaml
kubectl apply -f np-allow-frontend.yaml

# 16. frontend 通了（它在 default namespace 且掛 app=frontend——兩條件都中）
kubectl exec frontend -- wget -qO- -T 3 http://db.db.svc.cluster.local | head -n 1

# 17. backend 還是被擋（它沒有 app=frontend）
kubectl exec backend -- wget -qO- -T 3 http://db.db.svc.cluster.local || echo '-- BLOCKED --'
你該觀察到什麼

第 13–17 步是「default deny + 精準放行」的完整節奏：先下 podSelector: {} 的 deny 把所有入口關上，再用「更精準的 allow」開門——NetworkPolicy 是白名單思維：預設全通 → 一出現 policy 就翻成預設拒絕 → 每一條 allow 都是一扇開好的門。backend 被擋但 frontend 通，證明規則認的是 namespace＋label，不是 Pod 名字——跨 namespace 放行時 namespaceSelector 那半邊最容易漏。

實作 C：Egress 別忘了 DNS（經典坑）

Ingress 管「誰能進 db」，Egress 管「db／某 Pod 能去哪裡」。經典陷阱：你幫 Pod 設了 egress 白名單，卻忘了放行 DNS（53/UDP 給 kube-dns）——Pod 連「解析服務名稱」都做不到。實作：限制 frontend 只能「打 db 的 80」，先故意漏掉 DNS，看它怎麼死，再加回來。

frontend-egress.yaml — 只准對外打 db:80（忘了 DNS）
# frontend-egress.yaml — 只允許 egress 到「db namespace 裡 app=db 的 Pod:80」
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-egress
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes: ["Egress"]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: db
      podSelector:
        matchLabels:
          app: db
    ports:
    - protocol: TCP
      port: 80
套用：frontend 連 DNS 都出不去
# 18. 套用後，frontend 連 db 的「名稱」都解析不了（DNS 封包被 egress 規則丟掉）

考場小抄

① NetworkPolicy 不擋就放行；出現 policy 後「被選中的方向」預設拒絕。② podSelector: {}＝該 namespace 全部 Pod；policy 有 namespace 欄位，跨 namespace 用 namespaceSelector。③ 被擋的症狀是逾時（不是 connection refused）——除非 CNI 是 iptables REJECT。④ egress 忘 DNS 是經典考點：白名單裡要留 kube-dns 的 53/UDP（加 53/TCP 保險）。⑤ 規則沒生效先查三件事：CNI 支不支援（kindnet 不支援）、label 有沒有打對、policy 的 namespace 對不對。⑥ default deny 兩條模板（上面方框）背起來，考場直接改。
