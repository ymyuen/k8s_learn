Deployment、自我修復與 Rollout/Rollback

上一課你用 kubectl run nginx --image=nginx 跑出一顆裸 Pod——然後發現它很脆弱：kubectl delete pod nginx 之後它就真的消失了。本課的目標只有一個：學會用 Deployment 包住 Pod，讓「Pod 死掉會自己長回來」變成一件理所當然的事。

控制器思維：期望狀態 vs 現況

回想 Lesson 0001 的關鍵心法——你宣告「我要什麼」，Kubernetes 負責「變成那樣」。Deployment 就是這個心法的第一次完整落地：

Reconcile loop（調節迴圈）
你宣告：我要 3 顆 nginx Pod
   ↓ 寫進 etcd（期望狀態）
控制器不斷比對：現在有幾顆？
   ├─ 現在有 3 顆 → 什麼都不用做
   ├─ 現在有 2 顆 → 立刻補 1 顆   ← 這就是「自我修復」
   └─ 現在有 5 顆 → 砍掉 2 顆

這個迴圈由 kube-controller-manager 裡的控制器們執行（見 詞彙表 Controller）。自我修復不是魔法，就是一道不斷比對的迴圈。

Deployment 的三層結構

Deployment 不直接管 Pod，它透過 ReplicaSet 間接管。記住這張表，之後排障全靠它：

層級負責什麼一個比喻
Deployment 管「版本」：滾動更新、回滾、期望副本數 發行負責人：決定現在該出哪一版
ReplicaSet 管「數量」：確保 N 顆 Pod 同時存在 排班主管：確保隨時有 3 個人上班
Pod 管「容器」：實際跑應用 員工：真的在做事的人

Deployment 怎麼「認領」自己的 ReplicaSet 和 Pod？靠 Label & Selector——Deployment 用 selector 選中它的 ReplicaSet，ReplicaSet 再用 selector 選中它的 Pod。細節留到後續課程，現在先記住：「誰管誰，是靠標籤認的」。

實作 A：自我修復

在你的 kind 叢集（單節點就夠用）開一個新終端機照打：

把 3 顆 nginx Pod 變成 Deployment
# 1. 建立 Deployment，期望 3 顆副本
kubectl create deployment nginx --image=nginx:1.25 --replicas=3

# 2. 一次看三層（deployments, replicasets, pods）
kubectl get deployments,replicasets,pods

# 3. 故意刪掉一顆 Pod——注意 Pod 名字
kubectl delete pod nginx-(隨機尾碼)

# 4. 再列一次：Pod 名字尾碼變了，表示是「新的一顆」
kubectl get pods

# 5. 看 Deployment 的事件——會看到 ReplicaSet 重建的紀錄
kubectl describe deployment nginx
你該觀察到什麼

第 4 步的 Pod 列表裡，總數維持 3 顆，但被你刪掉的那一顆名字尾碼換了——那是 ReplicaSet 控制器幫你補上的新 Pod。這就是自我修復，親眼看到一次就懂了。你也會看到 kubectl get pods 輸出中每顆 Pod 的 READY 與 RESTARTS 欄位。

實作 B：Rollout 與 Rollback

Deployment 的招牌能力：換版不中斷、出事能回滾。同一叢集繼續：

換版本、看歷程、回滾
# 6. 把 image 從 nginx:1.25 換成 nginx:1.26（觸發 rollout）
kubectl set image deployment/nginx nginx=nginx:1.26

# 7. 等 rollout 完成（會顯示 "deployment "nginx" successfully rolled out"）
kubectl rollout status deployment/nginx

# 8. 看歷史版本——REVISION 欄就是版本號。
#    CHANGE-CAUSE 顯示 <none> 是正常的（新版 kubectl 已不用 --record）。
#    想留說明：kubectl annotate deployment/nginx kubernetes.io/change-cause="..."
kubectl rollout history deployment/nginx

# 9. 反悔，回到上一版（1.25）。
#    注意：undo 後會出現「新的」REVISION（例如 3），不是把 2 改回去——回滾本身也是新版本
kubectl rollout undo deployment/nginx
kubectl rollout status deployment/nginx
kubectl rollout history deployment/nginx   # 再看一次：多了一列 REVISION 3

# 10. 觀察換版過程：-w = --watch，先印快照、再持續串流變化（新舊並存、逐批替換）。
#     Ctrl+C 離開。想看到動態：開兩個終端機，一邊跑這行，另一邊 set image 或 delete pod
kubectl get pods -w

# 11. 結束練習後清理
kubectl delete deployment nginx
考場小抄

以下三個是必背反射指令：kubectl rollout status deployment/NAME、kubectl rollout history deployment/NAME、kubectl rollout undo deployment/NAME。CKA 常考「更新 image 後確認成功」與「新版本出問題，回滾」——這三個指令各一鍵搞定。--record 已不建議使用，想留 change-cause 註解可用 kubectl annotate。讀歷史時別誤判：每次 set image 或 rollout undo 都會產生一個新的 REVISION 編號（回滾=新版本），所以 undo 之後看到的不是舊編號復活，而是新編號。

本課戰果

  • 你能解釋 Deployment → ReplicaSet → Pod 三層各自管什麼。
  • 你親眼示範了自我修復：刪掉一顆 Pod，控制器自動補回。
  • 你完成了一次滾動更新與一次回滾，並用 -w 觀察到換版過程新舊並存。
