etcd 備份與還原

0001 埋過伏筆：etcd 是存放「所有叢集狀態」的一致鍵值庫——Deployment 的期望狀態、Secret、Namespace 全在裡面。etcd 掛了等於叢集的記憶沒了，所以 CKA 必考「備份與還原」這一整套：snapshot save（存）、snapshot status（驗）、snapshot restore（還原）。本課先在本機 Calico 叢集把「存 + 驗」跑一遍；「還原」的完整手術在 Killercoda 的 VM 上做（考試環境就是 VM，路徑與本機 kind 不同）。

先建立正確心智：snapshot 是什麼、restore 在幹嘛

  • snapshot save：把 etcd 整個資料庫（連同 member 狀態）倒成單一檔案。對「還活著的 etcd」直接存即可，不必停服務。
  • snapshot status：讀 snapshot 檔印出 metadata（revision、總 key 數、db 大小）——備份完「驗得出來是好的」才算數。
  • snapshot restore：把 snapshot 檔「解壓」成一個全新的資料目錄。注意——它不是原地復活舊目錄，而是產生一個新的 member 資料夾，然後你把它接回去給 etcd 用。所以還原流程的本質是：新資料目錄接回 + 重啟 etcd。

考試必背路徑：etcd 是 static pod，manifest 在 /etc/kubernetes/manifests/etcd.yaml，資料目錄在 /var/lib/etcd。憑證三件套固定放在 /etc/kubernetes/pki/etcd/：ca.crt（CA）、server.crt／server.key（etcd 自己）。

三條指令模板（背起來）
# 存
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-snapshot.db

# 驗
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db --write-out=table

# 還原（產生新資料目錄 /var/lib/etcd-from-backup）
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-from-backup
環境提醒：ETCDCTL_API=3

etcdctl 對 v3 API 有「相容模式」的歷史包袱，考試慣例在指令前加 ETCDCTL_API=3 確保走 v3。加上無害、漏了可能踩雷——照抄就對了。endpoints 一律 https://127.0.0.1:2379（本機的 etcd 就聽這裡）。

實作 A：在本機 kind 叢集存一份 snapshot

kind 的 etcd 是跑在 control-plane 節點上的 static pod（名字 etcd-kind-control-plane）。我們在 pod 裡執行 etcdctl，再把檔案拷出來。先製造一點「值得備份的狀態」：

先做點事，讓 snapshot 有內容
# 1. 隨便建一個 namespace 當作「要被備份的狀態」
kubectl create ns backup-me
kubectl create deployment hello-backup --image=nginx:1.25 --replicas=2
kubectl rollout status deployment/hello-backup
找到 etcd pod，執行 snapshot save
# 2. etcd static pod 的名字 = etcd-<節點名>
kubectl get pods -n kube-system | grep etcd
#    etcd-kind-control-plane

# 3. 在 pod 內執行 etcdctl snapshot save（三憑證 + 本機端點）
#    檔案要寫進 /var/lib/etcd（這是 hostPath，節點容器才讀得到、docker cp 才拷得出）
kubectl exec -n kube-system etcd-kind-control-plane -- sh -c 'ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key snapshot save /var/lib/etcd/etcd-snapshot.db'
#    成功會印 "Snapshot saved at /var/lib/etcd/etcd-snapshot.db"

# 4. 確認檔案存在與大小
kubectl exec -n kube-system etcd-kind-control-plane -- ls -lh /var/lib/etcd/etcd-snapshot.db
拷到 host、用 snapshot status 驗證
# 5. 從節點容器拷回 WSL2 host（docker 對 kind 節點直接用；路徑在 hostPath 裡才拷得到）
docker cp kind-control-plane:/var/lib/etcd/etcd-snapshot.db ./etcd-snapshot.db
ls -lh etcd-snapshot.db

# 6. 在 pod 內驗證 snapshot 可讀（存完一定要驗——壞檔沒人想還原時才發現）
kubectl exec -n kube-system etcd-kind-control-plane -- sh -c 'ETCDCTL_API=3 etcdctl snapshot status /var/lib/etcd/etcd-snapshot.db --write-out=table'
#    table 會印 HASH / REVISION / TOTAL KEYS / TOTAL SIZE
預演 restore：還原到一個暫存目錄（不動正式資料）
# 7. 把 snapshot 還原成「新資料目錄」到 /tmp——證明這份備份還原得出來
kubectl exec -n kube-system etcd-kind-control-plane -- sh -c 'ETCDCTL_API=3 etcdctl snapshot restore /var/lib/etcd/etcd-snapshot.db --data-dir=/tmp/restored-etcd'
#    成功會印 "Restored a new etcd database..."

# 8. 看看還原出來的目錄結構（member/ 就是 etcd 的資料夾）
kubectl exec -n kube-system etcd-kind-control-plane -- ls /tmp/restored-etcd
kubectl exec -n kube-system etcd-kind-control-plane -- ls /tmp/restored-etcd/member

# 9. 收掉暫存與 snapshot（備份檔 host 上留著）
kubectl exec -n kube-system etcd-kind-control-plane -- rm -rf /tmp/restored-etcd /var/lib/etcd/etcd-snapshot.db
kubectl delete ns backup-me
kubectl delete deployment hello-backup
你該觀察到什麼

第 6 步的 table 是「備份品質保證」：REVISION 代表 etcd 寫入到哪一版、TOTAL KEYS 是 key 總數。第 7–8 步先看懂 restore 的本質：它把 snapshot「吐」成一個新的資料目錄（含 member 子目錄），不會動你原本在跑的 etcd。真正切換只是把 etcd 指向新目錄重啟——下面實作 B 就是那台手術。

實作 B：完整還原手術（在 Killercoda VM 上演練）

本機 kind 的 etcd 跟正式叢集長得不同（manifest、kubelet 都在節點容器裡），真正的還原手術在VM 型叢集上做才有意義——考試環境也正是 VM。開一個 Killercoda 的 kubeadm／多節點場景，把下面整套跑過一次（約 15 分鐘）。

完整還原流程（VM 版；只可意會不可省略）
# step 0 — 開 Killercoda（killercoda.com），挑一個「kubeadm、含 control-plane」的場景
#    本段假設你在該 VM 的 root／sudo 環境

# step 1 — （第一次練習時先）存一份現在狀態的備份
#    若 VM 的 host 沒裝 etcdctl（kubeadm 不保證會裝）：把底下每行 etcdctl
#    包成 kubectl -n kube-system exec -it etcd-$(hostname) -- sh -c '…' 在 pod 內跑，
#    憑證路徑與指令內容完全一樣——本課實作 A 就是這個做法
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key snapshot save /root/etcd-snapshot.db
ETCDCTL_API=3 etcdctl snapshot status /root/etcd-snapshot.db --write-out=table

# step 2 — 還原成新資料目錄（別放在舊的 /var/lib/etcd 上）
ETCDCTL_API=3 etcdctl snapshot restore /root/etcd-snapshot.db --data-dir=/var/lib/etcd-from-backup

# step 3 — 停掉 etcd static pod：把 manifest 移開，kubelet 就會收掉 etcd
mv /etc/kubernetes/manifests/etcd.yaml /root/
crictl ps | grep etcd || docker ps | grep etcd
#    等到輸出裡看不到 etcd 容器為止（kubelet 約幾秒內收掉）

# step 4 — 備份舊資料目錄、把還原出來的換上去
mv /var/lib/etcd /var/lib/etcd.bak
mv /var/lib/etcd-from-backup /var/lib/etcd

# step 5 — 放回 manifest，讓 kubelet 重新拉起 etcd（此時它讀的是新資料目錄）
mv /root/etcd.yaml /etc/kubernetes/manifests/
crictl ps | grep etcd
sleep 10
kubectl get nodes
kubectl get pods -A
#    節點 Ready、控制平面元件回來，表示還原成功
還原後一定會掉狀態——這不是 bug

還原是回到 snapshot 那一刻：snapshot 之後才建立的物件全部消失（step 1 存檔之後的操作都會不見）。這正是備份的意義：時間點 = 還原點。另外 restore 會換掉 etcd 的 member ID，所以「把還原後的節點重新加入叢集」在 HA 環境要小心——考試只考單一 control-plane 或照題目指令走即可。

考場小抄

① 三指令：snapshot save（三憑證+endpoints 模板）／snapshot status（驗）／snapshot restore --data-dir=...（還原成新目錄）。② 必背路徑：/etc/kubernetes/manifests/etcd.yaml、/var/lib/etcd、憑證在 /etc/kubernetes/pki/etcd/。③ restore 是「新資料目錄接回」不是原地復活——先停 static pod（搬 manifest）、換目錄、再放回 manifest。④ 還原點＝snapshot 時間點，之後的狀態會消失。⑤ 題目若給 member 多的叢集，restore 通常只對單一 member 做、再把其他 member 清掉重建。⑥ 指令前 ETCDCTL_API=3 照抄。

本課戰果

  • 你在本機 kind 叢集對「活著的 etcd」執行了 snapshot save，並用 snapshot status 驗證。
  • 你把備份檔拷出節點，並預演 restore（還原到暫存目錄）證明可還原。
  • 你理解完整還原手術的每一步，並知道在 Killercoda VM 上照表操課。
