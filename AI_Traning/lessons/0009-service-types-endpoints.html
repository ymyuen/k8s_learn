Service 與 Endpoints：穩定的存取入口

進入 Phase 3（Services & Networking，20%）。前八課的 Pod 彼此是「各活各的」：0008 你看到 Pod 可以死、資料不會死——那「別人怎麼找到它」呢？Pod 的 IP 生生死死一直在換，總不能每次重啟就去改設定。Kubernetes 的答案是 Service：一個不隨 Pod 變動的虛擬 IP（VIP）門口，selector 打到哪幾顆 Pod，它就把流量轉給誰。本課先建立「Service 思維」，下課再加 DNS。本課叢集沿用 0008 的雙節點。

Service 的組成：selector → Endpoints → 轉發

Service 把流量交給活的 Pod（概念圖）
              Service（穩定 VIP：10.96.x.x）
                    │ selector: app=web
                    ▼
             Endpoints（此刻的 Pod IP 名單）
               ├── 10.244.0.5:80
               └── 10.244.1.7:80
                    │ kube-proxy 在每台節點寫 iptables/IPVS 規則
                    ▼
            流量轉到名單上的 Pod（會輪流）

Service 自己不做轉發——真正動手的是每台節點上的 kube-proxy：它 watch Service 與 Endpoints，把「到 VIP:Port 的封包」改寫成「到某顆 Pod IP:Port」。kube-proxy 有兩種運作模式：iptables（預設，規則式）與 IPVS（核心內建的負載平衡，規則更多時效能較好）——概念知道即可，考試通常只問「誰在節點上實作 Service 規則」＝kube-proxy。

Service 的四種類型

類型對外範圍一句話
ClusterIP（預設） 叢集內 只給叢集內互相呼叫用的 VIP
NodePort 叢集外（靠節點 IP） ClusterIP + 每台節點開一個 30000–32767 的 port 收外部流量
LoadBalancer 叢集外（雲端） NodePort + 雲端幫你生一個對外負載平衡器（kind 沒有雲，需 MetalLB 等）
ExternalName — 只是 DNS 的 CNAME 轉址，沒有 VIP 也沒有 selector
VIP 的經典考點：ping 不通、curl 通

ClusterIP 是「iptables 規則做出來的假 IP」，不是某台機器上的實體網卡——所以 ping <VIP>（ICMP）一定不通，但 curl http://<VIP>/（TCP）會通。考試若有人拿「ping 不通代表 Service 壞了」來考你，答案是：ping 不通是正常的，要用 TCP 測。

實作 A：ClusterIP 與 Endpoints 連動

佈署、暴露、看三樣東西
# 1. 佈 2 顆 nginx（0002 的老朋友）
kubectl create deployment web --image=nginx:1.25 --replicas=2
kubectl rollout status deployment/web

# 2. expose 成 Service：沒給 --type 就是 ClusterIP；--port=80 會自動抓 containerPort
kubectl expose deployment web --port=80

# 3. 看 Service：CLUSTER-IP 就是那個「不會變的 VIP」
kubectl get svc web

# 4. 看 Endpoints：同名的 endpoints 物件列出此刻 2 顆 Pod 的 IP
kubectl get endpoints web
kubectl get pods -o wide -l app=web
#    比對：Endpoints 的 IP 就是那 2 顆 Pod 的 IP
從叢集內打 VIP
# 5. 起一顆常駐的 busybox 當「客戶端」（0009–0010 都要用）
kubectl run client --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/client

# 6. 把 VIP 存進變數，用 wget 打它（回傳 nginx 的 200 歡迎頁）
VIP=$(kubectl get svc web -o jsonpath='{.spec.clusterIP}')
echo $VIP
kubectl exec client -- wget -qO- "http://$VIP/" | head -n 5
刪一顆 Pod，看 Endpoints 自己更新
# 7. 挑一顆 Pod 刪掉，立刻重看 Endpoints
kubectl delete pod web-(隨機尾碼)

# 8. -w 看 Endpoints 的變化：舊 IP 消失，新 Pod Ready 後新 IP 補上
kubectl get endpoints web -w
#    想親眼看交替：開兩個終端，一邊跑這行、另一邊去刪 Pod（Ctrl+C 結束）
你該觀察到什麼

第 4 步是「Service 的真相」：它沒有自己的後端，selector 命中幾顆 Pod，Endpoints 就列幾個 IP。第 7–8 步是整個機制的精髓——Pod 換 IP、Service 不用動，Endpoints 控制器自動把名單換新，而你的客戶端永遠只需要記住 VIP。

實作 B：NodePort——把服務開到節點門口

ClusterIP 只活在叢集內；NodePort 在每台節點上開一個 30000–32767 的 port，外部（例如你的 WSL2 主機）打到「節點 IP:該 port」就能進來。真正從 host 連的示範留到 0011（那課會重建有 port mapping 的叢集），這裡先在叢集內驗證路徑通暢。

把 Service 升級成 NodePort
# 9. 刪掉舊 ClusterIP Service，改用 NodePort 重開（乾淨示範）
kubectl delete service web
kubectl expose deployment web --type=NodePort --port=80 --name=web-np

# 10. NODE(S) 欄：系統從 30000–32767 隨機配一個（例如 31234）
kubectl get svc web-np

# 11. 查節點的 IP（INTERNAL-IP）
kubectl get nodes -o wide
#    記下 kind-worker（或 control-plane）的 INTERNAL-IP，例如 172.18.0.3
在叢集內走「外部進來的路徑」
# 12. 用變數組出 NodeIP:NodePort，從 client pod 打
NODEIP=$(kubectl get nodes -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
NODEPORT=$(kubectl get svc web-np -o jsonpath='{.spec.ports[0].nodePort}')
kubectl exec client -- wget -qO- "http://$NODEIP:$NODEPORT/" | head -n 5
#    回 200 就代表 NodePort 路徑通了：封包 → 節點 port → iptables → 某顆 Pod

# 13. 驗證「哪台節點的 NodePort 都能到」：換 control-plane 的 IP 再打一次
NODEIP2=$(kubectl get nodes -o jsonpath='{.items[1].status.addresses[?(@.type=="InternalIP")].address}')
kubectl exec client -- wget -qO- "http://$NODEIP2:$NODEPORT/" | head -n 5
你該觀察到什麼

第 13 步的關鍵：NodePort 是「每台節點都開同一個 port、各自把流量轉進叢集」，所以不管打哪一台節點的 IP 都會通。LoadBalancer 其實就是「雲端造一台 LB，把流量送進任何一台節點的 NodePort」——你已經會 NodePort，LoadBalancer 的底層就懂了。

實作 C：Headless Service——不要 VIP，直接給我 IP 名單

某些場合（資料庫主從、StatefulSet）不想經由「VIP + 隨機轉發」，想要「DNS 直接回傳每顆 Pod 的 IP」。把 Service 的 clusterIP 設成 None，就是 Headless Service：不配 VIP、不轉發，只負責把 selector 命中清單餵給 DNS（細節下一課）。

建一個 headless Service
# 14. expose 時帶 --cluster-ip=None
kubectl expose deployment web --type=ClusterIP --name=web-hd --port=80 --cluster-ip=None

# 15. CLUSTER-IP 顯示 None
kubectl get svc web-hd

# 16. Endpoints 照樣列出身後 2 顆 Pod（headless 沒有 VIP，但 selector 照常運作）
kubectl get endpoints web-hd

# 17. 收尾：刪掉練習物件（保留 client 給下一課）
kubectl delete deployment web
kubectl delete svc web-np web-hd
kubectl get pods,svc,endpoints
考場小抄

① 建立：kubectl expose deployment NAME --port=80 [--type=NodePort|LoadBalancer|ClusterIP]；快速版 kubectl create service nodeport NAME --tcp=80:80。② 查後端：kubectl get endpoints NAME（連 Service 名稱同名的 endpoints）比對 get pods -o wide。③ 除錯口訣：Service 不通先查「selector 有沒有打到 Pod」——get endpoints 是空的就代表沒打到；再查 Pod 的 readiness（0007 的 READY 0/1）。④ NodePort 範圍 30000–32767。⑤ VIP ping 不通很正常，用 TCP 測。⑥ kube-proxy 是「在節點上實作 Service 規則」的那個人。

本課戰果

  • 你會用 expose 建立 ClusterIP Service，並看懂「selector → Endpoints → kube-proxy」的轉發鏈。
  • 你親眼看到刪 Pod 後 Endpoints 自動換新，Service 的 VIP 從頭到尾沒變。
  • 你用 NodePort 走通「外部 → 節點 → Pod」的路徑，並驗證任一台節點的 port 都通。
  • 你建立了 headless Service，看懂它「不要 VIP、只給 IP 名單」的定位。
