Kubernetes 詞彙表

課程共通詞彙表（建立於 Phase 0，於 Lesson 0005–0020 批量產出時擴充至全 20 課）· 所有課程與講解必須遵循此用語。英文術語一律保留原文，附繁體中文說明。

本表以 Kubernetes 官方詞彙表 為準。查不到的名詞先查官方文件，再決定是否補充至此。

基礎與叢集架構

Cluster（叢集）
一組執行容器化應用的節點（nodes）集合，由控制平面統一管理。Kubernetes 的最小部署單位就是一個叢集。
Control Plane（控制平面）
叢集的大腦，負責做出全局決策（如排程、擴縮容）並回應叢集事件。元件：kube-apiserver、etcd、kube-scheduler、kube-controller-manager、cloud-controller-manager。
Node（節點）
叢集內的工作機器，可以是實體機或虛擬機。分為「控制平面節點」（跑控制平面）與「工作節點」（跑你的工作負載）。節點上必有的元件：kubelet、kube-proxy、容器執行時期。
kube-apiserver
控制平面的前端，對外暴露 Kubernetes API。所有管理與控制指令都經由它進入叢集。
etcd
一致且高可用的鍵值儲存，Kubernetes 所有叢集狀態都存放在這裡。CKA 考備份與還原的重點。
kube-scheduler
負責為新建立的 Pod 選擇最合適的節點，考量資源需求、親和性、污點等條件。
kube-controller-manager
執行控制器流程的元件。控制器是一道迴圈，不斷把叢集現況推向期望狀態（例如 ReplicaSet 控制器確保副本數正確）。
kubelet
每個節點上的「節點代理人」，確保該節點上的容器依照 PodSpec 正常運行；也是「static pod」的管理者。
kube-proxy
節點上的網路代理人，實作 Service 的虛擬 IP 與負載平衡規則（iptables／IPVS）。
Container Runtime（容器執行時期）
實際啟動與管理容器的軟體（containerd、CRI-O…）。Kubelet 透過 CRI（Container Runtime Interface）與它溝通。
Pod
Kubernetes 最小的部署單位。一個 Pod 內可有一個或多個容器，共用網路與儲存。
Workload（工作負載）
跑在 Kubernetes 上的應用程式集合。管理工作負載的 API 物件包括 Deployment、ReplicaSet、StatefulSet、DaemonSet、Job、CronJob 等。
Controller（控制器）
一道比較期望狀態與現況並加以修正的迴圈。Kubernetes 的自我修復能力建立在控制器模式上。
kubectl
Kubernetes 的命令列工具，透過 kube-apiserver 與叢集互動。CKA 考試全程使用它。
Namespace（命名空間）
在叢集內切割資源範圍的機制，常用於隔離環境（如 dev/test/prod）。
Static Pod（靜態 Pod）
由 kubelet 直接從節點上的 /etc/kubernetes/manifests/ 目錄拉起、不經由 apiserver 排程的 Pod。控制平面的四個元件（kube-apiserver、kube-controller-manager、kube-scheduler、etcd）在 kubeadm 叢集裡都以 static pod 形式運行——想讓某個元件「消失」，搬走對應 manifest 即可。

物件與工作負載

Label（標籤）
附加在物件上的鍵值對，用於組織與選取物件。Selector 依標籤選擇物件。
Annotation（註解）
附加在物件上的鍵值對，僅附帶資訊（如記錄 change-cause），不可被 selector 選取——與 Label 的關鍵差別。
Selector（選擇器）
依 Label 挑選物件的條件。Deployment 用 selector 認領自己的 ReplicaSet，ReplicaSet 用 selector 認領自己的 Pod——控制器「認人」全靠它。分兩種寫法：equality-based（等值式，運算子 =、!=）與 set-based（集合式，運算子 in、notin、存在與否）。kubectl 用 -l 帶入。
Declarative（宣告式）vs Imperative（指令式）
宣告式：描述「期望狀態」（寫 YAML 交給 kubectl apply）；指令式：直接下「做什麼」（kubectl run）。Kubernetes 本質上偏宣告式。
Deployment
管理工作負載的控制器，負責聲明期望副本數並執行滾動更新與回滾。它不直接管 Pod，而是透過管理 ReplicaSet 來達成。
ReplicaSet
確保指定數量的 Pod 同時運行的控制器。通常被 Deployment 管理——Deployment 是它的「老闆」。Pod 數量不正確時由它補齊或縮減。
DaemonSet
確保每台節點恰好運行一顆 Pod 的控制器，適合節點級背景服務（日誌收集、監控 agent、CNI）。叢集新增節點時自動長一顆、節點移除時跟著收掉。它直接管理 Pod（中間沒有 ReplicaSet）。kubectl 沒有 kubectl create daemonset 指令，只能寫 YAML。
Job
負責「跑完就結束」任務的控制器。關鍵欄位：completions、parallelism、backoffLimit。Pod 的 restartPolicy 只能是 Never 或 OnFailure。kubectl create job 只有 --image／--from——批次欄位必須寫 YAML。它的自我修復是「補失敗、不補成功」。
CronJob
按 cron 排程（五欄時間）定時建立 Job 的控制器。控制器鏈：CronJob → Job → Pod。適合定時備份、定期清理等週期性工作。
Rolling Update（滾動更新）
Deployment 換版的方式：逐批建立新 Pod、移除舊 Pod，過程中隨時有可用副本，服務不中斷。
Rollback（回滾）
把 Deployment 退回先前的 revision（版本）。用 kubectl rollout undo 執行，CKA 常考。回滾本身也會產生一個新的 REVISION。
watch（-w）
kubectl 旗標（如 kubectl get pods -w）：先印出目前快照，再持續串流顯示物件的後續變化，直到 Ctrl+C。

資源、排程、設定與健康

requests（資源請求）
Pod 宣告「至少要這麼多」的資源額度（CPU／memory）。kube-scheduler 排程時以「節點上所有 Pod 的 requests 總和」為帳本；describe node 的 Allocated resources 就是這本帳。
limits（資源上限）
Pod 宣告「最多用這麼多」的使用天花板。CPU 超過會被節流（throttle）；memory 超過容器會被 OOMKilled。
QoS Class（服務品質等級）
依 Pod 的 requests／limits 寫法歸類：Guaranteed（有寫且 requests＝limits）、Burstable（有寫但不等）、BestEffort（全沒寫）。等級越低，OOM 時越早被殺。
Taint（污點）
標記在節點上、用來「排斥」Pod 的屬性。效果有三種：NoSchedule（不排新的）、PreferNoSchedule（盡量不排）、NoExecute（不排新的，並逐出已在上面且無 toleration 的 Pod）。正式叢集的 control-plane 節點帶有 node-role.kubernetes.io/control-plane:NoSchedule。語法：kubectl taint node <節點> <key>=<value>:<Effect>，移除加 -。
Toleration（容忍）
寫在 Pod 上、用來「容忍」特定污點的屬性。toleration 的 key／value（operator=Equal 時）／effect 三者都與污點對應，Pod 才被允許排到帶該污點的節點。容忍只是「允許」不是「偏好」；想逐出前寬限可用 tolerationSeconds（僅 NoExecute）。
nodeSelector（節點選擇器）
Pod 的 spec.nodeSelector：要求節點必須帶指定 label 才排得上去。只能表達「等於」，是 nodeAffinity 的簡化版。
Node Affinity（節點親和性）
Pod 的 spec.affinity.nodeAffinity：更強的表達力。requiredDuringSchedulingIgnoredDuringExecution＝硬性（等同 nodeSelector 但支援 In/NotIn）；preferredDuringSchedulingIgnoredDuringExecution＝軟性「盡量」。
ConfigMap
存放非機密設定的物件（明文），namespace 層級、上限約 1MiB。注入方式：envFrom（整包）、valueFrom.configMapKeyRef（單鍵）、volume 掛載（鍵變檔名）。volume 掛載的更新約 1 分鐘內由 kubelet 同步；env 注入不隨設定更新。
Secret
存放機密資料的物件，值以 base64 編碼存在 data（可用 stringData 寫明文、存檔自動轉換）。base64 不是加密；describe 只顯示大小。掛載成檔案的預設權限是 0644（與 ConfigMap 相同；想收緊就在 volume 設 defaultMode: 0400）。
Probe（探針）
kubelet 對容器做的週期健康檢查，三種實作：exec、httpGet、tcpSocket。參數 initialDelaySeconds／periodSeconds／failureThreshold 控制節奏與容忍度。
Liveness Probe
問「容器還活著嗎」。失敗→容器被殺掉重啟（RESTARTS 上升）。啟動很慢的容器若被它誤殺，改用 startupProbe 護航。
Readiness Probe
問「容器可以接流量嗎」。失敗→Pod 從 Service 的 Endpoints 摘除（不重啟）。症狀：Pod Running 但 READY 0/1。
Startup Probe
問「容器啟動完成了嗎」。成功前不會跑 liveness／readiness，保護啟動需要很久的容器不被誤殺。
HorizontalPodAutoscaler（HPA）
依 metrics API 的用量自動調整 Deployment／ReplicaSet 副本數的控制器。分母是 Pod 的 requests.cpu；沒寫 requests 或 metrics-server 沒資料時 TARGETS 顯示 <unknown>。
metrics-server
叢集級的用量蒐集器，把節點與 Pod 的 CPU／memory 餵給 metrics API，是 kubectl top 與 HPA 的前提。kind 安裝後需加 --kubelet-insecure-tls。

儲存

PersistentVolume（PV）
實際的儲存空間（NFS、雲端磁碟、hostPath…），叢集資源、不屬於任何 namespace。狀態：Available → Bound → Released；回收策略 Retain 會讓它停在 Released。
PersistentVolumeClaim（PVC）
「我要多大、什麼存取模式」的請求單，有 namespace。Kubernetes 依條件（容量、accessModes、storageClassName）找一顆符合的 PV 綁定；搭配預設 StorageClass 則會動態現做。
StorageClass
「動態供應」的工廠：PVC 一來就照參數（provisioner、reclaimPolicy、bindingMode）現做一顆 PV。kind 內建 local-path provisioner、類別名 standard。PVC 寫 storageClassName: "" 會關閉動態供應、去配靜態 PV。
Access Mode（存取模式）
PV/PVC 的掛載能力宣告：RWO（單節點讀寫）、ROX（多節點唯讀）、RWX（多節點讀寫，需共享儲存）。
Reclaim Policy（回收策略）
PV 被釋放後如何處理：Delete＝連底層儲存一起刪（動態供應常見）；Retain＝磁碟保留、PV 標成 Released 等管理者接手。PVC 刪掉 PV 卻還在，多半是 Retain。
CSI（Container Storage Interface）
Kubernetes 與儲存廠商之間的外掛標準，讓任何廠商（雲端磁碟、NFS…）不用改核心就能提供 volume。口訣：CSI 管「存」。

網路

Service
一群 Pod 前面的「穩定入口」：selector 打到哪些 Pod，Endpoints 就列誰，kube-proxy 在節點上寫規則轉發。類型：ClusterIP、NodePort、LoadBalancer、ExternalName。
ClusterIP
Service 的預設類型：一個只活在叢集內的虛擬 IP（VIP）。它是 iptables/IPVS 規則做出來的「假 IP」，所以 ping 不通很正常，要用 TCP 測。
NodePort
ClusterIP + 每台節點開一個 30000–32767 的 port。外部打「任一節點 IP:該 port」都能進叢集（每台節點都開同一個 port）。
LoadBalancer
NodePort + 雲端供應商幫你生一個對外負載平衡器。kind 沒有雲端整合，需要 MetalLB 之類的方案（概念即可）。
Endpoints / EndpointSlice
「Service 身後此刻有哪些 Pod IP:Port」的清單，由 Endpoints 控制器依 selector 自動維護。除錯 Service 的第一站：kubectl get endpoints NAME——空＝selector 沒打到或 Pod 不 Ready。
Headless Service
clusterIP: None 的 Service：不配 VIP、不做轉發，讓 DNS 直接回傳每顆 Pod 的 IP。適合資料庫主從這類要「直接連各顆 Pod」的情境。
CoreDNS
叢集內建的 DNS 伺服器（Deployment，跑在 kube-system，Service 名叫 kube-dns）。watch Service/Pod 產生 DNS 紀錄；設定在 ConfigMap coredns 的 Corefile。
Service Discovery（服務發現）
Pod 用「名字」找到 Service 的機制。FQDN 樣板：<service>.<namespace>.svc.cluster.local；短名靠 /etc/resolv.conf 的 search 欄自動補後綴。
Ingress
L7（HTTP/HTTPS）路由規則：宣告 host＋path 轉到哪個 Service。它只是資料，要靠 Ingress Controller 執行。
IngressClass
「指名用哪家 Ingress Controller」的接頭。Ingress 資源用 ingressClassName 引用它；一個叢集可同時有多家 Controller。
Ingress Controller
真正收外部流量、把 Ingress 規則翻譯成實際設定的程式（如 ingress-nginx）。ADDRESS 空著通常代表 Controller 沒起來。
Gateway API
Ingress 的下一代 API：用 CRD 拆成 GatewayClass／Gateway／HTTPRoute 等角色，表達力更強（headers 路由、權重、跨 namespace）。CKA 考概念即可。
NetworkPolicy
叢集內防火牆的 API：宣告哪些來源可連到哪些 Pod 的哪些 port。預設全通；一出現 policy，被選中的方向（Ingress/Egress）就翻成預設拒絕。要支援它的 CNI（如 Calico）才真的執行——kindnet 不支援。
CNI（Container Network Interface）
把容器接上叢集網路、分配 Pod IP 的標準介面。實作：kindnet（輕量、不實作 NetworkPolicy）、Calico、Cilium、Flannel 等。口訣：CNI 管「網」。
Calico
老牌 CNI 實作，用 BGP／VXLAN 建 Pod 網路，並以 iptables/eBPF 實作 NetworkPolicy。kind 安裝方式見 0012。

叢集管理與安全

ServiceAccount
Pod 用的「身分」。Pod 以 serviceAccountName 指名後，token 會自動掛進 /var/run/secrets/kubernetes.io/serviceaccount。本身不授權，權限靠 RBAC 另外給。
RBAC
Role-Based Access Control：以「角色」管理授權。核心四物件：Role／ClusterRole（權限）、RoleBinding／ClusterRoleBinding（綁定）。驗證工具：kubectl auth can-i。
Role
namespace 層級的權限清單（rules：apiGroups＋resources＋verbs）。
RoleBinding
把 Role 或 ClusterRole 綁給身分，只在某 namespace 內生效。ClusterRole × RoleBinding＝被侷限回該 namespace（考點）。
ClusterRole
叢集層級的權限清單，可用於 node、PV 等叢集資源。
ClusterRoleBinding
把 ClusterRole 綁給身分，全叢集生效。內建常用 ClusterRole：view／edit／cluster-admin。
kubeadm
官方叢集建置工具。init 產生憑證與 kubeconfig、把控制平面寫成 /etc/kubernetes/manifests 的 static pod、發出 bootstrap token；join 讓 worker／額外 cp 加入。token 過期用 kubeadm token create --print-join-command 重生。
HA（高可用）控制平面
多台 control-plane 用負載平衡器共享 apiserver 流量。拓撲分 stacked etcd（etcd 與 cp 同台）與 external etcd（etcd 獨立主機）。
kubeconfig（kubectl 組態檔）
定義叢集、使用者與 context 的檔案（預設 ~/.kube/config）。kubeadm 產出管理員版的 /etc/kubernetes/admin.conf。也代表各元件的「身分證」（admin/controller-manager/scheduler/kubelet 各一把）。
etcdctl
etcd 的命令列客戶端。備份/還原三大指令：snapshot save、snapshot status、snapshot restore；指令前慣例加 ETCDCTL_API=3。
Snapshot（etcd 快照）
把整個 etcd 資料庫倒成的單一檔案。restore 會把它解成一個新的資料目錄（非原地復活），再接回給 etcd。還原點＝快照時間點。
cordon
把節點標成不可排程（SchedulingDisabled）：不再排新 Pod，但不驅離已在跑的 Pod。
drain
cordon＋把節點上的 Pod 安全驅離（evict）到別處。常配 --ignore-daemonsets；DaemonSet 的 Pod 不該被搬走。
uncordon
解除不可排程標記，讓節點恢復收 Pod。
kubeadm upgrade（kubeadm 升級）
升級叢集的流程：一次一小版、cp 先 node 後；每台節點內「升 kubeadm → upgrade apply（cp）／upgrade node（worker）→ 升 kubelet 並重啟」。憑證檢查：kubeadm certs check-expiration／renew all。

發佈與擴充

Helm
Kubernetes 的套件管理員。把一整組 YAML（Deployment/Service/…）打包成 chart 安裝；一次安裝叫一個 release，可 upgrade／rollback／uninstall。
Chart（Helm 圖表）
Helm 的套件格式：模板 + values 預設值 + 中繼資料。安裝時可用 --set 或 values 檔覆寫預設值。
Kustomize
不寫模板的宣告式組態工具：base（基底）＋overlay（疊加差異）。kubectl apply -k 目錄 套用；kubectl kustomize 目錄 先預覽。
CRD（Custom Resource Definition）
定義「新品種 API 資源」的資源。apply CRD 之後，kubectl 就認得新資源型別（apiVersion 是 group/version）。
Custom Resource（自訂資源）
CRD 定義型別之後被建立的實例。會被 apiserver 接受並存進 etcd，但沒有 controller 的話只是一筆資料。
Operator
「watch 某種 CR、把它變成實際資源」的控制器（控制器模式延伸到自訂資源）。例：prometheus-operator 看 Prometheus CR 建出整套監控。

故障排除與備考

CrashLoopBackOff
容器不斷「啟動→失敗→重啟」的狀態（指數退避）。診斷：logs、logs --previous 看上次死因。
ImagePullBackOff
映像拉取失敗的狀態（前身 ErrImagePull）。根因多半寫在 describe 的 Events（tag 不存在、映像名錯）。
OOMKilled
容器用量超過 memory limit 被核心殺掉。指紋：Exit Code 137（128+9 SIGKILL）、describe 的 Reason=OOMKilled。
Pending
Pod 排不上去的狀態。看 describe 的 Events：Insufficient memory/cpu、nodeSelector 沒節點、taint 沒 toleration 都寫在這裡。
FailedScheduling（排程失敗事件）
Pod 排不上任何節點時，scheduler 記在「該 Pod」身上的 Warning 事件（describe pod 的 Events 可見），訊息形如 0/N nodes are available: … Insufficient cpu/memory，也會混入 taint／nodeSelector 等其他理由。對照 describe node 的 Allocated resources（節點帳本）即可定位「排不下」。
Node Conditions（節點條件）
describe node 的 Conditions 區塊。Ready=False 查 kubelet；MemoryPressure／DiskPressure／PIDPressure 代表節點資源告急。
Killer.sh
CKA 官方指定的模擬考環境（購考附 2 次、各 36 小時、17 題，與真實考試同介面）。考前衝刺用它計時演練。
